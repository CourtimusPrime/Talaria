<objective>
Build the second front end — the thin one, on the other machine.

Purpose: D-05-01 chose two front ends over one engine made headless, and the reason is the core value.
Making the shell headless so the local interface is always a client would put serialise, encode,
transmit, decode and present in the middle of the **local** path that Phase 1 measured at 4–36 ms, and
would require separating the interface from the engine's graphics context — the two share one, which
is why the interface library's version is pinned to the engine's workspace. That is the largest
available refactor in this codebase, and it buys uniformity, not capability. So the server stays
exactly what it is and gains one route, and this plan builds a client that does not link the engine at
all.

That last part is a real user-facing benefit rather than an implementation detail: a client with no
engine builds in seconds and runs on a laptop with none of the engine's native build prerequisites.
It also costs this plan the one thing `05-PATTERNS.md` could not find an analog for — creating a
graphics context without the engine's own context type. That is a bounded, named task here rather
than an assumption that it falls out of the interface library's constructor.

This plan ends when the client can connect, authenticate, and list the server's agent tabs. Frames and
input are 05-09; the rate controller and the degrade reporting are 05-10.

Output: a new binary crate, its window and graphics context, its secure WebSocket connection, its
connection-state and tab-list interface, and a launcher in the test harness.
</objective>

<interfaces>
**What the client copies from the shell, and what it must not.** `05-PATTERNS.md` maps this in detail;
the short version:

*Copies:* the result type on the entry point; a typed event loop with a user-event channel; spawning
the network thread with a cloned loop proxy **before** the loop runs; the two-state application enum
and the window creation in the resume handler; the drain-then-set-wait discipline in the new-events
handler; the interface library's setup after the graphics context exists, including the icon font
registration, so the two front ends do not diverge visually; and the rule that the interface returns
a list of intents and mutates nothing.

*Does not copy:* the single-instance forwarding dance, which exists because one process owns the
control socket **and** the engine's profile directory — a client owns neither, and two clients on one
machine is a legitimate state; the engine builder and its logging installation; the engine's own
window graphics context type; and the default-URL and search-engine resolution, because the client's
argument is a server address, not a page.

*Copies with a changed reason:* the cryptography provider installation stays first and stays
load-bearing, but now for the **client's own** transport security rather than for the engine's network
stack. Rewrite the comment — copying a comment about the engine's logging into a crate with no engine
would be a lie, and the shell's comment explicitly explains why no logger is installed there, which
does not hold here. The client needs its own logging initialisation or none, decided and stated.

**The graphics-context gap, and the answer that costs nothing.** The shell's interface is constructed
from the engine's own graphics context and its function loader. The client has no engine. The
workspace's lockfile already resolves the low-level graphics abstraction the engine itself uses, plus
the window-handle crate and the bindings crate the interface library draws through. Taking the
graphics abstraction as a **direct** dependency at the version already resolved should unify onto the
existing node and add nothing — the same result the research observed when it tested adding the image
crate. **Verify that with a resolution run before committing to it**, following 05-01's procedure, and
if it does not hold, record what it costs and take the fallback: land a window-and-context helper
through the same hand-edit-and-resolve procedure with its own legitimacy note in the manifest, the way
the existing interface-backend line carries one. Either way the answer is a measured number, not a
guess. This is the one construction step `05-PATTERNS.md` marks as unmapped and asks be treated as a
bounded task.

**The transport dependency was already measured.** 05-01 ran the hand-edit-and-resolve procedure
against a throwaway manifest adding the WebSocket client with a rustls-based transport-security
feature, recorded the added-package count, and restored the lockfile. Read that number from
`05-01-SPIKE.md` and land the same edit for real. Everything a rustls client needs — the async
adapter, the platform trust roots, the web trust roots, the platform verifier and the handshake hash
— is already resolved in this workspace, so the expected cost is small. Assert it rather than assume
it, and assert the release-candidate elliptic-curve pin survived.

**Where the credential comes from, and where it must not.** Not the command line. On Linux every
account on the machine can read another process's arguments, so a token in argv is a token in a
world-readable file that happens to be virtual. Read it from an environment variable, or from an
owner-only file in the client's own configuration directory, and never interpolate it into a log —
the server's own module already establishes that rule and the helper that satisfies it, naming a
credential in a log by a short digest prefix rather than by its value. Copy the rule, not the helper.

**Certificate verification is not optional and must not become configurable.** The server is fronted
by a daemon-managed certificate for a real name, so the platform's trust roots verify it without any
special handling. There is deliberately no way to turn verification off: an escape hatch added "for
local testing" is the one that ships, and the end-to-end suite has a legitimate path that does not
need it, because a loopback test connects to the browser's own listener without transport security at
all rather than with it disabled.

**Which address the client is given.** One positional argument: the server's base URL. Against a real
deployment that is the proxied secure address 05-04's script prints. Against the harness it is the
loopback address the shell bound, without transport security. The client derives the view endpoint
from the base URL rather than being told both, so the two cannot disagree — the same single-source
discipline the server applies to its own advertised identity.

**Interface register.** There is no design contract for this phase — the gate did not fire, because
the client is a new binary rather than a change to the existing chrome. `04-UI-SPEC.md` is still the
register to write in: plain sentences, the fact first and the next step second, no exclamation, no
jargon, no reassurance, and untrusted values fenced or marked as claimed rather than repeated as fact.
Read its copy tables before writing a line of user-facing text. The server name a client was pointed
at is a value the human typed, so it is not untrusted — but a **tab title** on the list comes from a
page, and every one of those goes through truncation and sanitisation exactly as the server's own
lists do.

**The pairing constraint, stated rather than hidden.** Authorising this client for the first time
requires a human at the server machine, because approval happens in the server's own chrome. 05-01
recorded that as an open product decision with three ways out and noted that the plans are written
against accepting it. The first-run copy says so plainly and says what to do — that is the whole of
what "accepting it" costs, and hiding it would turn a property into a bug report.
</interfaces>

    cloned loop proxy, following the degrade-with-an-event spawn shape rather than the expect-and-die

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the client process → every other account on the client machine | Process arguments are world-readable on this platform; an owner-only file and an environment variable are not equivalent to an argument |
| the client → the server it was pointed at | Without certificate verification the client will talk to whoever answers, and the channel carries a credential and then raw input |
| a page-supplied tab title → the client's own interface | The same untrusted claim the server's lists handle, in a surface that has never handled one before |
| the network thread → the interface state | A thread that touched the interface directly would reintroduce exactly the borrow hazards the server's intent convention exists to prevent |

| T-05-07-C | Information Disclosure | the bearer credential in process arguments, readable by every other local account | high | mitigate | Read from an environment variable or an owner-only file, never from the command line, with the reason in a comment at the read rather than only in a plan.
