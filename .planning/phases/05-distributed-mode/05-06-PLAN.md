<objective>
Let a human on another machine drive an agent's tab — and let nothing else.

Purpose: this is the plan that puts a **human input channel on a network port**, which
`05-RESEARCH.md` correctly calls a different and in places worse surface than Phase 4's agent tool
channel. An agent gets an allowlisted vocabulary of nine tools. A viewer gets raw clicks and
keystrokes into a live, logged-in session. Five of the phase's high-severity threats live here, and
four of them are closed by where a lookup happens rather than by what a check returns.

The codebase has already reasoned about this once and reached the right answer. `ChromeRect`'s doc
comment refuses to expose chrome geometry to agents **because** it would let something aim synthetic
input at the credentials button. That reasoning was written for agents; it applies verbatim to the
party this phase adds, and it is now sharper, because a viewer sends real coordinates rather than
tool calls.

`05-PATTERNS.md` found the trap that would otherwise make this plan's bug silent. The three
forwarders each begin by resolving the tab the local human is *displaying*, and the toolbar offset
reaches all three through one cached cursor position: only the motion forwarder subtracts it, and the
button and wheel forwarders inherit it by reading that cache back. So a remote path that reused the
cache would apply a local window's toolbar offset to a remote coordinate — every remote click landing
some forty pixels above where the human aimed, with nothing erroring, links near the top of a page
appearing to work and links below a control appearing "flaky". The fix is a signature change, not a
redesign, and the assertion that catches a regression is naming the **specific element hit**, not
merely that a navigation occurred.

Output: three generalised delivery functions, a wire-to-engine keyboard mapping sharing one table
with the existing one, a single validating entry point from the wire, and the end-to-end assertions
that pin all four of the structural guarantees.
</objective>

<interfaces>
**The three functions, and the exact shape of the change** (`app.rs:1316-1394`, quoted in full in
`05-PATTERNS.md`). All three begin by resolving the displayed tab's webview and returning early if
there is none. The motion forwarder then subtracts the toolbar height in device pixels from the
y coordinate, stores the result in the cached cursor position, reads the previous value, and either
emits a left-viewport event or a motion event depending on whether the point is inside the target's
viewport rectangle. The button and wheel forwarders read that cached position back and use it as
their own coordinate.

Split each into two layers:

- a **delivery** function taking a webview reference and a point **already relative to that tab's
  viewport**, doing the viewport containment check against **that** webview's own size and calling
  the engine's input entry point. `05-RESEARCH.md`'s code example shows the shape; the engine's entry
  point is a method on a webview, so this is a signature change rather than a redesign;
- a thin **local** caller that resolves the displayed tab, subtracts the toolbar height, maintains
  the cached cursor position and the left-viewport transition, and then calls the delivery function.

The local behaviour must not change at all. The offset subtraction moves to the call site; the cache
stays exactly where it is and keeps exactly the meaning it has. The remote path calls the delivery
functions directly, resolves its own webview through the agent-only lookup 05-05 added, and carries
its own coordinates on every message — which is why the wire puts coordinates on the button and wheel
messages too, rather than relying on a previous motion.

**The viewport check is the clamp untrusted coordinates need, and it already exists.** The
containment test against the target's size is exactly the check a hostile coordinate should meet, and
running it against the *target* tab rather than the displayed one is the whole of the correctness
requirement. A coordinate outside it is a refusal, not a clamp-to-edge: clamping would turn "aim at
nothing" into "aim at the nearest thing", which is a worse answer.

**Keys** (`keyutils.rs`, the whole file, 62 lines). The existing mapping takes a window-system key
event and returns an optional engine keyboard event, mapping a character key straight through and a
named key through a hand-written table, with an unmapped name returning nothing. Add a sibling taking
a state plus either a character or a named key name, **sharing the table**. Extract the arm list into
a name-to-named-key mapping both call, or the two will drift and the drift will be invisible until
one key works on one path and not the other. Do **not** put a window-system key event on the wire:
not all of its fields are constructible, and forging one would be a lie about provenance.

**Where the sequence state lives.** 05-05 put a last-seen input sequence on the view session. This
plan enforces it: strictly increasing per connection, a non-increasing value dropped, and the applied
value recorded so 05-08's frame header can echo it. That one field gives replay resistance within a
connection, ordering under coalescing, and the latency measurement — which is why
`05-RESEARCH.md` asks for it as one field rather than three mechanisms.

**Chrome unreachability is structural, and this is where it is made so.** The local window-event arms
route to the chrome **first** — the browser shortcut handler intercepts before the page sees a key,
and the interface-action queue is applied after the chrome's own frame. The remote path must have no
equivalent branch: it lives in its own module, and that module calls only the delivery functions. The
end-to-end proof uses the chrome-geometry test hook to fetch a real toolbar control's rectangle and
aims remote input at that coordinate, then asserts no panel opened. That is the assertion that would
catch a future refactor routing remote input through the local window-event path.

**Assert through a different channel from the one under test.** The revocation suite's control-socket
helper exists for exactly this and its docstring says so. A remote click's effect is asserted on the
tab's URL **over the control socket**, so the assertion does not depend on the frame path — which at
this point in the phase does not exist yet, and which is the point: the input half is provable on its
own.

**What remote input must not do**, from `05-RESEARCH.md`'s anti-pattern list, each of which is a
plausible-looking line somebody could write: resolve the displayed tab; write the cached cursor
position; apply the toolbar offset; change the active tab, the view mode or the window focus. A
viewer sending input is not a viewer choosing what the human sees — a remote click must not pull the
human's window onto a different tab, and the human switching tabs must not redirect the remote click.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the view wire → the engine's input entry point | Raw clicks and keystrokes from a network peer entering a live, logged-in browsing session |
| remote input → the browser's own chrome | The credentials control, the bookmark star and a downloads row's open control are all one coordinate away if the path is wide enough |
| remote input → the human's own tabs | Where the history rows, the bookmarks and the autofilled credentials live |
| remote input → the local pointer's cached position | Two input sources sharing one cache contaminate each other in both directions |
| a captured input message → a repeat of a destructive action | Within one connection, nothing but a sequence rule stops a replay |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-04 | Elevation of Privilege | remote input reaching the browser chrome — synthetic clicks at the credentials control, the bookmark star, or a downloads row's open control, which hands a file to the operating system's default application | high | mitigate | Structural: the remote path lives in one module that calls only the three delivery functions, and a source criterion asserts the chrome types, the shortcut handler and the interface-action queue appear in it zero times. Proven end to end by fetching a **real** toolbar control's rectangle through the chrome-geometry test hook, aiming remote input at that coordinate, and asserting with the absent-rectangle wait that no panel opened. The reasoning is not new — the protocol crate's chrome-rect comment made this exact argument for agents, and this plan applies it verbatim to the party the phase adds |
| T-05-05 | Elevation of Privilege / Information Disclosure | remote input reaching a tab the human owns | high | mitigate | Resolution goes through the agent-only lookup, which yields nothing for a human-owned tab, so it is unrepresentable rather than refused downstream. A human-owned tab and a nonexistent tab take the same exit and produce the same answer, so the channel is not an enumeration oracle either. Asserted at unit level and end to end, with the connection staying open so the refusal is a refusal rather than a disconnection |
| T-05-04-A | Tampering | the local toolbar offset applied to a remote coordinate — every remote click landing some forty pixels high, with nothing erroring | high | mitigate | The offset moves to the local call site and the delivery functions take an already-viewport-relative point, so applying it remotely is not expressible without adding a line the module's own comments forbid at the point somebody would add it. The regression assertion names the **specific element hit**, in both directions — a lower link and an upper link on a fixture with known positions — because an assertion that merely checked "a navigation occurred" would pass with the offset wrongly applied |
| T-05-04-B | Tampering | remote and local input cross-contaminating through the shared cursor cache | high | mitigate | The remote path never writes the cache; a source criterion asserts the field appears in the module zero times, and the wire carries coordinates on every pointer message precisely so the remote path needs no cached previous position |
| T-05-11 | Denial of Service | malformed wire input crashing, wedging, or being silently defaulted | medium | mitigate | Structural refusal is the decoder's (05-03); semantic refusal is this module's, and every one of the five cases — an unattached tab, a coordinate outside the target's viewport, a non-increasing sequence, an unmapped key name, an unrecognised wheel mode — is an explicit refusal with its own unit test. A coordinate outside the viewport is **refused, not clamped**, because clamping turns "aim at nothing" into "aim at the nearest thing" |
| T-05-15 | Tampering | replay of a captured input message within a connection | low | mitigate | The sequence is strictly increasing per connection and a non-increasing value is dropped, with per-connection isolation unit-tested so two viewers cannot starve each other, and a verbatim replay asserted to have no effect end to end. The cross-connection case is TLS's, which 05-04 landed |
| T-05-04-C | Tampering | a viewer's input redirecting what the local human is looking at, or the local human's tab switch redirecting a viewer's clicks | medium | mitigate | The remote path never resolves the displayed tab and never touches the active-tab or view-mode state — asserted by source criteria returning 0 and by an end-to-end assertion that the view mode and active tab are unchanged after a full remote input sequence |
| T-05-SC | Tampering | package installs | n/a | accept | No dependency change; 05-01 landed the phase's one addition with its audit recorded there |

ASVS level 1; block on high. All four high-severity items are mitigated **within this plan**, and all
four are mitigated by shape rather than by check: the chrome is unreachable because no type connects
the module to it; the human's tabs are unreachable because the lookup cannot name one; the offset is
unappliable because the delivery functions do not take a window coordinate; and the cache is
uncontaminable because the wire carries what the cache would have supplied. Each is asserted by a
source criterion returning zero and, for the two that a reader would most want proven, by an
end-to-end assertion that would fail on the plausible-looking regression rather than on an obvious one.
