<objective>
Measure the one number this phase cannot be planned without, and re-measure the two it was planned
on synthetic data.

Purpose: `05-RESEARCH.md` names `OffscreenRenderingContext::read_to_image` at a 30 ms cadence as
**the largest unknown in the phase** and marks it assumption **A1** — the highest-risk row in its
own log. Phase 1's 4–36 ms envelope includes a readback, which bounds it loosely, but "loosely
bounded once" is not "sustainable thirty-three times a second alongside the local chrome's own
render". And it matters twice over, because the e2e harness runs under **Xvfb on llvmpipe software
rendering**, where a 4 MB `glReadPixels` may cost far more than it does on the developer's real GPU.
If the Xvfb number is 15–20 ms, the harness can never demonstrate SC 2 by cadence alone and 05-10's
latency suite has to assert something else — which is a decision to make now, from a number, rather
than in the middle of writing a test.

The second half re-settles assumption **A8**. Every encoding figure D-05-05 rests on — 2.16 ms and
522 KB for a keyframe, 0.14 ms for a whole-frame dirty-tile scan, 0.007 ms for a caret tile — came
from *synthetic* frames, not from a Servo readback. The research says so plainly and asks for a
re-measure. Real pages should bracket between its page-like and photo-like cases, but "should" is
not a measurement, and the entire codec decision rests on these numbers.

Output: a written A1 and A8 answer with numbers, run against real Servo output on this machine, and
a stated instruction for what 05-08 does if the Xvfb figure cannot carry the cadence.
</objective>

<interfaces>
**What the capture path actually is today** (`app.rs:399-421`, quoted in `05-PATTERNS.md`):
`webview.paint()`, then `context.size2d().to_i32()`, then a `euclid::Box2D::from_origin_and_size`
over the whole surface, then `context.read_to_image(rect)`, which returns
`Option<servo::RgbaImage>` — `None` means the framebuffer read failed. `hide_after` re-hides a
background tab that was shown only to produce a frame. The one call site is `capture_now`, reached
from the `Command::Screenshot` dispatch at `app.rs:2189-2229`, which pushes onto `pending_captures`
with a 1.5 s deadline.

**What the pump will do differently, and why the measurement must match it.** The pump does not wait
for `notify_new_frame_ready` — Servo's own documentation says an embedder may call `paint()` and
present without one, and "Servo will repaint even without first calling" it
(`servo-0.4.0/webview.rs:77`). So the pump paints unconditionally on its own tick and lets the tile
diff decide whether anything is worth sending, and it holds the tab `show()`n for the life of the
view session rather than cycling show/hide per frame. **Measure that shape**, not the screenshot
shape: a sustained loop of `paint()` plus `read_to_image` on a shown tab, at a fixed interval, with
the window's own chrome still rendering.

**`servo::RgbaImage` is `image::RgbaImage`** — `ImageBuffer<Rgba<u8>, Vec<u8>>` — and is therefore
`Send`, which is the property that makes moving the diff and the encode to a worker thread possible.
Confirm that it still compiles as a `Send` value in this tree; the whole off-thread design depends
on it and it costs one line to prove.

**The encoder to measure against, and the one to leave alone.** `encode_screenshot`
(`app.rs:2494-2519`) sets colour and depth and nothing else, so it runs at `png::Compression::Default`
by omission. D-05-05 keeps it exactly as it is — a one-shot agent screenshot should be small and
lossless — and gives the frame path a **sibling** that diverges on three lines: a fast compression
setting, a `Sub` filter, and no base64. Measure both against the same real readback so the SUMMARY
can state the ratio rather than quoting a synthetic table.

**Two displays, two answers.** The harness creates Xvfb at `1280x800x24` on `TALARIA_E2E_DISPLAY`
(default `:99`), which is llvmpipe. This machine is a headless ThinkPad with no display manager, so
"real hardware" here means whatever GPU path is available without X — if no non-llvmpipe path exists
on this machine at all, **say so explicitly and report one number with that caveat**, rather than
inventing a second. An honest single number with a stated limitation is worth more than a fabricated
comparison, and it is itself a finding: it would mean this repository cannot measure the product's
real-hardware behaviour, which belongs in `VERIFICATION.md` as a manual item.

**What "at cadence" means concretely.** Run the loop at a 30 ms target for at least 300 iterations
against three page shapes: a mostly-static text page, a page mid-scroll (drive it with a small
scripted scroll between ticks), and an image-heavy page. Report per-tick readback time as a
distribution — mean, median, p95, max — not a mean alone, because a p95 that blows the budget is what
a user feels and a mean hides it.
</interfaces>
