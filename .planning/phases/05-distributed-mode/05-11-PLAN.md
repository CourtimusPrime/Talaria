<objective>
Close the phase: say publicly what was built, correct three claims that are now wrong, and turn the one
verification this harness cannot perform into a script somebody can run.

Purpose: this phase changes the published threat model more than any before it. Phase 4 added an
unauthenticated network peer as a hostile party. Phase 5 adds a **remote human**, and that party is
genuinely different from every party already described: more trusted than an agent, because they are
the trust root at a distance and `SECURITY.md` already says hardening must not quietly restrict the
human path; less verifiable than the human at the keyboard, because their identity is a bearer token
rather than physical presence; and the first party in this browser's history that sends **raw input**
rather than tool calls. A document that described four parties and now governs five is a document that
is wrong in the most consequential place it could be.

It also has one property to record before somebody deletes it by accident. The origin refusal is the
outermost layer, a browser always sends an origin header, and therefore cross-site WebSocket hijacking
is closed **by construction** and a browser-based viewer is **structurally impossible**. The research
is explicit that this reads like an inconvenience to anyone who does not know what it is for, and that
the failure mode is somebody adding a small web viewer, finding it refused, and relaxing the rule.
Writing down what the layer is load-bearing for turns that diff from a convenience into a visible
deletion.

Three claims are now wrong and are corrected here: the published statement that there is no encryption
and no non-loopback reach; the description of the shared vocabulary crate as the distributed-mode wire,
which survives in the generated project instructions even after 05-03 fixed the module headers those
instructions derive from; and — already corrected in 05-01 — the inherited note naming a configuration
struct as this project's certificate route.

Output: a rewritten security section, a changelog entry, three corrected claims, an executable
two-machine check, and Success Criterion 3's evidence collected rather than asserted.
</objective>

**What `SECURITY.md` says today and where each piece needs to change.** It is organised as: reporting,
the trust model stated plainly (four parties), what is enforced today, what revocation guarantees,
known limitations, and out of scope. The register is plain prose that argues rather than lists, and the

The pieces:

- **The trust model gains a fifth party**, and the paragraph on the fourth needs a sentence: an
  unauthenticated network peer used to mean "anything that can open a connection to the loopback
  listener". Under an overlay-network exposure it becomes "any device in the tailnet, plus whatever the
  tailnet's access rules admit" — a set governed by a web console outside this repository. That is a
  real widening and the document should say so rather than let a reader assume the old sentence still
  bounds it.
- **"What is enforced today" gains the view channel**: off by default like the rest of the listener; a
  bearer check the route performs in its own right rather than inheriting; agent tabs only, through a
  lookup that cannot name a human-owned tab; refusals that do not distinguish which rule was broken; the
  chrome unreachable from the input path; revocation closing the socket; and a monotonic sequence.

  replacing rather than editing. What is true instead: the bind is still `127.0.0.1` and now
  permanently rather than provisionally, because the exposure mechanism chosen puts encryption in front
  of the loopback listener rather than widening it; every published authorization URL uses the secure
  scheme once an identity is advertised; and this browser issues, loads and renews no certificate at
  all. Say what that buys — no expiry timer, no resolver that re-reads files, no day-ninety-one

    route, and it refuses any request carrying an origin header. WebSockets are not subject to the
    same-origin policy and have no preflight, so origin enforcement is entirely the server's job and
    forgetting it is what cross-site WebSocket hijacking is. Talaria's layer closes it by construction
    and in the strictest direction: a browser always sends the header, so a browser can never connect.
    The native client is therefore a **consequence** of that layer rather than a preference. State it as
    a property to keep, and say what its deletion would look like — a diff that adds an origin allowlist
    — so a reader who sees one knows what it costs.

    *The public-internet exposure variant is refused.* Name it, say what it does — exposes the service

    differ by a few characters. The setup script refuses an argument asking for it. A named non-option
    is safer than an unconsidered one.

    viewer **is** a remote-control primitive, by design. That is the feature. None of the layers above
    stop it and none should. The boundary is which clients you authorise — the same sentence this
    document already uses about agents, now with sharper teeth, because a viewer sends real clicks into

    tabs, cannot reach the chrome, cannot open or navigate anything, and cannot call a tool.

    loopback port, so the token is checked first and they are at most a second check.
