<objective>
Close the loop. This is the plan where a human on another machine can watch an agent's tab and take
it over.

Purpose: everything before this has been one half of a pair. The server can hold a tab shown, read it
back and stream tiles; the client can connect, authenticate and list. This plan makes the client
render what arrives and send what the human does, which is Success Criterion 1 in full and the first
moment the phase's product claim is demonstrable rather than assembled.

It also contains the client-side mirror of the trap `05-PATTERNS.md` found on the server. There, the
toolbar offset reached three input functions through one cached position, and a remote path that
reused it would have put every click forty pixels high with nothing erroring. Here, the client draws
its own interface above the page and fits a server surface of one size into a window of another —
so there are two transforms between a human's pointer and a page's coordinate space, and if the
picture's transform and the pointer's transform are written separately they will disagree the first
time either changes. **One transform, defined once, inverted at the other end.**

One design decision is worth stating up front because the obvious alternative is tempting and wrong:
**the viewer adapts to the page, not the page to the viewer.** The client could tell the server its
window size and have the tab resized to match, which would make coordinates one-to-one and delete the
transform entirely. It would also reflow an agent's page because a human started watching, resize it
again when the local human displayed it, and make an agent's layout a function of who is looking. The
transform is the cheaper cost.

Output: frame presentation with keyframes, deltas and ordering; input capture with one inverse
transform and a monotonic sequence; and an end-to-end proof that drives the real client binary with a
real pointer and asserts the effect on the server through a different channel.
</objective>

<interfaces>
**The presentation seam the server already demonstrates** (`gui.rs:2504-2527`). The shell adds a paint
callback into the background layer and, inside it, draws the displayed tab's own surface through the
graphics context. The client's callback does the same thing with different contents: it draws a
texture the client uploaded from decoded tiles. Everything about the seam transfers — the layer, the
callback, the rectangle-in-pixels conversion — and only the drawing call differs.

Note what sits immediately above that code in the shell: a resize of the webview when the available
area no longer matches. **The client has no equivalent.** Its response to its own window changing is
to recompute the fit transform, not to ask anybody to resize anything.

**The fit transform, defined once.** The server declares a full-frame size in every header. The client
has a content area — its window minus its own interface. Fit the former inside the latter preserving
aspect ratio: one scale factor, and an origin offset that centres the result, leaving margins on two
sides. That triple — scale, origin x, origin y — is the transform. `present.rs` uses it to place the
texture; `input.rs` inverts it to place a pointer. Neither computes its own.

**The inverse, and the rounding rule, which is a real question rather than a detail.** A pointer at a
window position maps to a page position by subtracting the content area's origin, subtracting the fit
origin, and dividing by the scale. That yields a fractional coordinate. Take the **floor** to integer
device pixels, so that a pointer anywhere within the screen pixel that shows page pixel *n* maps to
*n* — which is what a human means by "I clicked on that pixel" — rather than rounding to nearest,
which makes the right half of a pixel belong to its neighbour. State the rule in a comment; it is the
kind of choice that is arbitrary until somebody tests a one-pixel target and then is not.

A position outside the fitted surface — in the letterbox margin, or over the client's own interface —
**sends nothing.** Not a clamped edge position: clamping turns "the human aimed at the margin" into
"the human aimed at the edge of the page", which is a click they did not make. The server clamps too,
against the target tab's viewport, and the two are complementary rather than redundant.

**Half-resolution frames.** The header carries a scale denominator, which 05-10's ladder will set
above one. The client's fit transform composes with it: a half-resolution keyframe covers the full
surface at half the pixel dimensions, so the texture is uploaded at that size and the fit accounts for
the denominator. Get this right now even though nothing sends a denominator above one yet — a client
that ignored the field would silently show a quarter-sized page the first time the ladder stepped down.

**Ordering.** The frame sequence is strictly increasing per attachment. Apply a frame only when its
sequence exceeds the last applied for that attachment, and discard otherwise. A delta whose sequence
is greater but which arrives after a keyframe with a *higher* sequence is discarded by the same rule,
which is the whole of the ordering logic.

**Input, and the three refusals.** The client sends nothing when it is not connected, nothing for a
tab it is not attached to, and nothing for a key it cannot name. The last one matters: the wire
carries a character or a named key, and the server's mapping returns nothing for an unmapped name.
A client that sent an unmapped key as some fallback character would type something the human did not.
Share the name list with the server's table by keeping the client's key naming to the same strings the
server's shared table recognises, and unit-test that every name the client can emit is one the server
maps — a test that walks the list rather than a comment asserting it.

**The sequence.** Strictly increasing for the life of the connection, starting above zero, incremented
per sent message and never reused after a reconnect within the same process. The server drops
non-increasing values, and the frame header echoes the last applied one, which is what 05-10 reads.

**How this is proven.** `tests/e2e/takeover_test.py` drives the **local** shell with a real pointer
through the window system and asserts the result over the control socket. This plan does the same
across a process boundary: start a shell, start a real client against it, drive the **client's**
window with a real pointer and real keystrokes, and assert on the **server's** tab over the control
socket. That is the honest end-to-end shape and it exercises the client's own transform, which a
synthetic wire message would bypass entirely.

The client's controls are geometry-recorded (05-07), so the suite can locate the page area by name
rather than by a hardcoded coordinate — the same reason the server's geometry hook exists.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a human's pointer → a page coordinate on another machine | Two transforms sit between them; if they disagree the human clicks something they did not aim at, and nothing errors |
| the client's own interface → the input channel | A click on the client's own controls that leaked onto the wire would be input the human did not aim at any page |
| a decoded frame → the client's picture | A hostile or corrupt payload arrives as bytes from a network peer and becomes pixels |
| one attachment's pixels → the next attachment's surface | Two agent tabs may belong to different agents; a surface not cleared on detach shows one to a viewer of the other |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-04-F | Tampering | the picture's transform and the pointer's transform disagreeing, so every click lands somewhere the human did not aim | high | mitigate | One transform, computed in one function, inverted in the other module — asserted by a source criterion that the inverse module contains no second computation of it. Proven end to end by driving the **real** client with a **real** pointer at a deliberately mismatched window size and asserting the specific element hit in both directions, which is the client-side counterpart of the server-side assertion 05-06 added. A synthetic wire message would bypass exactly this |
| T-05-04-G | Tampering | a click on the client's own interface, or in the letterboxed margin, reaching a page | high | mitigate | The inverse transform returns nothing for any position outside the fitted surface, and the client's own interface offset is applied at exactly one place — inside that transform — so applying it twice or forgetting it is not expressible elsewhere. Unit-tested one pixel outside each of the four edges, and asserted end to end with a real pointer in a margin that a mismatched window size guarantees exists. **Not clamped:** clamping a margin click to the page edge would be a click the human did not make |
| T-05-11-D | Denial of Service | a corrupt or hostile frame payload wedging the client or corrupting the picture | medium | mitigate | A payload that does not decode costs one frame: it is discarded with a log line, the existing picture is untouched, and the connection is undisturbed. The header is decoded through the wire type, which refuses a short slice, an unrecognised version, a zero-sized tile and a tile exceeding its declared frame |
| T-05-15-B | Tampering | a stale or replayed frame painting old pixels over new ones | medium | mitigate | A frame is applied only when its sequence exceeds the last applied for that attachment, including the case of a delta arriving after a higher-numbered keyframe. The rule is one comparison and it is unit-tested including the before-any-keyframe case |
| T-05-10-B | Information Disclosure | one agent's page pixels briefly visible to a viewer who attached to a different agent's tab | medium | mitigate | The surface is cleared on detach, so a later attachment cannot show the previous tab's pixels between attaching and its first keyframe. This is a privacy detail as much as a correctness one, because the two tabs may belong to different agents |
| T-05-12-C | Denial of Service | an attachment reflowing an agent's page because a human started watching | medium | mitigate | No wire message asks for a resize and the client requests none: the viewer adapts to the page. Asserted end to end by reading the server's tab viewport before and after an attachment from a differently-sized client. The alternative would make an agent's layout a function of who is looking and would reflow again when the local human displayed the tab |
| T-05-07-D | Information Disclosure | the credential reaching a log or an argument from the client's input path | high | mitigate | Unchanged from 05-07 and re-asserted: the credential is read from an environment variable or an owner-only file, never from an argument, and never interpolated into a log. This plan adds no new credential path |
| T-05-SC | Tampering | package installs | n/a | accept | No dependency change; 05-07 landed the client's dependencies with the hand-edit procedure and the gated lock diff, and its audit is recorded there |

which in a page with a destructive control next to a benign one is an elevation of privilege wearing a
rendering bug's clothes.
