<objective>
Give Talaria local browsing history: every completed navigation on a human ("Me") tab is captured
as a (url, title, timestamp) row, survives a restart, and is browsable from a new History panel —
BROWSE-01.

Purpose: this is the first of Phase 3's four table-stakes features and, per the roadmap split,
establishes the shared substrate the other three extend rather than duplicate: the `ChromePanel`
enum (generalizing today's single `credentials_open: bool` into a real panel-selection type) and
the deferred-pending-queue idiom for a Servo delegate callback that needs to reach a plain-file
store. `app.rs` and `gui.rs` are touched by every one of Phase 3's four plans (each adds its own
`Shared` field, its own capture/apply-action wiring, and its own toolbar button + panel), so a
same-wave, file-disjoint split across 03-01..03-04 is not achievable regardless of whether the
substrate is factored into a separate zero-feature plan first — every later plan still has to touch
both files for its own addition. The leaner design, adopted here, is: this plan (03-01) builds the
`ChromePanel` mechanism *as part of* shipping the first real panel rather than as a preparatory
no-op plan, and 03-02/03-03/03-04 each extend the enum by one variant while shipping their own
feature. Waves are therefore fully sequential (03-01 → 03-02 → 03-03 → 03-04, each `depends_on` the
previous), matching the roadmap's proposed order exactly.

Context note: STATE.md's Blockers/Concerns section and `.planning/phases/02-harden-the-agent-surface/deferred-items.md`
both still list `Vault::load()`'s D-Bus-autolaunch startup hang as "an early Phase 3 plan, or a v1
blocker" — that record is stale. Commit `bf6a3b7` ("fix: stop the vault from hanging startup when
there is no session D-Bus", 2026-08-19, before this planning pass) already closed it with a
`session_bus_reachable()` pre-check plus a bounded `with_timeout()` worker-thread wrapper around the
keychain lookup, and `e2e.yml` dropped its `dbus-run-session` workaround wrapper the same commit.
No plan in this phase re-opens or re-verifies this; it is out of scope here because it is already
done, not because it was skipped.

Output: `history.rs` (a new store module), a `pending_history_writes` capture queue wired into
`notify_load_status_changed`, a generalized `ChromePanel` enum and History panel in the chrome, and
`tests/e2e/history_test.py` proving restart survival, the Me-only filter, and Servo 0.4.0's actual
`pushState`/hash-navigation callback behavior (RESEARCH.md's Open Question 1).
</objective>

  <behavior>
    - `History::load()` on a missing or unreadable `history.jsonl` returns an empty store (no panic,
      no error surfaced) — same as `Vault::load()`'s degrade path.
    - `History::load()` on a file with some unparseable lines (corrupted trailing write) skips those
      lines, keeps the parseable ones, and logs one `log::warn!` naming the skipped-line count — not
      one warning per bad line.
    - `History::append(url, title, visited_at_ms)` adds exactly one row to both the in-memory list
      and the on-disk file; two calls with the same `url` produce two separate rows, not one updated
      row.
    - `History::load()` when the on-disk entry count exceeds the configured cap (default 5,000,
      `TALARIA_HISTORY_MAX_ENTRIES` override, an unparseable override value falls back to the
      default rather than 0 or unbounded) keeps only the most recent `cap` entries in memory *and*
      physically rewrites the file down to that same set via a temp-file-plus-`fs::rename` (atomic on
      the same filesystem) — this is the module's only whole-file rewrite; it runs at most once per
      startup, never per navigation.
    - `History::clear()` empties the in-memory list and removes (or truncates) the on-disk file, and
      is idempotent — calling it twice in a row is not an error.
  </behavior>

    Create `crates/talaria-shell/src/history.rs`. Open with a `//!` module header (mirroring
    `vault.rs`'s) stating: this store is plaintext, not a secret, Me-tab-only, and an append-only
    log rather than the whole-array pattern the other three Phase 3 stores use.

    Define `HistoryEntry { pub url: String, pub title: String, pub visited_at_ms: u64 }`
    (`#[derive(Debug, Clone, Serialize, Deserialize)]`) and `History { path: PathBuf, entries:
    Vec<HistoryEntry> }`. Add a private `config_dir()` copying `vault.rs`'s four-line helper
    verbatim (`dirs::config_dir().unwrap_or_else(|| PathBuf::from(".")).join("talaria")`) — do not
    import vault's private fn or touch `vault.rs`.

    `History::load()`: read `config_dir().join("history.jsonl")`; on read failure, return an empty
    store. On success, split into lines, `serde_json::from_str::<HistoryEntry>` each non-empty line,
    collect the `Ok`s, count the `Err`s and `log::warn!` once with the count if any occurred. Read
    the cap via a private `history_max_entries()` fn shaped exactly like `max_download_bytes()`
    (`std::env::var("TALARIA_HISTORY_MAX_ENTRIES").ok().and_then(|v| v.parse().ok()).unwrap_or(5_000)`).
    If the parsed entry count exceeds the cap, keep only the tail (`entries.split_off(entries.len() -
    cap)` or equivalent — the *most recent* `cap` entries, since the file is written in append
    order), and rewrite the file to hold exactly that set: serialize each surviving entry back to one
    JSON line, write the joined lines to `<path>.tmp` in the same directory, then `fs::rename` over
    the target. Log a `log::warn!` naming the rewrite's before/after counts is optional but the
    rewrite itself is not.

    `History::append(&mut self, url: String, title: String, visited_at_ms: u64)`: push a new
    `HistoryEntry` to `self.entries`, then open `self.path` with
    `fs::OpenOptions::new().append(true).create(true).open(...)`, write one serialized JSON line plus
    `"\n"` via a single `write_all`, and `flush()`. On any I/O error, `log::warn!` and return — the
    in-memory push already happened, so the panel still reflects it for this session even if the
    write failed; do not roll back the in-memory push on a write failure (matches the codebase's
    house rule: a degraded write is logged, never fatal, never rolled back into a worse UX).
    Deliberately no temp+rename here: an interrupted single-line append can corrupt at most the
    trailing line, which `load()`'s corrupt-line skip already tolerates, and a temp+rename per
    navigation would reintroduce the O(n) rewrite cost Pitfall 1 exists to avoid.

    `History::clear(&mut self)`: clear `self.entries`, then `let _ = fs::remove_file(&self.path);`
    (ignore `NotFound` — clearing an already-empty store is not an error).

    `History::entries(&self) -> &[HistoryEntry]`: borrowed accessor, matching `Vault::entries()`'s
    shape (`crates/talaria-shell/src/vault.rs`, the equivalent accessor near the end of the impl
    block) so the panel can iterate without cloning.

    Add `#[cfg(test)] mod tests` covering: `load()` on a missing file returns empty; `append` then
    `load()` (fresh instance, same path) round-trips a written entry; two `append`s with the same URL
    produce two entries, not one; a file with one corrupt line among two good ones loads the two good
    ones and does not panic; a store over the cap at `load()` truncates to the cap's most recent
    entries and the on-disk file shrinks to match; `history_max_entries()` falls back to 5,000 on an
    unset or unparseable env var (use a per-test-unique tmp path so tests can run in parallel without

|----------|--------------|
| Servo delegate callback -> event loop | `notify_load_status_changed` runs inside Servo's own borrow; only a queue push is safe there |

| agent-owned tab -> human's history | An agent drives real navigation; that activity must not silently become part of the human's own record |

| T-03-01-02 | Tampering | a crash or `kill -9` mid-`append` leaves a truncated trailing line | medium | mitigate | `load()` skips unparseable lines rather than treating the whole file as corrupt; only the last line is ever at risk, per Pitfall 2's own reasoning |
