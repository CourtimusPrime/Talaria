<objective>
Give Talaria a downloads list: every completed download — agent-triggered via the MCP `download`
tool today, and any future control-socket-driven download regardless of client — appends an entry
recording its actual written path, and a Downloads panel lists, opens, and removes entries —
BROWSE-04.

Purpose: the fourth and final plan in Phase 3's sequential chain, and per the roadmap split's own
flag, its highest-risk task. `download()` (`crates/talaria-shell/src/app.rs`) runs today on a bare
`std::thread::spawn` with no path back to the main thread at all — it replies to the caller over a
`oneshot` channel and does nothing else. `Shared` holds no `EventLoopProxy<AppEvent>` of its own
(only `Waker`, Servo's own wake mechanism, and the control thread's independently-created one exist
today). Recording a completed download requires adding a **third** proxy holder — genuinely new
architecture, not a reuse of an existing hook, exactly as `03-RESEARCH.md` and `03-PATTERNS.md` both
flag. This plan also carries the phase's one explicitly-named high-severity security requirement:
the downloads-list "Open" action shells out (`xdg-open`), and Phase 2 spent its entire scope
narrowing the agent-reachable surface — an opener reachable from MCP would undo that. "Open" must
stay reachable only from the human-only downloads panel's own `UiAction`, launching only a path the
shell itself recorded.

Design simplification versus RESEARCH.md's drafted example: RESEARCH.md's `Pattern 3` code sample
carries a `session_owner: TabOwner` field on `AppEvent::DownloadCompleted`, speculating that the
downloads store might need to know who triggered a download. `03-PATTERNS.md`'s own downloads.rs
section and `03-RESEARCH.md`'s own "Pitfall 5" are explicit that the store records **every**
completed download regardless of owner (the opposite of history's Me-only filter, because a
download is about what landed on the human's filesystem, which matters regardless of who asked for
it). Given that, `session_owner` would be a field the store never reads — this plan drops it from
`AppEvent::DownloadCompleted` rather than carrying dead data, and notes the deviation here so a
later reader does not wonder why the shipped shape differs from the research draft.

Output: `downloads.rs`, `Shared::event_proxy`, `AppEvent::DownloadCompleted`, the Downloads panel,
and `tests/e2e/downloads_list_test.py` proving a real download (driven over the raw socket, the same
mechanism the MCP `download` tool itself uses) produces a correct list entry.
</objective>

`Command::Download`'s handler inside `execute_agent_command`
(`crates/talaria-shell/src/app.rs:1459-1471`), current shape:
```rust
Command::Download { url, filename } => {
    if filename.contains('/') || filename.contains("..") {
        let _ = reply.send(Outcome::Error { message: "bad filename".into() });
        return;
    }
    std::thread::spawn(move || {
        let outcome = download(&url, &filename, &reply);
        let _ = reply.send(outcome);
    });
},
```
This arm already runs inside a function taking `state: &Rc<Shared>` — `state.event_proxy.clone()`
is reachable right here, no new parameter threading needed. Clone the proxy *before* the
`std::thread::spawn` call (the closure cannot borrow `state`, `Rc` is not `Send`) and move the clone
into the closure alongside the existing `url`/`filename`/`reply` captures.

`download()`'s success return shape (`crates/talaria-shell/src/app.rs:1741-1817`, the tail):
```rust
Outcome::Ok {
    result: ResultPayload::Download {
        path: path.display().to_string(),
        bytes: written,
    },
}
```
`filename` and `url` are not part of `Outcome`/`ResultPayload` — they are still owned locally inside
the spawned closure (moved in from the outer scope, never otherwise used after the `download()`
call), so building the `AppEvent::DownloadCompleted` payload needs no new plumbing through
`download()`'s own signature; only the closure wrapping it changes.

`create_unique` (`crates/talaria-shell/src/app.rs:1695-1717`) is what may rename `filename` on disk
(`report (1).pdf`) — the **returned path**, not the original `filename` string, is what
`downloads.rs` must store and what `UiAction::OpenDownload` must carry. This is the plan's central
security-relevant data-flow constraint; trace it end to end while implementing rather than assuming
it holds.

The credentials panel's one-shot notice + Dismiss pattern (`crates/talaria-shell/src/gui.rs:509-540`,
read directly — `03-PATTERNS.md` names this range rather than excerpting it) is the template for the
downloads-open-error inline notice + `UiAction::DismissDownloadError`.

`tools.rs`'s `download` tool (`crates/talaria-mcp/src/tools.rs`, the `DownloadTool` struct and its
