# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is not a web project.** Talaria's chrome is Rust + egui 0.34.3 drawn immediate-mode into
> Servo's GL context (`crates/talaria-shell/src/gui.rs`). There is no DOM, no CSS, no component
> registry, and no responsive breakpoints. Every field below is translated into egui's actual
> vocabulary — `Style`/`Visuals`, `TextStyle`, `Color32`, `Margin`/spacing floats, `Frame`,
> `CentralPanel`/`Panel`, `UiAction`, and `egui-phosphor` glyphs — instead of a web analog. Where a
> template row has no meaningful native-GUI equivalent, that is stated explicitly rather than
> invented.
>
> No `CONTEXT.md` exists for this phase (`/gsd-discuss-phase` was not run) and this run is
> `--auto`. Every decision below is grounded in the conventions already shipped in `gui.rs`/`app.rs`
> (the credentials panel is the load-bearing precedent throughout) and in `03-RESEARCH.md`'s
> recommendations. Genuinely discretionary calls are logged in **Open Questions / Assumptions**
> at the end rather than left silently decided.

## Spacing Scale

egui has no rem/px token pipeline — every value below is an `f32` fed directly to `ui.add_space(_)`
or a spacing float on `Style`/`Frame`. **No `Style::spacing` override is introduced this phase** —
`item_spacing` (8.0, 3.0), `button_padding` (4.0, 1.0), and `window_margin`/panel frame margin all
stay at egui 0.34.3's untouched defaults, exactly as they are today (`gui.rs` sets no `Style`
override anywhere). The scale below governs only the explicit `ui.add_space(_)` calls this phase's
four new panels add, extending the one data point the codebase already has
(`ui.add_space(8.0)` in the credentials panel, `gui.rs:548`).

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4.0 | Tight inline grouping beyond default `item_spacing` (e.g. size + timestamp on one row) |
| sm | 8.0 | Default gap between a panel's intro paragraph and its first control — matches the existing credentials-panel precedent exactly |
| md | 16.0 | Section break within a panel: between the heading block and the list/form body, between the list and a footer action row (e.g. "Clear history") |
| lg | 24.0 | Reserved for a panel-level top inset if a later plan needs one; not used by any panel this phase specifies |
| xl | 32.0 | Unused this phase — no layout in Phase 3 needs a gap this large |
| 2xl | 48.0 | Unused this phase |
| 3xl | 64.0 | Unused this phase |

Exceptions: none. All four new panels (`History`, `Bookmarks`, `Downloads`, `Settings`) reuse
`egui::CentralPanel::default()` with no custom `Frame`/margin, identical to the credentials panel —
introducing a bespoke margin per surface would be the one inconsistency a later reader would have
to explain.

## Typography

egui has five `TextStyle`s, not an open size scale, and **no font-weight axis** — only one
proportional font family is registered (no bold/regular pair), so `RichText::strong()` and
`ui.heading()` change *color/size*, never weight. No `Style::text_styles` override exists in this
codebase today (confirmed by grep — zero matches for `text_styles`/`FontId::new` in `gui.rs`), and
this phase does not add one; every size below is egui 0.34.3's own compiled default (`egui::Style`,
`style.rs:1402-1407`), reused rather than restated.

| Role | egui `TextStyle` | Size | "Weight" | Line Height |
|------|-------------------|------|----------|-------------|
| Body | `TextStyle::Body` | 13.0pt proportional | n/a — egui has no weight axis; emphasis is `RichText::strong()` (color only) | n/a — egui derives row height from font metrics, not a settable token |
| Label (secondary/meta text — timestamps, byte sizes, hint text) | `TextStyle::Small` | 9.0pt proportional | n/a | n/a |
| Heading (panel titles: "History", "Bookmarks", "Downloads", "Settings") | `TextStyle::Heading`, via `ui.heading(...)` | 18.0pt proportional | n/a | n/a |
| Display | not applicable | — | — | — |

**Display row justification:** egui's largest built-in style is `Heading` (18pt). None of this
phase's four panels need anything larger — a bespoke `FontId` just for a bigger display size would
be a one-off inconsistent with every other panel in the shell. Do not add one.

**Rule for new code:** reference `ui.heading(...)`, default label text, and
`egui::RichText::new(text).small()` — never construct a raw `egui::FontId` with a hand-picked size.
This is how the credentials panel already stays consistent with the rest of the chrome, and it is
the only way a later theme-wide size change (should one ever happen) doesn't require hunting down
hardcoded numbers.

## Color

**No `ctx.set_visuals(...)` call exists anywhere in the codebase, and this phase adds none.** Every
color below is the app's already-in-effect default dark `egui::Visuals` (`dark_mode: true`,
`style.rs:1482-1530`), referenced through `ui.visuals().<field>` — never a hardcoded `Color32`
literal. Hex values are given here only so a reviewer can eyeball them; the executor should write
`ui.visuals().panel_fill` etc., not `Color32::from_gray(27)`.

| Role | `egui::Visuals` field | Value | Usage |
|------|------------------------|-------|-------|
| Dominant (60%) | `panel_fill` / `window_fill` | `Color32::from_gray(27)` = `#1B1B1B` | Every panel/toolbar background — the four new `CentralPanel`s inherit this automatically by using `egui::CentralPanel::default()`, same as the credentials panel |
| Secondary (30%) | `faint_bg_color` | additive luminance 5 (barely-visible tint over the base) | Alternating row background in the three new list panels (History/Bookmarks/Downloads), via `egui::Grid::new(_).striped(true)` or an equivalent manual `Frame::fill` on odd rows — a new visual pattern for this codebase (no existing list uses striping), but it is the standard egui mechanism for exactly this, not an invented one |
| Accent (10%) | `selection.bg_fill` | `Color32::from_rgb(0, 92, 128)` = `#005C80` | **Reserved for, and only for:** (1) the `.selected()` highlight on the four new toolbar toggle buttons (History/Bookmarks/Downloads/Settings), extending the exact mechanism the Credentials `KEY` button already uses; (2) the bookmark star button's `.selected(is_bookmarked)` state; (3) the active-panel's own selectable rows, if a plan adds row-level selection (none is specified this phase). Not used for body text, not used as list-row background, not used as a decorative fill anywhere. |
| Destructive | `error_fg_color` | `Color32::from_rgb(255, 0, 0)` = `#FF0000` | **Text only, never button icon tint.** Used exactly once in this phase's copy: the inline "couldn't open download" error line in the Downloads panel (see Copywriting Contract). The `TRASH` remove-buttons in History/Bookmarks/Downloads stay plain default-colored, deliberately matching the existing `DeleteCredential` `TRASH` button in the credentials panel, which carries no red tint today — introducing one only for the new panels would be a new, unrequested visual language split. |

Accent reserved for: the four toolbar panel-toggle buttons' selected state, the bookmark star's
selected state, and (if a later plan adds it) selected-row highlighting inside a panel. Nothing
else.

## Copywriting Contract

Voice: short, sentence-case, no exclamation points, no filler — matches every existing chrome
string (`"Nothing saved yet."`, `"No agents connected — point an MCP client at talaria-mcp"`,
`"💥 This tab crashed"`). Empty states in this phase deliberately extend the exact
`"Nothing saved yet."` construction the credentials panel already established, rather than
inventing a new empty-state voice.

| Element | Copy |
|---------|------|
| Primary CTA — History toolbar button | Icon `CLOCK_COUNTER_CLOCKWISE`, hover text: `Open history (Ctrl+H)` |
| Primary CTA — History row | Click navigates the displayed tab there and closes the panel (no button label; the row itself is the control) |
| Primary CTA — Bookmark toggle | Icon `STAR`, hover text: `Bookmark this page (Ctrl+D)` when not bookmarked, `Remove bookmark (Ctrl+D)` when bookmarked |
| Primary CTA — Bookmarks toolbar button | Icon `BOOKMARKS`, hover text: `Open bookmarks (Ctrl+B)` |
| Primary CTA — Downloads toolbar button | Icon `DOWNLOAD`, hover text: `Open downloads (Ctrl+J)` |
| Primary CTA — Downloads row action | Button label: `Open` |
| Primary CTA — Settings toolbar button | Icon `GEAR`, hover text: `Settings` (no keyboard shortcut — see Open Questions) |
| Primary CTA — Settings save | Button label: `Save` (verbatim match to the credentials panel's own Save button, for voice consistency) |
| Empty state — History | `Nothing visited yet.` |
| Empty state — Bookmarks | `Nothing bookmarked yet.` |
| Empty state — Downloads | `Nothing downloaded yet.` |
| Empty state — Settings | Not applicable — the form is always pre-filled with the current (default-or-saved) engine; there is no zero-state distinct from "populated with defaults" (mirrors the credentials add-form, which has no empty treatment either) |
| Error state — store load failure (History/Bookmarks/Downloads/Settings) | **No user-facing copy.** A corrupted or unreadable `history.jsonl`/`bookmarks.json`/`downloads.json`/`config.json` degrades silently to an empty list / default settings and `log::warn!`s, per `CLAUDE.md`'s "degrade, never abort, on user-data problems" rule and `vault.rs`'s exact precedent. Do not add a toast, banner, or panel message for this case — that would be new behavior the rest of the app doesn't have. |
| Error state — "open download" fails | Inline line above the Downloads list, in `ui.visuals().error_fg_color`: `Couldn't open {filename} — {os error}`, with a `Dismiss` button beside it using the identical pattern already shipped for the vault's one-shot notices (`gui.rs:509-540`) |
| Error state — Settings, invalid search template | No error text is shown after the fact — see "Destructive confirmation" row below for the prevention-at-entry design (Save is disabled, not apologized-for after a bad save) |
| Destructive confirmation — Remove bookmark | Immediate, no confirmation — `TRASH` icon button, single click, matches `DeleteCredential`'s existing zero-confirmation precedent exactly. Hover text: `Remove bookmark` |
| Destructive confirmation — Remove download from list | Immediate, no confirmation, same as above. Hover text: `Remove from list` (does **not** delete the file on disk — copy must not imply it does) |
| Destructive confirmation — Clear history (Claude's discretion; see Open Questions) | Two-stage in-place button, no modal (no modal/`egui::Window` pattern exists anywhere in this codebase and this phase should not introduce the first one). Default label `Clear history`. First click flips a `Gui`-local `confirm_clear_history: bool` (same shape as the existing `revealed_entry` view-state field) and re-renders the same button that frame as `Confirm clear?` in `ui.visuals().error_fg_color`. Second click emits `UiAction::ClearHistory`. `confirm_clear_history` resets to `false` whenever the History panel closes, mirroring exactly how `set_credentials_panel` already resets `revealed_entry = None` on close. |
| Settings validation copy | Persistent (not error-triggered) `Small`-style hint beneath the URL template field: `Must contain {query} exactly once` |

## Panel Taxonomy (native-GUI equivalent of a component inventory)

Adopts `03-RESEARCH.md`'s `ChromePanel` recommendation as-is — it is the direct generalization of
the credentials panel's already-proven `credentials_open: bool` mechanism, and inventing a
different mechanism for four more panels than the one already shipped and working would be the
inconsistency, not the reuse.

```rust
pub enum ChromePanel {
    None,
    Credentials,
    History,
    Bookmarks,
    Downloads,
    Settings,
}
```

- **Storage:** lives on `Gui` (view state), never on `Shared` — same rule the credentials panel
  already follows, and the same reason: `Gui::` methods return `Vec<UiAction>`, they never mutate
  shared state directly.
- **Opening a panel:** each toolbar button computes `if gui.panel() == target { ChromePanel::None } else { target }` and pushes `UiAction::SetPanel(that value)` — the exact generalization of today's `UiAction::SetCredentialsPanel(!credentials_open)`. Clicking a *different* panel's button while one is already open switches directly to the new panel in one click; it does not require closing first.
- **Closing a panel:** clicking its own toolbar button again (toggle), or pressing its keyboard shortcut again (Ctrl+H toggles History, Ctrl+B toggles Bookmarks, Ctrl+J toggles Downloads — Settings has no shortcut this phase, see Open Questions). There is no Escape-to-close binding — the credentials panel doesn't have one today either, and adding it only for the four new panels would be a new, inconsistent affordance.
- **Mouse/render takeover:** every non-`None` variant goes through the exact `chrome_replaces_page` gate the credentials panel already established (`app.rs:818-821`) — generalized from `gui.credentials_open()` to `gui.panel_open()` (`panel != ChromePanel::None`). The displayed tab is neither painted nor blitted while any panel is open, and mouse events route to the panel instead of the hidden webview.
- **Switching tabs while a panel is open:** `UiAction::SelectTab` does not close the open panel today (verified directly in `apply_ui_actions`, `app.rs:1100-1102` — it only calls `tabs.set_active(id)`), and this phase does not change that. A panel stays open across a tab switch, now covering whichever tab becomes displayed. This is a **carried-over existing behavior**, not a new decision, and not something this phase's plans should "fix" as a bug — flagged explicitly here so it isn't rediscovered and re-litigated mid-execution.
- **Human-only surface, same as Credentials:** none of the four new panels are reachable from any `Command`/MCP tool. Toolbar buttons and keyboard shortcuts are the only entry points, exactly like the `K`redentials panel and the autofill suggestion menu.

### Toolbar layout (left to right, extending the existing row)

```
[Me] [Agents] | ← Back → Forward ↻ Reload  ＋ New Tab |  🕐 History  ⭐ Bookmark  🔖 Bookmarks  ⬇ Downloads  ⚙ Settings  |  🔑 Credentials   [autofill suggestion]   [location bar]
```

The new group (History / Bookmark-star / Bookmarks / Downloads / Settings) is inserted **after**
the existing New Tab button and **before** the existing Credentials button, bracketed by one new
`ui.separator()` on its left — the existing toolbar has exactly one separator today (after the
Me/Agents toggle); this phase adds the second one, not a separator around every icon.

| Button | Icon | Shortcut | Toggles |
|--------|------|----------|---------|
| History | `CLOCK_COUNTER_CLOCKWISE` | Ctrl+H | `ChromePanel::History` |
| Bookmark (current page) | `STAR` | Ctrl+D | not a panel — direct `UiAction::ToggleBookmark(url, title)`; `.selected()` reflects `is_bookmarked(current_url)` |
| Bookmarks (list) | `BOOKMARKS` | Ctrl+B | `ChromePanel::Bookmarks` |
| Downloads | `DOWNLOAD` | Ctrl+J | `ChromePanel::Downloads` |
| Settings | `GEAR` | — (toolbar-only this phase) | `ChromePanel::Settings` |

`h`, `d`, `b`, `j` are all unused by `handle_browser_shortcut`'s existing `Ctrl+<char>` match arm
today (only `l`, `k`, `t`, `w`, `r` are claimed) — no collision. All four new bindings fit the
existing arm's shape without needing to add shift-key detection to the character branch (that
branch does not currently distinguish shift for any letter; adding a Shift-modified letter shortcut
would require new code there, which this design deliberately avoids by not needing one).

Both the Bookmark star and the four panel-toggle buttons follow `has_tab` gating consistent with
Back/Forward/Reload: `ui.add_enabled(has_tab, ...)` for the star (there's no "current page" to
bookmark with no displayed tab); History/Bookmarks/Downloads/Settings stay enabled with no tab open
(they show global lists/settings, not something scoped to the current page).

## Open Questions / Assumptions

Logged here per this run's `--auto` mode instead of blocking on a `/gsd-discuss-phase` pass. Each
is a genuinely discretionary call this research made on the project's behalf, flagged so the
planner or a human can override any one of them cheaply.

1. **"Clear history" bulk action — included, not required by BROWSE-01.** BROWSE-01 only requires
   that history exist, survive a restart, and show URL/title/timestamp; it says nothing about
   clearing it. This spec includes a `Clear history` control anyway (see Copywriting Contract's
   two-stage confirm design) because a browsing-history feature with no way to clear it is a
   plausible complaint on a "real daily-driver browser," and the two-stage in-place button is
   cheap to build (one `Gui`-local bool, one new `UiAction::ClearHistory` variant, no modal). If
   the planner wants to descope this for a tighter Phase 3, it is the one clean line to cut —
   nothing else in this spec depends on it.

2. **Per-row delete for History/Downloads — deliberately excluded.** Bookmarks gets per-row
   `TRASH` removal because its list is small and user-curated; History and Downloads don't, because
   at real-world scale (thousands of history rows per `03-RESEARCH.md`'s own cap discussion) a
   delete icon on every row is UI noise for low value, and neither BROWSE-01 nor BROWSE-04 asks for
   it. If a future pass wants per-row history/download deletion, it's additive to this contract,
   not a change to it.

3. **Settings — file-plus-panel, not file-only.** `03-RESEARCH.md`'s Open Question 3 flagged this
   as the one area genuinely open to discretion. This spec resolves it toward shipping both
   (`config.json` as source of truth, plus the minimal two-field settings panel specified above)
   because the marginal cost is one more `ChromePanel` variant reusing a mechanism that already
   exists for four other surfaces, and "a real daily-driver browser" reads oddly if changing the
   search engine requires hand-editing a JSON file. A file-only v1 remains a legitimate descope if
   time is tight.

4. **No keyboard shortcut for Settings.** Every other new panel maps to a real-browser convention
   (Ctrl+H history, Ctrl+D bookmark-this-page, Ctrl+J downloads — matching Chrome/Firefox exactly;
   Ctrl+B for the bookmarks *list* is this project's own choice, since Chrome's own
   Ctrl+Shift+O doesn't fit this codebase's shortcut-matching shape without adding shift-detection
   to the character-match arm). No comparably strong cross-browser convention exists for a
   "settings" keystroke, so this spec leaves it toolbar-button-only rather than picking an
   arbitrary binding.

5. **SPA / `pushState` navigations may under-count history** — carried over verbatim from
   `03-RESEARCH.md`'s Open Question 1 / Assumption A2. This is a capture-point/backend question,
   not a UI-contract question, but it's worth restating here: if Servo 0.4.0 doesn't re-fire
   `Complete` on an in-page navigation, the History panel will simply show fewer rows than a user
   might expect for a heavy SPA — no UI change is needed to accommodate either outcome, since the
   panel just renders whatever the store contains.

6. **Downloads list has no retention cap**, unlike History's proposed 5,000-entry cap. Nothing in
   BROWSE-04 asks for one, and `03-RESEARCH.md`'s recommended storage shape for downloads is a
   whole-array rewrite (low-churn, unlike history's append log) — a real user is very unlikely to
   accumulate enough completed downloads for this to matter within v1's lifetime. Flagged rather
   than silently assumed.
