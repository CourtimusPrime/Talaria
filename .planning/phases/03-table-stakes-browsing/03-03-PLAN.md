<objective>
Replace the address bar's hardcoded DuckDuckGo fallback with a configurable search engine —
BROWSE-03 — backed by `config.json` (the project's first config-file-format file) plus a minimal
Settings panel, per `03-UI-SPEC.md`'s resolved "file-plus-panel" decision (RESEARCH.md's Open
Question 3).

Purpose: third plan in Phase 3's sequential chain. Unlike 03-01/03-02, this plan's core change is
not a new capture point or a new list — it is a signature change to an existing, load-bearing
function (`resolve_location`) that every "type something and hit Enter" path in the human's own
toolbar already calls, plus one call site in `main.rs` outside the whole `Shared`/event-loop
machinery entirely. Getting every call site right, and getting the human/agent trust-root boundary
(`resolve_location` vs `parse_agent_url`) *un*-touched, matters more here than any new UI surface.

Assumption-delta note (advisory, non-blocking, per the orchestrator's checkpoint): BROWSE-03 is a
singular-to-plural transition — one hardcoded engine becomes a user-chosen one. The durable identity
model this plan adopts: a `SearchEngine` is a `{ name, url_template }` pair with no id/uuid of its
own, because exactly one is ever configured at a time (this is "the current engine," not an entry
in a list of engines a user picks between) — nothing else in the shell assumes there is exactly one
engine beyond `resolve_location`'s own single `&SearchEngine` parameter, so this plan introduces no
multi-engine concept, no engine list, and no "default vs active" distinction to manage. If a future
phase wants a picker among several presets, that is additive to this shape, not a change to it.

Open Question resolved (edge-probe row `BROWSE-03 / unclassified`): the deterministic edge probe
returned this requirement as `unclassified` rather than mapping to adjacency/empty/ordering, because
BROWSE-03 configures a single scalar value, not a collection — none of those three categories has a
literal meaning here. The concretely relevant question this plan resolves instead is the one
`03-UI-SPEC.md`'s own Settings-form rows already answer: an *invalid* template is prevented at entry
(Save disabled) rather than accepted and surfaced as an error after the fact, and a template that
somehow reaches disk invalid anyway (hand-edited `config.json`) degrades to the default at load time.
Both are must-haves above; this paragraph exists so the unclassified probe row is not silently
dropped, per the flagged-assumption discipline.

Output: `settings.rs`, `resolve_location(input, engine)`, `ChromePanel::Settings`, and unit tests
for `resolve_location` — a function this codebase has never had tests for before this plan.
</objective>

```rust
pub fn resolve_location(input: &str) -> Url {
    let input = input.trim();
    if let Ok(url) = Url::parse(input) {
        if !url.scheme().is_empty() && url.host().is_some()
            || url.scheme() == "about"
            || url.scheme() == "file"
        { return url; }
    }
    if !input.contains(' ') && input.contains('.') {
        if let Ok(url) = Url::parse(&format!("https://{input}")) { return url; }
    }
    let query: String = url::form_urlencoded::byte_serialize(input.as_bytes()).collect();
    Url::parse(&format!("https://duckduckgo.com/?q={query}")).expect("static url")
}
```
