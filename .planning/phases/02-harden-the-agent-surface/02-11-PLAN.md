<objective>
Close TEST-03: build, clippy, unit tests, and the end-to-end suite run on every push, and they are
green.

Purpose: there is no CI and no workflow directory anywhere in the repository. Every check in the
project's development record was run by hand, and nothing prevents a regression from being committed
— which is how HEAD came to have no full end-to-end pass on record before plan 02-01 produced one. A
build-only pipeline would be theatre here: there are three unit tests in the whole workspace and the
Python suite carries essentially all behavioural coverage, so CI has to run it under Xvfb or it
verifies nothing that matters.

This plan is deliberately last in the phase, so the pipeline it adds locks in a state that already
passes rather than starting red and teaching everyone to ignore it.

Output: A push-and-pull-request pipeline running all four steps in order under Xvfb, a separate
scheduled job that resolves dependencies from scratch to surface the hand-pinned drift, and the pin
documented in the manifest.
</objective>

The harness contract the job must satisfy (`tests/e2e/harness.py:1-21`):

```python
"""Shared launcher for the e2e suites that start their own shell.

Isolation knobs (so a suite can run next to a long soak on the default
display without killing it):

- ``TALARIA_E2E_DISPLAY``  X display to create with Xvfb (default ``:99``).
- ``XDG_RUNTIME_DIR``      inherited by the shell — point it at a private
  directory to get a private control socket (``$XDG_RUNTIME_DIR/talaria.sock``).
"""
REPO = os.path.join(os.path.dirname(os.path.abspath(__file__)), "..", "..")
DISPLAY = os.environ.get("TALARIA_E2E_DISPLAY", ":99")
BINARY = os.path.join(REPO, "target", "release", "talaria")
```

External binaries the harness and the suites shell out to: `Xvfb`, `xdpyinfo`, `pkill`, `xdotool`,
`xwd`, and ImageMagick's `convert` (`.planning/codebase/TESTING.md` prerequisites). The harness also
reads `/proc` to find shells on its display, so it needs a Linux runner.

Exit-code contract (`tests/e2e/run_all.py:63-65`): the orchestrator prints the failing suite names and
exits with the count of failed suites, so a non-zero exit is the gate and exit 1 means exactly one
suite failed.

Documented verification commands (`.planning/codebase/CONVENTIONS.md` section "Linting"):
`cargo build --release` plus `python3 tests/e2e/run_all.py`. There is no `rustfmt.toml` and no
`clippy.toml`, so default clippy behaviour applies and the phase must end clippy-clean.

Both binaries must exist before the suite runs: `target/release/talaria` and
`target/release/talaria-mcp`. A workspace-wide release build produces both.

The dependency pin to surface (`.planning/codebase/CONCERNS.md` section "Dependencies at Risk"): a
fresh resolution pulls a final `primeorder` release that breaks the release-candidate elliptic-curve
crates with a trait-bound error. The workaround exists only inside the committed lockfile
(`Cargo.lock:5241`) and in a design-note file. Recovery is
`cargo update -p primeorder --precise 0.14.0-rc.14`.

Platform prerequisites for a Servo build: Rust 1.88 or newer plus python3, pkg-config, cmake, clang,
and the fontconfig and freetype development headers. The toolchain is unpinned — no
`rust-toolchain.toml` is committed.

Python usage is stdlib-only across the whole suite, so the job needs no package installation for it.

    Create `.github/workflows/ci.yml` with a single job on a Linux runner, triggered on push and on
    pull request, with no branch filter and no path filter. A path filter is what would let a push

    one — state that in a comment at the trigger block.

    Give the job a generous timeout in minutes: a Servo build from cold is long, and a job killed

    Use only first-party actions, pinned to a major version tag: the checkout action and the cache

    chain for no capability. Use the runner's preinstalled toolchain and print its version as an
    explicit step, so a failure caused by a toolchain change is visible in the log rather than inferred.

    Steps, in this fixed order, each failing the job on a non-zero exit. That ordering is itself a
    guarantee: a clippy failure should stop the run rather than let a broken build's end-to-end results
    confuse the diagnosis.

    First, free disk space. A Servo release build plus its dependencies is large relative to a hosted
    runner's free space, and running out surfaces as a confusing linker error. Remove the preinstalled
    language toolchains and container images the job does not need.

    Second, install system packages: Servo's build prerequisites — pkg-config, cmake, clang, and the
    fontconfig and freetype development headers — plus the test environment's binaries: the X virtual
    framebuffer server, the X display information utility, the X input automation tool, the X window
    dump utility, ImageMagick, and the process utilities that provide the pattern-matching kill the
    harness calls. Fail the job if any package is unavailable rather than continuing; a missing X
    utility must be an install failure, never a silently skipped test.

    Third, cache the cargo registry, the cargo git database, and the build directory, keyed on the
    runner and the lockfile hash. Caching is a speed measure only — a cache miss must change nothing
    about correctness.

    Fourth, build the whole workspace in release mode, then assert both expected binaries exist as an
    explicit step. That assertion stops a later reorganisation from producing a green build whose
    end-to-end step then fails for an unrelated-looking reason.

    Fifth, run clippy across all targets with warnings denied. Sixth, run the Rust unit tests.

    Seventh, run the end-to-end suite. Create a job-private runtime directory with owner-only
    permissions and export it, set the display number the harness should create explicitly rather than
    relying on its default, and set the artifact output directory to a path under the runner's
    temporary space. Then run the orchestrator with the system Python. Its exit code is the gate: zero
    passes, and any non-zero value — including 1, meaning exactly one suite failed — fails the job. Do
    not wrap it in anything that could swallow that exit code.

    Pinning the display and using a job-private runtime directory is also what makes concurrent runs
    safe: two jobs on hosted runners are separate machines, but a self-hosted runner executing two jobs
    at once would otherwise have them fight over the default display and the shared socket path. Put
    that reasoning in a comment.

    On failure only, upload the end-to-end log and screenshot artifacts from the output directory.
    Upload nothing from a home directory or a configuration directory: the credential vault, its key
    file, and the engine profile all live there, and a debugging convenience that publishes the user's
    secrets is not a convenience. Scope the upload path to the artifact output directory and nothing
    else.

    Add a short "Continuous integration" section to `README.md` stating what runs on every push, and
    that the end-to-end suite needs a virtual framebuffer, so a contributor understands why the job
    installs what it installs.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull request from a fork -> CI runner | Untrusted code executes on a runner with whatever token and cache the workflow grants |
| third-party actions -> job | Any non-first-party action is arbitrary code running with the job's permissions |
| job filesystem -> uploaded artifacts | Anything uploaded becomes downloadable, and the runner's home directory holds a vault, a key file, and an engine profile |
| dependency resolution -> build | A fresh resolution changes what code is compiled and run |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-11-01 | Information Disclosure | artifact upload publishing the credential vault or its key | high | mitigate | The upload path is scoped to the end-to-end output directory only, and references no home or configuration directory; asserted by a source criterion |
| T-02-11-02 | Tampering | third-party action executing arbitrary code in the job | high | mitigate | Only first-party actions are used, pinned to a major version tag; the toolchain comes from the runner image rather than a marketplace action. Asserted by a source criterion on every `uses:` line |
| T-02-11-03 | Repudiation | a green conclusion for a pipeline that skipped its real verification | high | mitigate | No path filter, no failure-swallowing step, an explicit binary-existence assertion before the end-to-end step, and the orchestrator's exit code used directly as the gate |
| T-02-11-04 | Tampering | dependency resolution silently drifting to an incompatible combination | high | mitigate | The committed lockfile is used by the main pipeline; a separate scheduled job resolves from scratch and prints the diagnosis and recovery command on failure. The audit job never writes the lockfile back |
| T-02-11-05 | Elevation of Privilege | a fork pull request obtaining a write-scoped token or poisoning the cache | medium | mitigate | The job needs no write permissions; grant it the minimum read scope explicitly rather than relying on repository defaults. The cache key includes the lockfile hash, so a poisoned entry cannot be served to a different dependency set |
| T-02-11-06 | Denial of Service | a cold Servo build exceeding the job timeout and reading as a broken build | medium | mitigate | A generous timeout is configured and the observed duration is recorded against it in the SUMMARY, so the headroom is measured rather than assumed |
| T-02-11-07 | Denial of Service | concurrent runs colliding on the display or the control socket | medium | mitigate | The job pins its own display number and creates a job-private runtime directory at owner-only permissions |
| T-02-11-08 | Tampering | package installs | n/a | accept | The job installs distribution packages from the runner image's configured archives, which is the standard trust root for a hosted runner. No npm, pip, or cargo package is added to the project, and no manifest dependency changes. No legitimacy gate applies |

ASVS level 1; block on high. T-02-11-01 through -04 are high and all mitigated.
