<objective>
Close MCP-11: one slow or wedged tool call no longer blocks tool calls against other tabs, and the
retry that papers over a restarted shell can no longer run a command twice.

Purpose: both sides serialize. `ShellConnection::request` takes a mutex for the whole round trip, so
a wedged `evaluate` blocks every other tool call from that agent — including `tabs_list`,
`screenshot` and `tabs_close` on unrelated tabs — for the full command timeout. The shell mirrors it:
`handle_connection` awaits each request's outcome before reading the next line. And the existing
retry fires on any round-trip error including a post-write read failure, so a `tabs_open` or
`download` whose write succeeded can execute twice. Pipelining makes that bug more likely, which is
why D-10 rides along in the same change rather than being split off.

No wire change is needed or permitted (D-09): the protocol already IDs every request and its module
docstring already documents out-of-order replies. Only the socket layer changes shape.

Output: A background reader with an id-to-waiter map on the MCP side, spawned per-request handling on
the shell side, a retry rule that cannot double-execute, and e2e assertions that prove concurrency on
both the raw socket and the real MCP binary.
</objective>

```rust
pub struct ShellConnection {
    inner: Mutex<Option<Wire>>,
    next_id: AtomicU64,
}

struct Wire {
    reader: BufReader<tokio::net::unix::OwnedReadHalf>,
    writer: BufWriter<tokio::net::unix::OwnedWriteHalf>,
}

impl ShellConnection {
    /// Send one command, await its reply. Connects (with the given client
    /// identity) on first use; reconnects once if the shell restarted.
    pub async fn request(&self, client: &str, command: Command) -> Result<Outcome, String> {
        let mut guard = self.inner.lock().await;          // serialises everything
        for attempt in 0..2 {
            if guard.is_none() {
                *guard = Some(connect(client).await?);
            }
            let wire = guard.as_mut().expect("connected above");
            match round_trip(wire, self.next_id.fetch_add(1, Ordering::Relaxed), &command).await {
                Ok(outcome) => return Ok(outcome),
                Err(error) if attempt == 0 => {
                    // Stale connection (shell restarted): drop and retry once.  <- the D-10 bug
                    *guard = None;
                    let _ = error;
                },
                Err(error) => return Err(error),
            }
        }
        unreachable!()
    }
}
```

```rust
async fn round_trip(wire: &mut Wire, id: u64, command: &Command) -> Result<Outcome, String> {
    write_message(wire, &ClientMessage::Request { id, command: command.clone() }).await?;
    loop {
        match read_message(wire).await? {
            ServerMessage::Reply { id: reply_id, outcome } if reply_id == id => {
                return Ok(outcome);

            ServerMessage::Reply { .. } | ServerMessage::Event { .. } | ServerMessage::HelloAck { .. } => {
                // Not ours (event or stray reply) — keep reading.   <- where events die today

    }
```

    Replace the single-wire round-trip design with a background reader plus a dedicated writer,
    keeping `ShellConnection::new()` and the `request` signature exactly as they are so
    `crates/talaria-mcp/src/tools.rs` needs no change.

    Structure. `ShellConnection` keeps its request-id counter and holds a mutex over an optional
    connected state. The connected state owns: an unbounded sender for outbound client messages that a
    writer task drains and writes to the socket; a shared map from request id to the one-shot sender
    that will deliver that request's outcome, wrapped so both `request` and the reader task can reach
    it; and the join handles for the reader and writer tasks. Choose the map and channel types
    yourself — a standard hash map behind a mutex is sufficient and the choice is explicitly left to
    your discretion by the phase context.

    Connect. Keep the existing `connect` function's body — the unreachable-shell error string and the
    hello-then-acknowledgement handshake are asserted by users and tests and must stay byte-identical.
    After a successful handshake, split the wire and spawn the two tasks. The writer task drains the
    outbound channel and writes each message, breaking on the first write failure, exactly like the
    shell's writer. The reader task loops reading server messages: on a reply, remove that id from the
    waiter map and send the outcome to it, discarding the result because a caller that gave up is not
    an error; on an acknowledgement, ignore it; on an event, ignore it for now and leave a comment
    naming plan 02-08 as the change that turns this arm into an MCP notification — that seam is the
    only reason D-11 becomes possible at all. On a read error or a closed connection, exit the loop,
    clear the waiter map so every outstanding caller's one-shot is dropped (they observe a closed
    channel rather than hanging forever), and abort the writer task so the outbound channel closes and
    the next `request` sees a dead connection.

    Request. Take the mutex only long enough to establish or validate the connected state, allocate
    the request id, register a fresh one-shot in the waiter map, clone the outbound sender, and drop
    the mutex. Then send the request message on the cloned sender and await the one-shot outside the
    lock. That is what makes concurrent calls concurrent: the lock is held for bookkeeping, never
    across a network round trip.

    Retry rule (D-10). Attempt at most twice, and only ever re-attempt for one reason: the connection
    was not live at the moment this call tried to hand its request over. Concretely, treat the state
    as needing a reconnect when it is absent or when its outbound sender reports itself closed, and
    treat a failed send on the outbound channel the same way — a closed channel means the writer task
    is gone and this message was never handed to a live wire, so re-sending cannot double-execute.
    Before re-attempting, remove the id from the waiter map and clear the connected state. Once the
    send succeeds, there is no retry: if awaiting the one-shot yields a closed channel, return an
    error saying the shell closed the connection before replying. A request that reached a live
    connection is never re-sent, which is exactly the bug being fixed — a retried tabs_open or
    download that runs twice is worse than the error it was hiding.

    Keep `write_message` and `read_message` as helpers, adapting their parameter types to the split
    halves. Do not introduce `unwrap()`; the file's existing `expect` on a just-established connection
    disappears with the design that needed it. Do not add a dependency and do not touch the wire
    format — no new message type, no new field, no serde change.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP client -> proxy -> control socket | An agent can now have many requests outstanding at once, so per-request state is attacker-influenced in volume |
| shell read loop -> spawned per-request tasks | Untrusted request volume decides how many tasks exist concurrently |
| reply id -> waiter map | A server-supplied id selects which caller receives which outcome |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05-01 | Tampering | retry re-executing a non-idempotent command | high | mitigate | Retry is restricted to the case where the outbound channel was closed, meaning the message never reached a live wire; a successful send is never retried |
| T-02-05-02 | Spoofing | a reply id steering an outcome to the wrong caller | medium | mitigate | Ids are allocated by the client's own monotonic counter and removed from the waiter map on delivery, so an unknown or repeated id matches nothing and is discarded |
| T-02-05-03 | Denial of Service | unbounded per-request task growth from a request flood | medium | accept | Each task is bounded by the command timeout and the connection is already peer-UID gated by plan 02-03, so the flood source is the same local user. Bounding the per-connection event channel is recorded as deferred in the phase context |
| T-02-05-04 | Denial of Service | outstanding callers hanging forever after the reader exits | medium | mitigate | The reader clears the waiter map on exit, so every outstanding one-shot is dropped and its caller observes a closed channel rather than hanging |
| T-02-05-05 | Repudiation | teardown truncating replies for outstanding requests | medium | mitigate | The task set is drained before the outbound sender is dropped, and the writer is awaited rather than aborted |
| T-02-05-06 | Information Disclosure | events read by the background reader being surfaced to the wrong session | high | mitigate | The event arm stays a no-op in this plan; owner filtering lands with the queue in plan 02-07 before plan 02-08 surfaces anything, so no unfiltered event can reach a client at any point in the phase |
