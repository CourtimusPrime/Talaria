<objective>
Close MCP-12: `download` is bounded, cannot fill the disk, cannot clobber a user file, and cannot
outlive the request that started it.

Purpose: `Command::Download` validates only that the filename contains no separator and no parent
reference, then a detached thread performs a blocking fetch and copies the whole body into the
downloads directory. There is no content-length limit, so an agent can fill the disk; no
existing-file check, so it silently clobbers a same-named user file; and no timeout, so the thread
outlives the 30-second command timeout and keeps writing long after the agent was told the call
failed.

Routing through Servo's network stack is explicitly deferred (D-20) — it is the right fix for
downloads behind a login silently fetching the login page, but it is an `ureq`-to-Servo-fetch
re-architecture and Phase 3 builds the storage and progress model anyway. This plan records that as
a stated limitation in the tool description instead of hiding it.

Output: An env-tunable byte cap with partial-file cleanup, exclusive-create uniquifying, a request
timeout under the command timeout, a cancellation handle, and an e2e suite that proves all of it.
</objective>

fn download(url: &str, filename: &str) -> Outcome {
    let dir = dirs::download_dir().unwrap_or_else(|| std::path::PathBuf::from("."));
    let path = dir.join(filename);
    let response = match ureq::get(url).call() {
        Ok(response) => response,
        Err(error) => return Outcome::Error { message: format!("request failed: {error}") },
    };
    let mut reader = response.into_reader();
    let file = match std::fs::File::create(&path) {
        Ok(file) => file,
        Err(error) => return Outcome::Error { message: format!("create failed: {error}") },
    };
    let mut writer = std::io::BufWriter::new(file);
    match std::io::copy(&mut reader, &mut writer) {
        Ok(bytes) => Outcome::Ok {
            result: ResultPayload::Download { path: path.display().to_string(), bytes },
        },
        Err(error) => Outcome::Error { message: format!("write failed: {error}") },
    }
}

    `std::io::Result<(std::fs::File, std::path::PathBuf)>`. It splits the filename at its final dot
    into a stem and an extension (a name with no dot is all stem), then tries candidate names — the
    plain name first, then the stem followed by a space and a parenthesised counter, then the
    extension — creating each with `std::fs::OpenOptions` configured to write and to create
    exclusively. Exclusive creation, not truncating create, is what makes the no-clobber guarantee
    hold under two concurrent downloads asking for the same name: the loser of the race gets an
    already-exists error and advances to the next counter rather than opening the winner's file.
    Advance the counter only on an already-exists error; return any other error. Stop after a bounded
    number of attempts — use 1000 — and return an already-exists error rather than looping forever.

    Rewrite `download` to take the destination directory resolution it has today, then call
    `create_unique` instead of the truncating create, so the returned path is the path actually
    written. Build the HTTP request through a `ureq` agent configured with the download timeout for
    both connect and read, rather than the bare module-level get, so a server that accepts and then
    stalls cannot hold the thread open past the command timeout.

    Replace the whole-body copy with an explicit loop over a fixed-size buffer. On each iteration:
    read a chunk; add its length to a running total; if the total would exceed the cap, stop. Write
    the chunk. After a successful full read of the body, flush the writer and return the ok outcome
    carrying the uniquified path and the exact running total. The reported byte count is the number
    of bytes written, not a content-length header, because the header is attacker-controlled and may
    not match the body.

    On the cap being exceeded, on a read error, on a write error, and on cancellation: drop the
    writer, remove the file at the uniquified path so no partial file survives, and return the
    corresponding error outcome. The cap message names the cap in bytes and the environment variable
    that tunes it. Keep every message lowercase with no trailing period.

    Give `download` a fourth responsibility: cancellation. Change its signature to take a reference to
    the reply sender, and check that sender's closed state at the top of each loop iteration. Once
    the control socket's command timeout has dropped the receiver, the sender reports closed and the
    loop stops, deletes the partial file, and returns without writing further — which is the whole
    point of D-19. Also enforce an overall deadline computed from the download timeout at the same
    check, so a peer that drips bytes slowly enough to defeat the per-read timeout is still bounded.

    Update the `Command::Download` arm to keep its existing filename validation and its early return

| detached thread -> user's filesystem | Runs outside the event loop with no supervision once spawned |
