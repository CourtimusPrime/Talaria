<objective>
Finish AGENT-04: tab crash and close events reach MCP clients as notifications instead of dying in the
proxy.

Purpose: the events exist on the control socket and a raw client already receives them, but
`crates/talaria-mcp/src/socket.rs` treats a server event as noise to skip while hunting for a reply
id. An agent whose tab crashes finds out only when its next tool call returns a crash error — it
cannot react, and it cannot tell a crash apart from a slow page without polling.

This plan is the last link in a chain the phase has been building: plan 02-05 replaced the
request-reply mutex, which structurally could not raise an unsolicited message, with a background
reader that can (D-14); plan 02-07 made the shell address each event to exactly the session that owns
the tab (D-12) and stop dropping events under reentrancy (D-13). Here the reader's event arm stops
being a no-op.

Output: An event sink out of the reader, a notification capability advertised by the server, a drain
task that emits the notification, and an e2e proof that it arrives at its own session and at no other.
</objective>

Where the connection is constructed and where the server runtime is built
(`crates/talaria-mcp/src/main.rs:57-101`):

```rust
#[tokio::main]
async fn main() -> SdkResult<()> {
    let connection = ShellConnection::new();

    let server_details = InitializeResult {
        server_info: Implementation { /* ... */ },
        capabilities: ServerCapabilities {
            tools: Some(ServerCapabilitiesTools { list_changed: None }),
            ..Default::default()
        },
        meta: None,
        instructions: Some(/* ... */),
        protocol_version: ProtocolVersion::V2025_11_25.into(),
    };

    let transport = StdioTransport::new(TransportOptions::default())?;
    let handler = Handler { connection };
    let server = server_runtime::create_server(rust_mcp_sdk::mcp_server::McpServerOptions {
        server_details, transport, handler: handler.to_mcp_server_handler(),
        task_store: None, client_task_store: None, message_observer: None,
    });
    server.start().await
}
```

`Handler` owns the connection (`crates/talaria-mcp/src/main.rs:25-27`), and
`handle_call_tool_request` already receives an `Arc<dyn McpServer>` runtime handle
(`crates/talaria-mcp/src/main.rs:43-55`) — that is one route to a runtime reference without
restructuring `main`.

Crate versions and features: `rust-mcp-sdk` 1.0.1 with `server`, `macros`, `stdio` and
`default-features = false` (root `Cargo.toml:45`); tokio in the MCP crate has `rt-multi-thread`,
`net`, `io-util`, `sync`, `macros`. No dependency change is expected.

MCP protocol version advertised: `V2025_11_25`.

The e2e client's transport contract (`tests/e2e/mcp_client_test.py`): JSON-RPC 2.0 spoken line by line
to `target/release/talaria-mcp` over stdin and stdout with line buffering; initialize, then an
initialized notification, then a tool list asserted against an exact sorted list, then a call for

closes, the last 800 characters of stderr are reported.

| AGENT-04 | unclassified | unresolved | "unclassified — review manually" | AGENT-04's text says "tab open/close/crash events reach MCP clients as MCP notifications". The control-socket protocol defines only two event variants — crash and close — and defines no tab-open event, so this plan delivers crash and close and does **not** invent a wire-level open event. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| control socket -> proxy reader | Events arrive unsolicited on the same stream as replies; a malformed or unexpected one must not derail reply matching |
| proxy -> MCP client stdout | The transport stream is shared with the JSON-RPC protocol; any stray write corrupts the session |
| session A's proxy -> session B's proxy | Two separate processes; the only thing keeping B ignorant of A's tabs is the shell's addressing |

## STRIDE Threat Register

| T-02-08-01 | Information Disclosure | proxy re-broadening the shell's owner addressing | high | mitigate | The proxy forwards its own connection's events only and performs no fan-out; the second-proxy silence assertion in the e2e suite fails if it ever does |
| T-02-08-02 | Repudiation | notification discarded when no runtime exists yet or the channel is closed | high | mitigate | Events are buffered until a runtime handle exists, and every send failure is logged rather than swallowed |
