<objective>
Cut the MCP tool surface out of the stdio binary and into a library crate target, behind a
`CommandSink` trait that abstracts *how a `Command` reaches the shell*. No behaviour change: the
stdio proxy keeps working exactly as it does today, and the diff is a move plus one parameter type.

Purpose: Success Criterion 1 says an HTTP client must "drive the same tool surface." Today
`dispatch` hard-codes `&ShellConnection` (`crates/talaria-mcp/src/tools.rs:120-124`), so a second
transport in the shell would need a second copy of the nine tool definitions — at which point "the
same tool surface" is a thing a human re-verifies by eye every phase instead of a thing the compiler
holds. `04-CONTEXT.md`'s D-04-03 makes this the phase's first plan for exactly that reason: it is
what turns SC 1 from a review item into a structural property, and every later plan in this phase
consumes it.

This plan writes no HTTP, no auth, and no shell code. It touches one crate.

Output: `crates/talaria-mcp/src/lib.rs` with `CommandSink` and a transport-agnostic `dispatch`, a
`[lib]` target on the crate, `impl CommandSink for ShellConnection`, and a `main.rs` that is a thin
consumer of its own library — with `tests/e2e/mcp_client_test.py` proving the stdio path is
byte-for-byte what it was.
</objective>

<interfaces>
**The one line that couples the surface to stdio** (`crates/talaria-mcp/src/tools.rs:120-124`):

```rust
pub async fn dispatch(
    connection: &ShellConnection,
    client: &str,
    tool: TalariaTools,
) -> Result<CallToolResult, CallToolError> {
```

**Its one use** (`crates/talaria-mcp/src/tools.rs:137-140`):

```rust
    let outcome = connection
        .request(client, command)
        .await
        .map_err(CallToolError::from_message)?;
```

Those two are the entire seam. The `Command` match (`tools.rs:125-135`) and the `ResultPayload`
match (`tools.rs:147-178`) touch nothing but `talaria_protocol` types and are already
transport-agnostic — **do not restructure either one.**

**The existing request signature to forward to** (`crates/talaria-mcp/src/socket.rs:85`):

```rust
    pub async fn request(&self, client: &str, command: Command) -> Result<Outcome, String>
```

It is already exactly the shape the trait method needs, which is why the impl is a one-line forward
and why no retry / pipelining / reconnect logic moves in this plan.

**The stdio consumer that must keep compiling with the same semantics**
(`crates/talaria-mcp/src/main.rs:44-55`) — the only change is the path `dispatch` is called through.

**The module-scoped lint allow** at the head of `tools.rs`
(`#![allow(clippy::enum_variant_names)]`, `tools.rs:11`) exists because `tool_box!` generates the
variant names. An inner attribute is only legal at the top of a module file, so it stays where it
is when `tools.rs` becomes a module of the library rather than of the binary. Do not move it to
`lib.rs` and do not narrow it.

**Crate facts, already checked** (`04-PATTERNS.md`, "Crate-level note"): `talaria-mcp` has `serde`
with `derive`, `rust-mcp-sdk`, and `async-trait` today; `talaria-shell` has none of them. Adding a
`[lib]` target here is what later lets `talaria-shell` depend on this crate — that dependency edge
is **04-02's** to add, not this plan's. This plan changes no dependency anywhere.

**Async trait mechanics:** `async_trait` is already a direct dependency of this crate (used at
`main.rs:30` for `impl ServerHandler`). Use `#[async_trait::async_trait]` on both the trait and the
impl; the trait needs `Send + Sync` bounds so a `&dyn CommandSink` can cross a tokio task boundary
in the shell's future use.

| library crate → future second consumer | After this plan the tool surface has two callers instead of one. A definition that drifts between them is the failure mode SC 1 exists to prevent |
