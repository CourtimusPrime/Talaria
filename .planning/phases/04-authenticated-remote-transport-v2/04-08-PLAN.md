<objective>
Close AUTH-02 and Success Criterion 3: a list of authorized agents the human can see, a Revoke that
actually revokes, and — the part that is easy to skip and easy to get wrong — termination of a
revoked client's already-open response streams.

Purpose: `04-RESEARCH.md` calls the open-stream case "the single most likely way SC 3 gets marked
done while being false." The ordinary path is nearly free: the specification requires authorization
on **every** request even within one logical session, so a revocation lands on the next request
provided verification reads live state, which 04-05 guaranteed and asserted. The part that is not
free is a long-lived response stream, which has no next request to fail. A revocation that only
stopped new requests would leave a revoked agent still receiving from the browser, and a test that
only issued a fresh request would pass anyway. So this plan keeps a registry of live stream handles
per client, drops them on revoke, and asserts the stream *closes* rather than asserting the next
POST fails.

This plan also completes the Access panel. 04-03 shipped its status half — the listener's state and
the switch that turns it on. This adds the list half: one row per authorized client, keyed on the
client id, with a two-step Revoke keyed on that same id rather than on a row index, so a list that
reorders between the arming click and the confirming one cannot move the confirmation onto a
different client. The panel lists **clients, not sessions**: sessions come and go with every
reconnect, and the thing a human revokes is the agent.

Output: the revocation endpoint, the stream registry and its termination, the Access panel's client
list, `tests/e2e/revocation_test.py`, and the phase's closing documentation.
</objective>

<interfaces>
**Read `04-02-SPIKE.md`'s A6 finding first.** Assumption A6 is whether terminating a revoked
client's live handles is expressible against the published API. The spike was asked to answer it or
to mark it explicitly open. If it is **open or negative**, the fallback `04-RESEARCH.md` names is a
per-request re-check inside the stream's own keepalive — the stream re-verifies on each keepalive
tick and closes itself when verification fails. That fallback is acceptable and must be implemented
with a stated bound: the maximum time a revoked client's stream can keep delivering is one keepalive
interval, and that number goes in `SECURITY.md`. Do not leave the case unimplemented on the grounds
that the API made it awkward.

**The store already revokes** (`crates/talaria-shell/src/agents.rs`, 04-04):
`revoke_client(client_id) -> bool` removes the registration and every token in the client's family,
returns whether anything changed, and persists only on an actual change — which is both the
already-revoked adjacency answer and the restart-survival mechanism. `revoke_family(family_id)` does
the token half alone and is what the revocation endpoint uses when a caller presents one token.
`clients()` returns records in **insertion order**; the store deliberately does not sort, because
two clients authorized in the same millisecond would then have an order depending on a sort's
stability. Display-side ordering is this panel's business.

**The panel's existing half** (04-03): the status block, the enable control, `toolbar.access`, the
`access.status` rect, and `Gui::confirm_enable_remote`. This plan adds the list below the status
block, separated by the medium spacing token, wrapped in a vertical scroll area like Bookmarks.

**Arm-then-confirm, and why keyed on identity.** `gui.rs:1240-1273` is the pattern — two clicks in
place, no modal, the confirming state dying with the panel via `set_panel`, and **two rect names for
one control** so the armed state and the reset are observable rather than inferred. Phase 3's
`confirm_clear_history` is a `bool` governing a single control; a per-row confirm keyed by row
*index* would move onto a different client if the list reordered between the two clicks, so this one
is an optional client id. The counter-precedent is real and should be acknowledged in the comment:
`RemoveBookmark` and `DeleteCredential` are immediate row-trash buttons with no confirming click.
Revoking is not that, because the failure mode is an agent silently losing access mid-task rather
than a row a human can re-add in two seconds.

**Untrusted-claim handling in a row** (`04-UI-SPEC.md`, "The Access panel"): the claimed name goes
through `truncate_chars` then `sanitize_claim` — the same helper 04-06 added — and is rendered in
quotes with a small `(as claimed)` suffix, because the fence the consent screen uses does not exist
in a single-line row and the quotes plus the suffix carry the framing instead. The client id is
truncated too; the full values live in the row's hover text.

**No "last used" column**, deliberately (`04-UI-SPEC.md` Open Question 4). It would be genuinely
useful and it is excluded because with the whole-document atomic rewrite this store uses, a
last-used timestamp makes every authenticated request a disk write. The relative authorization time
costs nothing and answers the question that actually matters when revoking. If a later phase moves
the store to an append log or accepts a debounced write, it becomes a cheap addition rather than a
redesign — record that in `deferred-items.md`.

**The AUTH-02 concurrency probe has to be answered, not dodged.** A request that passed verification
a microsecond before the revoke completed will finish. That is correct and it is the honest answer:
the boundary is the verification, verification is per request, and a mid-flight command is already
executing against the engine. What must not happen is the *next* request succeeding, or an open
stream surviving. Say so in the code comment and in `SECURITY.md`, and let the e2e suite pin the two
things that are actually guaranteed.

**What happens to a revoked agent's tabs** is a question this plan must answer explicitly rather
than leave to discovery. The conservative answer, consistent with the product: leave them open. They
are visible in the Agents view, the human can take any of them over, and closing a person's tabs
because a credential was withdrawn would destroy state they may want. Record the decision and its
reasoning in the SUMMARY and in `deferred-items.md` if a later phase should revisit it.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a revoked client → an already-open response stream | Verification is per request, and an open stream has no next request to fail — the one place where "revoked" can be true of the store and false of reality |
| the revocation endpoint → an unauthenticated caller | Anyone who can reach the listener can call it; a response that distinguished outcomes would be an oracle for which tokens exist |
| the Access panel's Revoke → the agent tool surface | A revoke reachable from a tool would let an agent revoke a competitor, or itself, without the human |
| an attacker-chosen display name → a list row | The same untrusted claim the consent screen handles, in a surface with no room for a fence |
| a list that reorders → a half-armed confirmation | An index-keyed confirm can complete against a different client than the one it was armed on |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-7 | Elevation of Privilege | a revoked agent's open event stream continuing to deliver | high | mitigate | A registry of live stream handles per client, dropped in the same action that removes the client from the store, so "revoked" means both halves; if `04-02-SPIKE.md`'s A6 finding made handles unaddressable, the recorded fallback is per-keepalive re-verification with a stated, documented bound. The e2e suite asserts the stream **closes** from the client end rather than asserting that a fresh request fails, which is the assertion that would have passed regardless. The legacy event-stream transport feature was never enabled (04-02), which removes the other half of this surface entirely |
| T-04-08-01 | Elevation of Privilege | a revoke reachable from an MCP tool or a control-socket command | high | mitigate | The revoke action follows `OpenDownload`'s rule and its doc comment: one panel's own button, applied in `apply_ui_actions`, no protocol variant, no control-socket command, no MCP tool. Asserted by a source criterion returning 0 across the tool surface and the protocol crate |
| T-04-08-02 | Tampering | a confirming click landing on a different client than the one it was armed on | high | mitigate | The armed state is an optional client id rather than a row index or a boolean, so a list that reorders between the two clicks cannot move the confirmation; the two states carry different rect names so the arming is observable, and the e2e suite asserts the arming affected exactly one row |
| T-04-08-03 | Information Disclosure | the revocation endpoint acting as an oracle for which tokens exist | medium | mitigate | Always success, identical response for a valid token, an already-revoked token and a never-valid token — the specification's own requirement, unit-tested for byte-identical responses |
| T-4 | Spoofing | an attacker-chosen display name in a list row | high | mitigate | The same `sanitize_claim` plus `truncate_chars` treatment the consent screen uses, with quotes and a claimed-suffix carrying the framing that a single-line row has no space to fence. The client id — the identifier the client did not choose — is what the row is keyed on and what the revoke carries |
| T-04-08-04 | Repudiation | revocation appearing to work in the session and not surviving a restart | medium | mitigate | The store's `revoke_client` removes the registration as well as the tokens and persists through the atomic whole-document rewrite; the e2e suite restarts the shell and re-asserts the refusal, the row count and the surviving client |
| T-04-08-05 | Denial of Service | the stream registry growing without bound as requests complete | low | mitigate | Handles remove themselves on normal completion, unit-tested, and the whole registry is dropped at listener shutdown |
| T-04-08-SC | Tampering | package installs | n/a | accept | No dependency change; every crate this plan uses landed in 04-02 with its Package Legitimacy Audit recorded there |

ASVS level 1; block on high. The four high-severity items are all mitigated within this plan: the
open-stream gap by a registry terminated in the same action as the store mutation and asserted from
the client end; the tool-reachability by the established single-call-site rule with a source
assertion; the misdirected confirmation by keying the armed state on identity rather than position;
and the hostile display name by reusing the sanitiser 04-06 built for the higher-stakes surface.

**Concurrency, stated rather than mitigated:** a request that passed verification a moment before a
revoke completes will finish. That is the honest boundary — verification is per request, and a
command already executing against the engine is not interruptible. It is documented in the code, in
`SECURITY.md`, and in the e2e suite's docstring, and what the suite pins instead is the two things
that *are* guaranteed: the next request is refused, and the open stream closes.
