<objective>
Build the front half of Talaria's own OAuth 2.1 authorization server: metadata, dynamic client
registration, the authorization endpoint with its full validation chain, and the human approval step
that happens in native chrome. A client can get from *knowing only the MCP endpoint URL* to *holding
an authorization code*. Exchanging that code for a token is 04-07's.

Purpose: `04-RESEARCH.md`'s fork settles that Talaria is a resource server co-hosting its own
authorization server — which the specification explicitly permits and which is what the roadmap
meant — and that the authorization-server logic is Talaria's to write *inside* the SDK's routing and
401 machinery rather than from scratch. The SDK gives the plumbing; the validation chain, the code
store, the consent surface and the anti-harassment caps are this plan's.

The consent surface is the security centre of the phase, not its decoration. `http` is in the agent
navigation allowlist, so an agent holding `evaluate` can open Talaria's own authorization endpoint
in a tab it owns and script the page. A page-hosted Approve button would therefore be clickable by
the exact party requesting permission. So the endpoint serves a page with no controls at all and the
decision happens in egui — and, because adding a `Consent` variant to `ChromePanel` makes
`SetPanel(Consent)` *representable*, both `apply_ui_actions` and `Gui::set_panel` refuse it
outright. That refusal is what turns "no control constructs it" from an invariant every future panel
button has to maintain into a property a reviewer confirms in one place, the same move that made
`OpenDownload`'s single call site checkable.

**Split note.** This was one plan with the token endpoint until the plan-checker flagged its size:
one task was carrying metadata, registration, the five-step authorization chain, parking, the
holding page, the code store, constant-time PKCE, refresh rotation and a two-armed cooldown machine,
against peer tasks a quarter that size. The seam is the code: this plan **writes** authorization
codes, 04-07 **redeems** them. Everything a human sees, and every refusal that happens before a
human is asked, lands here; everything that turns a code into a credential lands there.

**This plan depends on `04-02-SPIKE.md`'s answer.** Assumption A1 — whether `rust-mcp-axum` routes a
self-hosted authorization server's declared endpoints to the provider's `handle_request` — was
settled before this plan was executed precisely because it is this plan's foundation. Read that file
first. If it recorded `A1: REFUTED`, do not improvise: escalate, because the recorded alternative
changes this plan's shape rather than one of its lines.

Output: the authorization-server front half of `oauth.rs`, `ChromePanel::Consent` and its rules,
`AppEvent::ConsentRequested`, and `tests/e2e/oauth_flow_test.py`'s consent half — driven from the
endpoint URL alone, with approval delivered by a real click on the real control.
</objective>

<interfaces>
**The store already owns the token half** (`crates/talaria-shell/src/agents.rs`, built in 04-04).
This plan calls `register(client_name, redirect_uris) -> Option<AgentClient>`, which mints a
`client_id`, leaves the authorization time unset, and returns nothing when the registration cap is
reached — an unapproved registration is inert. `authorize(...)` and `rotate_refresh(...)` are
04-07's callers, not this plan's. The digest helper is `agents.rs`'s; do not define a second one.

**Chrome mechanics, all existing** — this is a seventh instance of a mechanism that has six:
`ChromePanel` (`gui.rs:26-40`), `UiAction` and its "even this goes through the round trip" rule
(`gui.rs:53-68`), `UiAction::OpenDownload`'s security paragraph (`gui.rs:89-103`) which the consent
actions need in the same form, `truncate_chars` (`gui.rs:115-126`, counted in characters because
`String::truncate` panics mid-codepoint), `is_display_unsafe` and `sanitize_for_display`
(`gui.rs:128-158`), `record_rect` (`gui.rs:176-204`, where the absence of the collection is the off
switch), `Gui::set_panel`'s reset-everything discipline (`gui.rs:400-424`), and `apply_ui_actions`
(`app.rs:1253-1262`) with its `drop(borrow)` before `request_redraw`.

**The parked-request round trip, and one deliberate divergence from `04-UI-SPEC.md`'s literal
signature.** The spec says `Gui::raise_consent(request)`. It also says, in the same contract, that
**no timing state lives on `Gui`** — the arm delay reads the request's `raised_at_ms` off `Shared`.
Both cannot hold if the request is handed to `Gui`. Resolution: the request is parked on
`Shared::pending_consent` and read by the panel body each frame the way every other panel reads its
store, and `Gui::raise_consent()` takes no argument — it performs the same view-state reset
`set_panel` does and sets the panel. What the contract actually fixes is that the reset happens on
**both** paths and that `set_panel` is not one of them, and both hold. Record this in the SUMMARY as
a deliberate reconciliation rather than a drift.

**Expiry, and who owns the clock.** The parked request carries a `oneshot::Sender`; the HTTP side
holds the receiver and bounds its wait. When the HTTP side times out it drops the receiver, which
makes `Sender::is_closed()` true — the cancellation handle decision 02-04 established, and the same
mechanism 04-03 relies on for shutdown. The panel checks it on the repaint it already schedules for
the arm delay and closes itself. This puts **every** cooldown arming on the HTTP side, which is what
`04-UI-SPEC.md` requires: the chrome emits no action for a resolution it never sees, so an expiry
cooldown armed by the chrome would never arm at all.

**Consent timings, and the decision the plan-checker asked for.** `04-UI-SPEC.md` fixes a 120 s
parked-request lifetime, a 10 s cooldown after Deny and a 30 s cooldown after expiry, and records all
three as invented anti-harassment caps rather than specification requirements. Those durations are
correct for a human and ruinous for a test: an e2e suite that must observe an expiry and then the
cooldown it arms would spend two and a half minutes on one assertion, and `run_all.py` runs
sequentially on a single self-hosted runner.

**Decision: the durations are compiled constants that a `TALARIA_TEST_HOOKS=1`-gated override may
shorten.** Option (a) — accept the real wait — was considered and rejected: it would add roughly
three minutes to a suite this phase already grows by three files, and it would make the expiry path
the slowest thing in the repository's verification, which is how an assertion gets quietly deleted
later. The override is deliberately narrow, and its narrowness is the whole argument for it:

- It adjusts **durations only**. There is no override that answers a request, and the approve branch
  reads no environment variable at all — asserted by a source criterion confining every override
  name to the one timing function, and by a unit test that sets every override to its floor and
  confirms an unanswered request still resolves as **denied**.
- It can only **shorten**. Each value is clamped to the compiled default as a ceiling and to a
  non-zero floor, so an override cannot lengthen a security timeout, cannot zero one, and cannot
  turn a cooldown off.
- It is gated exactly as `Command::ChromeRects` is (`app.rs:1892-1909`): read once, behind
  `TALARIA_TEST_HOOKS=1`, and inert in any build the variable is not set for.

This is not the bypass 04-06's own prohibition forbids. Shortening how long a human has to answer is
not answering; the grant still requires the human's click on the native control, and that path is
what the source criterion and the floor-value unit test pin. Say all of this in the timing
function's own doc comment, so the next reader meets the reasoning rather than the knob.

**Copy is a contract here, not a suggestion.** `04-UI-SPEC.md`'s Copywriting Contract fixes every
line on the consent screen and the four holding-page bodies. Use it verbatim, including the seven
grant bullets, which were written against the actual tool surface. The `tool_box!` invocation in
`crates/talaria-mcp/src/tools.rs` carries a comment (added by 04-01) recording that this coupling
runs both ways.

**`sanitize_claim` is `sanitize_for_display` plus one rule.** The ASCII double quote is also
replaced with the replacement character, because here the quote *is* the delimiter: a claimed name
of `Talaria" verified by Talaria "` would otherwise render as Talaria's own words. Replacement
rather than removal, for `sanitize_for_display`'s own stated reason — a dropped character lets a
name shorten silently into something else plausible. Curly quotes are left alone: they cannot forge
an ASCII delimiter, and mangling ordinary punctuation in a legitimate name costs trust for nothing.

**Redirect URI matching** must be exact against the registration, with the loopback port as the only
permitted variance — RFC 8252 requires an authorization server to allow any port for a loopback
redirect, because a native client binds an ephemeral one. Loopback IP literals are preferred over
the `localhost` name. This is the one place where "exact match" has a documented exception, and the
exception is exactly one field wide.

**What is deliberately not implemented** (`04-CONTEXT.md` D-04-02): Client ID Metadata Documents.
They require the authorization server to fetch an attacker-supplied HTTPS URL, which is an
unauthenticated server-side request forgery primitive inside the process holding the credential
vault. The metadata advertises a registration endpoint and does **not** advertise that capability,
because advertising an unimplemented capability breaks conformant clients that prefer it. The
deferral and its reasoning are already recorded in this phase's `deferred-items.md` by 04-02.

**The issuer parameter** (RFC 9207) is cheap to emit and is a SHOULD moving toward a MUST. If it is
emitted in the authorization response, the metadata must advertise that it is — an emitted parameter
the metadata does not claim is as broken as the reverse. Decide, do both or neither, and say which
in the SUMMARY.

    **Registration.** Parse a registration request, take the display name and redirect URIs, and
    call the store's `register`. Validate the redirect URIs before storing them: each must parse,
    and each must be either an HTTPS URL or a loopback HTTP URL — the loopback exception is the only
    reason an HTTP redirect is admissible at all. Refuse the whole registration if any URI fails,
    rather than storing a partial list. The response carries the minted client id and the echoed
    metadata. **Nothing is fetched.** The redirect URI is compared and displayed; it is never
    dereferenced, which is the whole of what makes this endpoint safe to expose unauthenticated.

    **Authorization.** Validate in this order, refusing with the appropriate OAuth error before any
    panel is raised: the client is registered; the redirect URI matches the registration exactly,
    with the loopback port as the only permitted variance; the challenge method is S256; the
    challenge is present and well-formed; and the resource parameter names this server's canonical
    identifier. A refusal here is why the chrome never has to render an invalid request — say that
    in the comment, because it is the reason the consent panel has no error state.

    Then check the two harassment caps before parking: at most one request on screen at a time, and
    no request during a cooldown. Both refuse with access-denied immediately and raise nothing. A
    comment carrying the reasoning: a cooldown scoped to denial alone would leave the expiry path
    open, letting a peer raise a request, wait out a human who simply ignores it, and re-raise the
    instant it expires — holding the displayed page off screen indefinitely, because a panel replaces
    the page. Because the cooldown covers denial and expiry alike, an unauthenticated local peer
    cannot repaint the chrome faster than the human can browse. Approval needs no cooldown: a client
    that just received a code has no reason to ask again, and the one-on-screen cap still applies.

    Park the validated request keyed by a random id, carrying the client id, the claimed name, the
    validated redirect URI, the challenge, the state, and the time it was raised. Send
    `AppEvent::ConsentRequested` with the parked request. Await the decision under the parked-request
    lifetime from the timing function; on timeout, resolve as access-denied and arm the longer
    cooldown.

    bound to the client id, the challenge and the redirect URI it was issued for, and stamped with
    an expiry from the timing function. Codes come from the operating system's random source, never
    a clock. On approval, mint one and redirect the caller to its registered redirect URI carrying
    the code and the original state. Single-use is enforced at redemption, which is 04-07's — write

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an unauthenticated caller → the registration endpoint | Anyone who can reach the listener can register; every field they supply is attacker-chosen |
| an attacker-chosen display name → the human's approval decision | The name is shown at the exact moment the human decides whether to hand over browser control |
| a page in a Talaria tab → the approval control | `http` is in the agent navigation allowlist, so an agent can point a tab at this server's own endpoints |
| the chrome → secret material | Anything the chrome handles is one panel bug away from being rendered |
| a caller-supplied URL → the authorization server's own network access | An authorization server that fetches what a caller names is an unauthenticated request-forgery primitive inside the vault's process |
| the environment → the consent state machine | A test-only knob on a security timeout is one edit away from being a knob on the security decision |
