<objective>
Turn an authorization code into a credential. This is the back half of Talaria's authorization
server: the token endpoint, constant-time PKCE verification, single-use code redemption, and the
refresh grant wired to the rotation and reuse detection the store has owned since 04-04. It closes
AUTH-01 and Success Criterion 2.

Purpose: 04-06 gets a client from *knowing only the MCP endpoint URL* to *holding a code*, and stops
there deliberately. This plan is the seam's other side. The split exists because the two halves have
genuinely different shapes: 04-06 is validation and human interaction — five refusals, a panel, a
holding page, an anti-harassment state machine — while this plan is cryptographic and concurrent,
and its failure modes are a code redeemed twice, a verifier compared in variable time, and a rotation
that either misses a replay or false-positives on a legitimate retry. Reviewing those in the same
commit as consent copy is how one of them gets skimmed.

Almost nothing here is invented. The store already mints token families, rotates refresh tokens and
detects reuse, all unit-tested in 04-04 against a pinned clock, including the false-positive case the
AUTH-01 concurrency probe names: a client retrying with its *current* token rotates normally, and
only a token the store has already consumed revokes the family. This plan is the protocol that calls
that, plus the one genuinely new piece — redemption — which has to be a remove-and-return in a single
operation, because a read-then-remove pair is how two concurrent exchanges both find the same code.

Output: the token endpoint in `oauth.rs`, and `tests/e2e/oauth_flow_test.py` completed into the full
round trip — discovery, registration, approval by a real click, exchange, an authorized tool call
that opens and closes a real tab, rotation, and a reuse that takes the family with it.
</objective>

<interfaces>
**The store owns rotation and reuse detection** (`crates/talaria-shell/src/agents.rs`, 04-04):

- `authorize(client_id, ...) -> Option<(String, String)>` — marks the client authorized and mints an
  access/refresh pair sharing a fresh family id, returning both raw tokens exactly once.
- `rotate_refresh(digest, now_ms) -> RefreshOutcome` — three outcomes, and the distinction that
  matters is already implemented and unit-tested there: **rotated** with a new pair, **reuse
  detected** with the family already revoked as a side effect, and **unknown or expired**. A client
  retrying with its current, unconsumed token is not reuse; only an already-consumed token is. The
  mark-consumed-then-issue happens in one mutation, so two interleaved rotations of one digest cannot
  both succeed.
- The digest helper and the constant-time comparison helper are both `agents.rs`'s. Do not define a
  second of either — that module's doc comment states why the mapping lives in one place.

**The code store's write side is 04-06's** and its doc comment already records the requirement this
plan depends on: redemption must remove and return in one operation, because a read-then-remove pair
would let two concurrent exchanges both find the same code. Read that comment before writing the
redemption path; it is the contract between the two plans.

**What 04-06 already refused, so this plan is the second gate rather than the first.** The
authorization endpoint refuses an unknown client, a mismatched redirect URI, a challenge method
other than S256, a missing or malformed challenge, and a wrong resource parameter — all before a
panel is raised. A code therefore only exists if those held at minting. Re-checking the client and
redirect-URI binding at redemption is not redundant: the code travelled through a redirect the
attacker in T-5's scenario may have intercepted, and the binding is what makes an intercepted code
useless without the verifier. Say so in the comment, so a later reader does not "simplify" the second
check away as duplication.

**The response helpers, the canonical resource identifier function and the digest-prefix logging
helper** all exist in `oauth.rs` from 04-05. Reuse them; the 400/401/403 shapes are written once and
the logging helper is the only way a log line on this path may identify a token.

**Panic-freedom is a requirement, not a style note** (`04-RESEARCH.md` C-4): a token request body is
attacker input, `app.rs` contains zero `unwrap()`, and this module must match. Every parse degrades
to an OAuth error response.

**Grant types.** Only the authorization-code and refresh-token grants are implemented, which is what
04-06's metadata already declares. OAuth 2.1 removed the implicit and password grants entirely, so
there is nothing else to support and no arm to write for one.

**One scope** (`04-RESEARCH.md` C-11). `SECURITY.md` states that per-agent permission scoping is out
of scope by design. The scope field exists because the specification needs one and nothing branches
on it. Do not build a permission matrix here.

**Test timings.** 04-06 defined the consent durations as constants with a `TALARIA_TEST_HOOKS=1`-gated
shorten-only override, and its suite launches the shell with them set. This plan's suite section runs
in the same process and inherits them. The **code** lifetime is one of those constants too, which is
what lets this plan assert code expiry in seconds rather than a minute — state at the launch site
that the override shortens windows and answers nothing, and that every approval in the suite is still
a real click on the real control.
</interfaces>

    - Exchanging a code with the correct verifier, client and redirect URI returns an access token, a
      refresh token, the token type, the expiry and the scope.

      exchanges are concurrent — the successful one removed it in the operation that read it.
    - Exchanging a code whose lifetime has elapsed fails.
    - Exchanging a code with a wrong verifier fails, and the comparison does not short-circuit on the
      first differing byte.
    - Exchanging a code with a client id other than the one it was issued to fails.
    - Exchanging a code with a redirect URI other than the one it was issued for fails.
    - A code whose stored challenge method is anything other than S256 cannot be redeemed.
    - Exchanging a refresh token rotates it and returns a new pair; the client's next call with the
      new token succeeds.
    - Exchanging an already-consumed refresh token fails and the family is gone: the access token
      from that family stops resolving.
    - Exchanging an unknown refresh token fails with a response byte-identical to the reuse case.
    - A request with an unsupported grant type, a missing parameter, an unparseable body, or a body
      past the size cap produces an OAuth error response rather than a panic.
  </behavior>
  <action>
    Replace 04-06's token-endpoint stub with the real handler. Parse the request body as form-encoded
    parameters and branch on the grant type; anything other than the authorization-code and
    refresh-token grants is an unsupported-grant-type error. Both branches share the response
    builder, so a successful body is constructed in one place.

    **The authorization-code branch.** Redeem the code through the store's remove-and-return in a
    single operation — do not read it, validate, and then remove it, for the reason 04-06's own doc
    comment gives: two concurrent exchanges would both find it. Having removed it, validate what it
    carried: the client id matches the request's, the redirect URI matches the one the code was
    issued for, the stored challenge method is S256, and the code has not expired against the same
    clock it was stamped from. A failure at any of these still leaves the code consumed — that is
    correct and worth a comment, because a code that survived a failed redemption would be retryable
    by whoever intercepted it.

    Verify PKCE: hash the presented verifier with `agents.rs`'s digest helper and compare it to the
    stored challenge through `agents.rs`'s constant-time comparison helper. Do not write a new
    comparison and do not use the equality operator on the two strings. A comment stating the split
    plainly — the algorithm is three lines and entirely uninteresting; the danger is a comparison
    that returns early and a server that accepts the unsafe challenge method — and noting that the
    unsafe method was already refused at the authorization endpoint in 04-06, so this is the second
    gate and both exist on purpose.

    On success, call the store's `authorize` for this client and return the pair with the token type,
    the access token's lifetime in seconds and the scope. The refresh token is returned alongside it.

    **The refresh branch.** Hash the presented token, call the store's `rotate_refresh`, and
    translate its three outcomes: rotated returns the new pair, reuse-detected returns an
    invalid-grant error with the family already revoked by the store, and unknown returns the **same**
    invalid-grant error with the same body. A comment: the two failures are indistinguishable
    deliberately, because a caller that could tell a revoked family from an unknown token would have
    an oracle. Do not re-implement rotation or reuse detection here — 04-04 owns both, unit-tested,
    including the retry-is-not-reuse case.

    Every failure is an OAuth error response with the correct status, built from 04-05's helpers,
    never a panic. Log at most the client id and a digest prefix through the existing helper.

    Unit tests covering every line of `<behavior>`, with a pinned clock passed as a parameter, at the

    the rotation, the reuse revoking the family, the client rotating its current token successfully,
    the byte-identical unknown and reuse responses, the unsupported grant type, and the malformed

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an authorization code in transit → the token endpoint | The code travelled through a redirect another local process may have raced for; the endpoint is where the interception is made useless |
| a presented verifier → the stored challenge | A comparison that returns early on the first differing byte leaks the challenge one byte at a time |
| two concurrent exchanges → one code | Single-use is a concurrency property, not a bookkeeping one |
| a presented refresh token → the token family | Reuse detection must separate a stolen replay from a legitimate retry, and both look similar from one call |
| the token endpoint's failure modes → an unauthenticated caller | Distinguishable failures make the endpoint an oracle for which tokens and families exist |
