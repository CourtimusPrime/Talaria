<objective>
Make the endpoint protected, and make it **findable**. This is the resource-server half of AUTH-01:
the RFC 9728 protected-resource metadata document, the `WWW-Authenticate` challenge on 401 that
points at it, audience validation, and the live per-request token check that everything after this
depends on.

Purpose: `04-RESEARCH.md`'s Pitfall 3 is the failure this plan exists to prevent — tokens that mint
and validate while no metadata document exists and 401s carry no challenge, so a real MCP client
cannot *find* the authorization server and gives up before the flow starts. The roadmap's original
Success Criterion 2 permitted exactly that plan, which is why it was reworded during planning to
name the four requirements it was hiding. Two of the four land here: discovery and audience binding.
Building the resource server **before** the authorization server is deliberate — it makes the
discovery path provably first, and it means the end-to-end suite can start from the MCP endpoint URL
and nothing else, which is what a real client has.

This is also the plan where SC 1 becomes provable. 04-03 shipped a transport that refused
everything; here a token exists to present. The suite seeds `agents.json` with a client and a token
digest before launching the shell — the same seed-the-store-before-launch technique
`history_test.py` and `bookmarks_test.py` use — and then drives `tools/list` over HTTP and over
stdio and compares them. That is not a bypass: a pre-existing authorization record is exactly what
a prior approval looks like on disk, and no environment variable, hook, or code path grants access.

Output: `crates/talaria-shell/src/oauth.rs` with `TalariaAuth`, the real provider wired into
`http.rs` in place of 04-03's interim one, `tests/e2e/oauth_flow_test.py`'s discovery half, and the
`SECURITY.md` rewrite this phase has owed since 04-03.
</objective>

and whether it constructs a `WWW-Authenticate` challenge itself and what it puts in it. Write

**The trait, as `04-RESEARCH.md` Pattern 2 quotes it** — the methods this plan implements or
deliberately leaves at their defaults:

- `verify_token(String) -> Result<AuthInfo, AuthenticationError>` — a lookup hook, which is exactly
  what an opaque token wants;
- `required_scopes()` — one scope (`04-RESEARCH.md` C-11: `SECURITY.md` states per-agent permission
  scoping is out of scope by design; do not build a permission matrix);
- `auth_endpoints()` — this plan declares **only** the protected-resource metadata endpoint. 04-06
  adds the authorization-server ones. An endpoint declared but unimplemented is a 500 waiting to
  happen, and the introspection endpoint is never declared at all, because the authorization server
  and the resource server are the same process and there is nothing to introspect across;
- `handle_request(...)` — dispatch to the one handler this plan has;
- `protected_resource_metadata_url()` — the absolute URL that goes into the challenge.

`AuthInfo` carries `token_unique_id`, `client_id`, `user_id`, `scopes`, `expires_at` and `audience`
— which is the shape `agents.rs`'s `TokenRecord` already returns, and a sign the trait was designed
for this.

**What the specification makes mandatory here** (`04-RESEARCH.md`, "What the spec actually
requires"): implement RFC 9728 protected-resource metadata including the authorization-servers
field; advertise it via the `WWW-Authenticate` challenge on 401 or at a well-known URI; validate
that the token's audience is this server and reject anything else, never accepting or transiting a
token issued for another resource; and return 401 for invalid or expired, 403 for insufficient
scope, and 400 for malformed. That error table is normative.

**The store's contract** (`04-04-SUMMARY.md` and `crates/talaria-shell/src/agents.rs`):
`Agents::lookup(digest, now_ms)` is a live search returning a single `None` for unknown, expired and
wrong-kind alike, with a doc comment stating that a caller which memoises it has broken SC 3. This
plan is that caller. Do not add a cache "for performance" — the store is a `Vec` in memory and the
lookup is a scan of a handful of records.

**Reaching the store from the HTTP thread.** `Shared` is `Rc`-based and not `Send`, so the provider
cannot hold it. Give `TalariaAuth` its own `Arc<Mutex<Agents>>` — or the equivalent the observed API
supports — constructed once at startup and shared by clone with the main thread, so a revocation
applied from `apply_ui_actions` and a verification running on the HTTP thread see the same store.
Say in the doc comment that two independently-loaded `Agents` values would give the panel and the
verifier different answers, which is the bug this arrangement prevents. The main thread's access
must not block on the HTTP thread: keep every lock hold to a single operation with no `await`
inside it.

**Canonical resource identifier.** RFC 8707 audience validation needs one string that names this
server. Derive it from the address the listener actually bound — the same `Shared::remote` state
04-03 made the single source of truth — so it cannot disagree with the metadata document or with the
URL a client was given. Define it in one function with a doc comment stating that the value is
compared byte-for-byte and that a second construction site would be a way for a token to validate
against one spelling and not another.

**Panic-freedom is a requirement, not a style note** (`04-RESEARCH.md` C-4): a malformed
`Authorization` header is attacker input, `app.rs` contains zero `unwrap()`, and the new modules
must match. Every parse on the request path degrades to a status code.

**e2e seeding.** `harness.write_config()` and `harness.free_port()` landed in 04-03. This plan adds
a helper that writes an `agents.json` with a known client and a known token digest before
`start_shell` — the digest is computed in Python with `hashlib.sha256`, so the suite and the shell
agree on the mapping without the shell exposing anything. Put it in `harness.py`: 04-07's suite
needs it too, which is the same "two suites need it, so it lives in the harness" reasoning that put
`chrome_rects` there.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a presented bearer token → the browser's whole tool surface | The token is the entire boundary on this transport; there is no second factor and no peer credential to fall back on |
| a token issued by anyone, for anything → this resource server | Without an audience check, a token minted for another service and presented here would be accepted, making Talaria a confused deputy |
| the 401 response → an attacker enumerating tokens | Distinguishable failure modes turn the endpoint into an oracle for which tokens exist |
| the `talaria-http` thread → the shared token store | The verifier and the chrome's revoke action mutate and read one store from two threads |
| log output → token material | A log line is a durable artifact readable by anything that can read the log |
