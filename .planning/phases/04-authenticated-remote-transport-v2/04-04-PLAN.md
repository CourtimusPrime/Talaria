<objective>
Build the store the whole authorization half of this phase rests on: a client registry and a hashed
opaque-token store, following the Phase 3 store pattern exactly, with unit tests at `vault.rs`
density. **No HTTP in this plan** — every security property here is a pure function or a file write,
which is precisely why it can be tested without a browser and why it is worth having before the
endpoints that call it exist.

Purpose: `04-RESEARCH.md` Q3 settles the format and storage questions, and the answers are all
security-load-bearing. Tokens are opaque random values rather than JWTs, because SC 3 requires
revocation to bite on the *next request* — a self-contained token cannot be revoked without a
denylist lookup, at which point you have paid for the token format and still do the lookup — and
because the authorization server and the resource server are the same process, so there are no
verification keys to distribute, which is the only thing JWTs are genuinely good at. Storing only
digests is what lets this file be plaintext at `0600` instead of encrypted: a stolen `agents.json`
yields hashes, not credentials.

Keeping it out of the vault is deliberate twice over. The vault holds the human's passwords under a
keychain-derived key and has a documented startup hang on machines with no session D-Bus, tracked in
`STATE.md` as a candidate v1 blocker; coupling agent authorization to that failure mode would make
"no D-Bus" mean "no agent can connect." And `cookies_read` reaches the vault from the agent tool
surface — tokens must not live behind a door an agent already holds a key to.

This plan also carries the phase's four `AUTH-02` edge probes and one of its two `AUTH-01` probes,
because all five are answerable here as unit tests rather than as end-to-end guesses: the empty
store, two clients sharing a name, two clients authorized in the same millisecond, revoking an
already-revoked client, and two refreshes interleaving on one token family.

Output: `crates/talaria-shell/src/agents.rs` and its module declaration. Nothing else in the shell
references it yet — 04-05 wires lookup, 04-06 wires minting and rotation, 04-07 wires revocation.
</objective>

  <behavior>
    - Minting produces a raw token and stores only its digest; two mints never collide and neither
      is derivable from a clock.
    - Looking up the digest of a live, unexpired token returns its record; looking up the digest of
      an expired one does not, and neither does looking up an unknown digest — the two failures are
      indistinguishable to the caller.
    - Looking up a token whose record was removed a moment ago does not find it: the lookup reads
      the current list, with nothing cached across calls.
    - Registering a client mints a `client_id` the caller did not choose; registering with a name
      that is already in use produces a second, distinct client rather than replacing the first.
    - Registration is capped: past the cap, a new registration is refused rather than evicting an
      existing client, and a refusal is reported to the caller rather than logged and swallowed.
    - Rotating a refresh token invalidates the presented token and issues a new pair in the same
      family; the client's own next call with the *new* token succeeds.
    - Presenting a refresh token that was already consumed revokes the entire family, and the
      client's still-live access token from that family stops working.
    - A client retrying with its current, unconsumed refresh token is not treated as reuse.
    - Revoking a client removes its registration and every token in its family, returns that
      something changed, and persists once.
    - Revoking a client that is not present returns that nothing changed and writes nothing.
    - An empty store answers every one of these without a special case.
    - Clients are reported in a defined, stable order that does not depend on two authorization
      timestamps differing.

    Add the operations. All of them mutate in memory and then `save()` once, matching the store
    conventions; none of them takes a raw token as a stored value.

    `fn digest_of(token: &str) -> String` — lowercase hex SHA-256, a private helper with a doc
    comment saying this is the only place the mapping is defined so the minting and lookup paths
    cannot drift.

    `pub fn mint(...) -> (String, TokenRecord)` or an equivalent returning the raw token to the
    caller exactly once and retaining only the record. 32 bytes from `rand::rngs::OsRng`, encoded
    URL-safe so the value is header- and query-clean. `hex` is already a dependency if a hex
    encoding is preferred for the digest; the token itself should be base64url so it stays compact.
    Doc comment: never a time-seeded or user-space PRNG, and never derived from any client-supplied
    value — the vault's precedent is right there.

    `pub fn lookup(&self, digest: &str, now_ms: u64) -> Option<&TokenRecord>` — a live search of the
    current list, filtered by kind and by expiry. Doc comment: this is what makes revocation land on
    the next request, so **nothing** may cache the digest-to-identity mapping past the request
    boundary; a caller that memoises it has broken SC 3, and the fix is here rather than there. Also
    note that the failure is a single `None` for unknown, expired and wrong-kind alike, because a
    caller that could tell them apart is an oracle.

    Comparison of digests must be constant-time. Do not hand-roll a comparison loop that returns
    early; use a byte-wise accumulate-and-compare helper with a doc comment saying why the obvious
    early return is wrong here. This is the one place in this file where the readable version is
    the insecure one, so it deserves the comment.

    constant with a doc comment giving both halves of T-11's mitigation: the cap bounds the file, and

    amount of disk and buys them nothing.

    `pub fn authorize(&mut self, client_id: &str, ...) -> Option<(String, String)>` — marks the

    long-lived. Take both lifetimes as parameters with named constants for the defaults rather than
    burying literals, and note in the doc comment that the values are conventional defaults, not
    specification requirements (`04-RESEARCH.md` assumption A5).

    `pub fn rotate_refresh(&mut self, digest: &str, now_ms: u64) -> RefreshOutcome` where the
    outcome distinguishes three cases explicitly: rotated, with the new raw pair; **reuse detected**,
    with the family revoked as a side effect; and unknown or expired. Doc comment carrying the
    reasoning: rotation on every use is required for public clients, and reuse detection — presenting
    an already-consumed refresh token revokes the whole family — is the standard mitigation and is
    cheap when the store is local. State the distinction the AUTH-01 concurrency probe turns on: a
    client legitimately *retrying with its current token* has presented a token that is still live,
    which rotates normally; only a token this store has already consumed triggers the family
    revocation. Implement it that way — mark-consumed-then-issue in one mutation, so two interleaved
    rotations of the same digest cannot both succeed, and the second is unambiguously reuse.

    `pub fn revoke_family(&mut self, family_id: &str) -> bool` — the same shape, tokens only, used by

    Ordering: `clients()` returns records in insertion order, and any display-side ordering is the

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `agents.json` on disk → other local user accounts | A plaintext file in the user's config directory; the mode is the whole boundary |
| the token store → the agent tool surface | The vault is reachable from `cookies_read`; this store deliberately is not reachable from anything an agent can call |
| a corrupt store file → the authorization decision | The degrade path decides what a damaged file means, and one of the two possible answers admits everybody |
| a presented refresh token → the token family | Reuse detection has to separate a stolen replay from a legitimate retry, and both look similar from one call |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15 | Elevation of Privilege | a corrupt `agents.json` failing open and admitting every token | high | mitigate | The degrade path yields an **empty client set**, and the code is shaped so the alternative is not writable: `lookup` searches a list, an empty list finds nothing, and there is no store-is-empty branch. Unit-tested in Task 1 against an unparseable file, and again in Task 2's empty-store probe, which asserts every operation against a store with no clients |
| T-8 | Information Disclosure | `agents.json` readable by other local users | medium | mitigate | Only SHA-256 digests are stored — a stolen file yields no credential, which is the argument that lets this store skip encryption. The file lands at `0600` via `permissions::write_owner_only` on the staged sibling, in a `0700` directory via `create_dir_owner_only`, both asserted by `permissions::mode_of` in Task 1's tests. A round-trip test asserts no raw token appears in the written bytes |
| T-9 | Spoofing | a stolen refresh token replayed after the legitimate client rotated | medium | mitigate | Rotation on every use plus reuse detection revoking the whole family, implemented as mark-consumed-then-issue in one mutation so two interleaved rotations of one digest cannot both succeed. Task 2's concurrency probe asserts rotated-then-reuse, that the family's access token stops resolving, and — the false-positive half — that a client rotating its current token is not caught |
| T-11 | Denial of Service | unbounded registration filling the client registry | medium | mitigate | Two halves, both in the store: registrations are capped and a registration past the cap is refused rather than evicting an existing client, so flooding cannot displace a legitimate one; and an unapproved registration is inert — it holds no tokens and appears in no list — so the flood buys nothing even below the cap |
| T-04-04-01 | Elevation of Privilege | coupling agent authorization to the credential vault, so the known `Vault::load()` D-Bus startup hang becomes "no agent can connect", or so `cookies_read` reaches token material | high | mitigate | Structural separation: this module never imports the keychain crate or the cipher crate, asserted by two source criteria returning 0, and it is reached from no `talaria_protocol` variant and no MCP tool. The reasoning is in the module header so a later "reuse the vault, it is right there" refactor has to delete a stated rationale |
| T-04-04-02 | Information Disclosure | a timing side channel in digest comparison | medium | mitigate | Constant-time byte-wise comparison with a doc comment stating why the obvious early return is wrong, at the one place the mapping is checked |
| T-04-04-03 | Spoofing | token material predictable from a clock or a user-space PRNG | high | mitigate | 32 bytes from the operating system's random source, the same source `vault.rs` uses for keys and nonces; a source criterion asserts the module contains no clock type at all, since every time value is a parameter — which also makes the tests deterministic |
| T-04-04-SC | Tampering | package installs | n/a | accept | No dependency change; `sha2` and everything else this file uses landed in 04-02 with its Package Legitimacy Audit recorded there. `git diff` on the manifests is empty for this plan |
