# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This is not a web project.** Talaria's chrome is Rust + egui 0.34.3 drawn immediate-mode into
> Servo's GL context (`crates/talaria-shell/src/gui.rs`). No DOM, no CSS, no stylesheet, no box
> model, no media queries, no component registry. Every field below is expressed in egui's own
> vocabulary — `Style`/`Visuals`, `TextStyle`, `Color32`, `Frame`, `Margin`, `CentralPanel`,
> `ScrollArea`, `RichText`, `UiAction`, `egui-phosphor` glyphs. Where a template row has no
> meaningful analog in an immediate-mode native GUI, that is stated in one line rather than
> answered with a web invention.
>
> **This spec extends `03-UI-SPEC.md`; it does not restate or replace it.** Phase 3 fixed the
> spacing scale, the three text roles, the colour contract, the accent reserved-list, the
> `ChromePanel` mechanism, the `UiAction` round trip, and the two-step arm-then-confirm control.
> Values already fixed there are **referenced**, not re-derived. Everything this phase *adds* to
> the system is called out under **What this phase adds to the design system** below, so a reader
> can see the delta without diffing two documents.
>
> **`04-CONTEXT.md` exists** and locks four decisions (D-04-01 … D-04-04). D-04-04 — listener off
> by default, loopback-only — is the one that drives this spec. `04-CONTEXT.md` explicitly routed
> three open questions here: the consent screen's location, whether the AUTH-02 panel lists
> sessions or clients, and (by implication of D-04-04) how the user turns the listener on. All
> three are answered below. This run is `--auto`; genuinely discretionary calls are logged in
> **Open Questions / Assumptions** rather than silently decided.

## What This Phase Adds to the Design System

Everything else is inherited from `03-UI-SPEC.md` unchanged.

| Addition | What | Justification |
|----------|------|---------------|
| Two `ChromePanel` variants | `Access` (persistent, toolbar-toggled) and `Consent` (transient, event-raised, **not** user-openable) | Sixth and seventh instances of a mechanism that already has five. `Consent` is the first non-user-openable variant, and the first with a *refused* `SetPanel` path — it is raised only by `Gui::raise_consent`, so T-3's "no control can reach Approve" is a code property rather than a convention. See Panel Taxonomy. |
| Four `UiAction` variants | `SetRemoteAccess(bool)`, `ApproveConsent(u64)`, `DenyConsent(u64)`, `RevokeClient(String)` | The established intent round trip. None of them mutate `Shared` from an egui closure. |
| One new `Frame` treatment | The consent screen's **untrusted-claim block**: `Frame::new().fill(ui.visuals().faint_bg_color).stroke(ui.visuals().widgets.noninteractive.bg_stroke).inner_margin(egui::Margin::same(8))` | Required by T-4: an attacker-chosen string must be visually fenced off from Talaria's own words. The codebase has `Frame::new().fill(...)` today (history/bookmark striping) but no inner margin or stroke; the margin value is the existing `sm` token (8.0), and the stroke is an existing `Visuals` field, not a new colour. This is the smallest addition that makes the fence visible. |
| One arm-then-confirm control keyed by identity | `confirm_revoke: Option<String>` (a `client_id`), not a `bool` and not an index | Phase 3's `confirm_clear_history: bool` governs a single control. A per-row confirm keyed by *row index* would move onto a different client if the list reorders between the arming click and the confirming one. Keying on `client_id` makes that impossible. |
| One new interaction primitive: the **arm delay** | The consent screen's `Approve` is `add_enabled(false)` for the first 1000 ms it is on screen | The consent panel is raised by an unauthenticated network peer, at a moment of that peer's choosing, over whatever the human was doing. Without the delay, a click already in flight can approve full browser control. Nothing in the existing chrome needed this because nothing in the existing chrome could appear uninvited. |
| **No new colours, and the accent reserved-list is NOT extended** | See Color | The Access toolbar button's `.selected()` state is already covered by the existing list entry "the active panel-toggle button". Listener state is signalled by **glyph and text**, never by accent. |
| **No new text roles, no new spacing tokens** | See Typography, Spacing | Body / Small / Heading and the 7-token f32 scale carry all five surfaces. |

## Spacing Scale

Inherited verbatim from `03-UI-SPEC.md` — the same 7-token f32 scale (4 / 8 / 16 / 24 / 32 / 48 /
64), fed to `ui.add_space(_)` and nothing else. **No `Style::spacing` override is introduced this
phase either**; egui 0.34.3's `item_spacing`, `button_padding` and panel frame margins stay
untouched, as they are today.

Tokens actually used by this phase's surfaces:

| Token | Value | Usage this phase |
|-------|-------|------------------|
| xs | 4.0 | Not used — no surface here needs a gap tighter than default `item_spacing` |
| sm | 8.0 | Gap between a panel's intro paragraph and its first control; the consent claim-block's `Frame` **inner margin** (the one new application of an existing token) |
| md | 16.0 | Section break: between the consent heading block and the claim block, between the claim block and the grant list, between the grant list and the button row; in the Access panel, between the status block and the client list |
| lg | 24.0 | Unused |
| xl / 2xl / 3xl | 32.0 / 48.0 / 64.0 | Unused |

Exceptions: none. Both new panels use `egui::CentralPanel::default()` with no custom panel
`Frame` or margin, identical to all five existing panels.

## Typography

Inherited verbatim from `03-UI-SPEC.md`. egui has **no font-weight axis** in this build (one
proportional family is registered), so the template's Weight column has no analog and the
Line Height column has none either — egui derives row height from font metrics and exposes no
settable ratio. No `Style::text_styles` override exists in this codebase and this phase adds none.

| Role | egui `TextStyle` | Size | Used this phase for |
|------|------------------|------|---------------------|
| Body | `TextStyle::Body` | 13.0pt (egui default) | Consent fact lines, the claimed name, the redirect host, each grant bullet, button labels, Access row primary labels, the listener status line |
| Label / secondary | `TextStyle::Small` | 9.0pt (egui default) | The `it calls itself` / `Talaria did not check this name` framing lines, the loopback warning, `client_id`, relative timestamps, the arm-delay hint, the listener caveat line |
| Heading | `TextStyle::Heading`, via `ui.heading(...)` | 18.0pt (egui default) | The two panel titles: `Authorize connection`, `Access` |
| Display | not applicable | — | egui's largest built-in style is Heading; a bespoke `FontId` for one screen would be the inconsistency |

**Rule for new code (unchanged from Phase 3):** call `ui.heading(...)`, plain `ui.label(...)`, and
`egui::RichText::new(text).small()`. Never construct a raw `egui::FontId` with a hand-picked size.

**Emphasis note specific to this phase:** `RichText::strong()` changes *colour*, not weight. The
consent screen must not rely on "bold" to distinguish Talaria's words from the client's claim,
because there is no bold — the distinction is carried by the fenced `Frame` and by the explicit
`Small` framing text. This is why the claim block exists at all.

## Color

Inherited verbatim from `03-UI-SPEC.md`. **No `ctx.set_visuals(...)` call exists anywhere in the
codebase and this phase adds none.** Every value below is read through `ui.visuals().<field>`;
hex is given only so a reviewer can eyeball it. Never write a `Color32` literal.

| Role | `egui::Visuals` field | Value | Usage this phase |
|------|------------------------|-------|------------------|
| Dominant (60%) | `panel_fill` / `window_fill` | `Color32::from_gray(27)` = `#1B1B1B` | Both new `CentralPanel`s inherit it by using `egui::CentralPanel::default()` |
| Secondary (30%) | `faint_bg_color` | additive luminance 5 | Alternating Access-list row fill (the striping pattern Phase 3 introduced), and the fill of the consent claim block |
| Accent (10%) | `selection.bg_fill` | `Color32::from_rgb(0, 92, 128)` = `#005C80` | **Only** the Access toolbar button's `.selected(access_open)` state — the same panel-toggle use Phase 3 already reserved accent for. **No new *class* of accent use is introduced** (see the note below the table on how the list is worded). |
| Destructive | `error_fg_color` | `Color32::from_rgb(255, 0, 0)` = `#FF0000` | **Text only, never an icon tint.** Exactly three uses: the armed label `Confirm — allow network connections?`, the armed label `Confirm revoke?`, and the listener bind-failure line. |
| Fence stroke | `widgets.noninteractive.bg_stroke` | theme default | The consent claim block's border. An existing `Visuals` field, not a new colour. |

Accent reserved for: the active Me/Agents view toggle, the active panel-toggle button (now
including Access), and the bookmark star when set. **Nothing else.**

**On inheritance, stated precisely rather than loosely:** this is not Phase 3's list verbatim. It
*generalizes* Phase 3's enumeration of four named toggle buttons into "the active panel-toggle
button" (so a sixth panel does not require an edit to be covered), **corrects a Phase 3 omission**
by naming the Me/Agents view toggle — the two `ui.selectable_label` calls in `gui.rs`'s
view-toggle block consume `selection.bg_fill`, so accent was already there and unlisted — and drops Phase 3's conditional
"selected rows, if a plan adds row selection", since no plan added it and this phase adds none.
**The class of uses is unchanged: accent means "this control is the active one" and nothing else.**
No surface in this phase paints accent anywhere Phase 3 would not have.

**Explicitly rejected:** using accent to signal "the listener is on". It was considered and turned
down for two reasons. Accent in this chrome means *this control is the active one*, and a listening
port is not a control state. And a colour-only signal for a security-relevant state fails anyone
who cannot distinguish it, and would silently break under a future light `Visuals`. The signal is
form — a different glyph plus a text port label — which survives both.

## Copywriting Contract

Voice inherited from Phase 3: short, sentence-case, no exclamation points, no filler, no
marketing. One addition specific to this phase: **on the consent screen, Talaria never speaks in
the client's voice and never repeats an attacker's string as a fact.** Every sentence is either
something Talaria knows, or is explicitly framed as something a stranger claimed.

### The consent screen (surfaces 1 and 2)

| Element | Copy |
|---------|------|
| Heading | `{PLUGS} Authorize connection` |
| Fact line (Body) | `Something connected to Talaria's remote access port is asking for full control of this browser.` |
| Claim block — framing line (Small, above the name) | `It calls itself:` |
| Claim block — the name (Body) | `"{sanitize_claim(truncate_chars(client_name, 48))}"` — always inside literal double quotes, always inside the fenced `Frame`, **never** in the heading and never as the grammatical subject of any sentence. `sanitize_claim` is `sanitize_for_display` plus the delimiter rule in Surface 2: a `"` inside the name becomes U+FFFD, so the name cannot close the quotes it is rendered inside |
| Claim block — disclaimer (Small, below the name) | `Talaria did not check this name. Any program on this computer can claim any name.` |
| Redirect line (Body) | `Sends you back to: {host}:{port}` — host and port parsed out of the validated `redirect_uri`, rendered through `sanitize_for_display`, `truncate_chars(_, 48)`; hover text is the full URI, same treatment. This is the spec **MUST** ("clearly display the redirect URI hostname"). |
| Loopback warning (Small, shown when the redirect host is a loopback literal) | `That address is a program on this computer, not a website. Talaria cannot tell you which one.` — the spec's SHOULD for loopback-only redirect URIs |
| Client id (Small) | `Client ID: {client_id}` — the one identifier the client did **not** choose for itself; the Access panel keys on it |
| Grant heading (Body) | `Approving lets it, until you revoke it:` |
| Grant bullets (Body, one `ui.label` each, prefixed `• `) | `open, close, and switch tabs` / `see the address and title of every tab, including your own` / `navigate any tab to any http or https address` / `run JavaScript in any page and read what it returns` / `take a picture of any tab` / `read the passwords and cookies you saved in this browser` / `download files into your downloads folder` |
| Grant footer (Small) | `There is no smaller amount of access to grant. Approve only something you started.` |
| Arm-delay hint (Small, shown only while `Approve` is disabled) | `Approve turns on in a moment, so a click meant for something else can't grant this.` |
| Primary CTA | Button label `Approve` — emits `UiAction::ApproveConsent(request_id)` |
| Secondary CTA | Button label `Deny` — emits `UiAction::DenyConsent(request_id)` |
| Expiry note (Small, under the button row) | `This request expires if you leave it unanswered.` — no countdown; see UI Considerations |
| Empty state | Not applicable — the panel only exists while a request is parked. Zero requests means the panel is not shown at all. |
| Error state | Not applicable — a malformed or unauthorized `/authorize` request is refused by the HTTP layer with an OAuth error **before** any panel is raised. The chrome never renders an invalid request; that is the point of validating in `/authorize` first. |

### The Access panel (surface 3)

| Element | Copy |
|---------|------|
| Heading | `{PLUGS} Access` (glyph `PLUGS_CONNECTED` when the listener is bound) |
| Intro (Body) | `Agents that can drive this browser from another program, and the switch that lets them reach it at all.` |
| Status — off (Body) | `Remote access is off.` |
| Status — off (Small) | `Agents can still connect the way they do today: a local MCP client, over Talaria's socket, running as you.` |
| Status — starting (Body) | `Starting…` |
| Status — on (Body) | `Remote access is on — listening on {bound_addr}.` — `{bound_addr}` is the address the listener **actually bound and reported back**, never the configured value |
| Status — on, caveat (Small) | `Anyone signed in to this computer can reach that address; the access token is the only thing stopping them. It is not reachable from other machines.` |
| Status — bind failed (Body, `error_fg_color`) | `Couldn't start remote access — {addr} is already in use.` Remote access stays off. |
| Enable CTA (off → on) | Button `Turn on remote access`; first click arms, relabelling the same button to `Confirm — allow network connections?` in `error_fg_color`; second click emits `UiAction::SetRemoteAccess(true)` |
| Disable CTA (on → off) | Button `Turn off remote access`, single click, no confirmation — emits `UiAction::SetRemoteAccess(false)`. The safe direction never needs ceremony. |
| Empty state | `Nothing authorized yet.` (extends Phase 3's `Nothing saved yet.` / `Nothing visited yet.` construction) |
| Empty state — next step (Small, shown only when the listener is on) | `Point an MCP client at {bound_addr}/mcp, then approve it here.` (echoes the existing `No agents connected — point an MCP client at talaria-mcp` line in the Agents tab view) |
| Row — primary (Body) | `"{sanitize_claim(truncate_chars(client_name, 48))}"` followed by a `Small` suffix `(as claimed)` — the same delimiter rule as the consent screen, since the row quotes the name the same way |
| Row — secondary (Small) | `{truncate_chars(client_id, 12)} · authorized {relative_time(authorized_at_ms, now)}` |
| Row — hover text | Full `client_id`, full sanitized claimed name, and the registered redirect URI, one per line |
| Row CTA — revoke | Button `Revoke`, hover text `Revoke this client's access`; first click arms **that row** (`confirm_revoke = Some(client_id)`), relabelling only that button to `Confirm revoke?` in `error_fg_color`; second click emits `UiAction::RevokeClient(client_id)` |
| Rows present, listener off (Small, above the list) | `Remote access is off, so none of these can connect right now.` |
| Error state — store load failure | **No user-facing copy.** A corrupt or unreadable `agents.json` degrades to an *empty client set* and `log::warn!`s, per C-5 and `vault.rs`'s precedent — never an empty allow. The panel simply shows the empty state. Do not add a banner; the rest of the app has none. |
| Error state — revoke failed | Not applicable — `RevokeClient` removes a row from an in-memory store and rewrites a local file. A failed write degrades and logs, exactly as every other Phase 3 store does. |

### The holding page (the HTML `/authorize` returns to the external browser)

Not egui, but it is a shipped surface and it is the one place in this phase where attacker-supplied
strings could reach HTML. The contract is deliberately austere.

| Element | Copy |
|---------|------|
| Title | `Talaria — approve this connection` |
| Body — pending | `Talaria is asking you to approve this connection. Switch to the Talaria window to answer.` |
| Body — approved | `Approved. You can close this tab.` (shown only in the instant before the redirect fires) |
| Body — denied | `Denied. Nothing was granted.` |
| Body — expired | `That request expired. Start it again from the program that opened this page.` |
| Contents rule | **The holding page renders no value taken from the request** — no `client_name`, no `state`, no `redirect_uri`, no `client_id`, no error detail. Static bytes per state, chosen by the request id's parked status. This removes the injection and phishing surface from that page entirely rather than escaping it. |
| Controls rule | **No control of any kind.** No form, no button, no link. No script at all — `default-src 'none'` forbids inline script, so 04-06 shipped a `<meta http-equiv="refresh">` instead, which is stricter than this table originally asked for. A page that cannot approve anything cannot be scripted into approving anything (T-3). |
| Headers | `Content-Type: text/html; charset=utf-8`, `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` |

### Destructive actions in this phase

| Action | Treatment |
|--------|-----------|
| Revoke a client | Two-step arm-then-confirm, in place, per row, keyed on `client_id`. Resets when the panel closes (`set_panel`). No modal — no `egui::Window` exists in this chrome and this is not the surface to introduce the first one. |
| Turn **on** remote access | Two-step arm-then-confirm, though it is not destructive in the delete sense. Justification: it is the click that opens a network port in a process holding a credential vault, and D-04-04 exists precisely because that click deserves weight. Reusing the established control costs one `bool` and introduces nothing new. |
| Turn **off** remote access | Immediate, one click. Confirming a move toward safety trains people to click through confirmations. |
| Deny a consent request | Immediate, one click. Same reasoning. |

## UI Considerations

Applicable state considerations resolved: 22 covered, 2 backstop, 0 unresolved (plus 7 dismissed with reasons).

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Access client list | ✅ covered | Zero authorized clients renders `Nothing authorized yet.`, plus the `Point an MCP client at {bound_addr}/mcp, then approve it here.` next-step line when the listener is on (see Copywriting Contract) |
| loading | Access status block | ✅ covered | Genuinely applicable here, unlike every Phase 3 surface: the bind happens off the main thread, so between `SetRemoteAccess(true)` and the listener's `AppEvent` reporting its bound address the status block reads `Starting…`. The panel calls `ctx.request_repaint_after(_)` while in this state so a reactive egui actually redraws when the event lands |
| loading | Access client list | ⛔ dismissed | `Agents::load()` runs synchronously at startup, the same call site and idiom as `Vault::load()` and the four Phase 3 stores. No async fetch, no spinner |
| error | Access status block | ✅ covered | A failed bind (port in use) renders the `error_fg_color` line naming the address, and remote access stays off — the UI never claims a listener that does not exist |
| error | Access client list | ✅ covered | A corrupt `agents.json` degrades to an empty client set with a `log::warn!` and no user-facing copy, matching the four Phase 3 stores exactly. Explicitly **never** an empty allow-list check (T-15) |
| populated | Access client list | ✅ covered | Newest-authorized first (the same display-side reversal History uses), striped rows, each row carrying the quoted claimed name plus `(as claimed)`, a `Small` `client_id`-and-age line, and a `Revoke` button |
| partial | Access client list | ✅ covered | A registered-but-never-approved client is **not** a row: registration alone is inert (T-11), and the list is of *authorized* clients. There is no half-authorized state to render |
| overflow | Access client list | ✅ covered | `egui::ScrollArea::vertical()` wraps the panel, the same container every list panel already uses |
| zero-one-many | Access client list | ✅ covered | No count label anywhere — the same deliberate sidestep of singular/plural copy Phase 3 made. Zero renders the empty state; one and many use the identical row layout |
| long-text | Access client list | ✅ covered | Claimed name `truncate_chars(_, 48)`, `client_id` `truncate_chars(_, 12)`, both through `sanitize_for_display`; the full values are in the row's hover text |
| long-text | Access status line | 🧪 backstop | `{bound_addr}` is short by construction (`127.0.0.1:PORT`), but the status line is a `ui.label` in a panel whose width follows the window, and a narrow window was not rendered against during this pass. Needs a held-out visual check at a small window size, or an e2e assertion that the status rect stays inside the panel |
| empty | Consent panel | ⛔ dismissed | The panel exists only while a request is parked; "no requests" means the panel is not shown. There is no zero-state to design |
| loading | Consent panel | ⛔ dismissed | Everything the panel renders arrives in the `AppEvent` that raised it. Nothing is fetched after it opens |
| error | Consent panel | ✅ covered | An invalid `/authorize` request (unknown client, mismatched redirect URI, `code_challenge_method` other than `S256`, wrong `resource`) is refused by the HTTP layer with an OAuth error **before** a panel is raised. The chrome is never asked to render an invalid request |
| populated | Consent panel | ✅ covered | Fact line, fenced untrusted-claim block, redirect host, client id, the seven-item grant list, then `Deny` / `Approve` |
| partial | Consent panel | ⛔ dismissed | A parked request is constructed only from a fully validated `/authorize`; every field the panel renders is present or the request was already refused |
| overflow | Consent panel | ✅ covered | Wrapped in `egui::ScrollArea::vertical()` like every other panel, so a short window cannot push the button row out of reach. The button row is the last thing in the scroll body, not pinned — pinning would be a new layout mechanism for one screen |
| zero-one-many | Consent panel | ✅ covered | **At most one consent request is ever on screen.** While one is pending, a second `/authorize` is answered `access_denied` immediately without raising anything. No queue, no stacking, no "2 of 3" copy — and a spam loop cannot bury the chrome |
| long-text | Consent panel — claimed name | ✅ covered | `truncate_chars(_, 48)` then `sanitize_claim` (which is `sanitize_for_display` plus the delimiter rule — see Surface 2), rendered inside quotes inside the fenced `Frame`. A 10 KB `client_name` cannot push the buttons off screen, cannot escape the fence, and cannot close the quotes it is rendered inside |
| long-text | Consent panel — redirect URI | ✅ covered | Host and port only in the visible line, `truncate_chars(_, 48)` + `sanitize_for_display`; full URI in hover text under the same treatment |
| timeout | Consent panel | ✅ covered | A parked request expires after 120 s unanswered: the panel closes to `ChromePanel::None`, the HTTP side answers `access_denied`, nothing is granted, **and the post-resolution cooldown starts — expiry is a terminal resolution like any other, and it arms the cooldown exactly as Deny does.** Expiry's cooldown is the longer of the two (30 s, against Deny's 10 s): an unanswered request means nobody is at the keyboard to answer the next one either, so re-raising immediately can only hold the page off screen. No countdown is displayed — a visible timer pressures a security decision — but the `This request expires if you leave it unanswered.` line means the disappearance is not a surprise |
| interruption | Consent panel over an open panel | ✅ covered | A consent request calls `Gui::raise_consent(request)` (never `SetPanel` — see Panel Taxonomy), replacing whatever panel was open. `set_panel` clears `revealed_entry` (a revealed password never survives — good), and does **not** clear the credentials draft fields (a half-typed credential survives the interruption — also good). Both are existing behaviour, verified in `Gui::set_panel`, and neither needs changing |
| attention | Consent panel while Talaria is not focused | ✅ covered | The flow starts in an **external** browser (RFC 8252), so the human is by definition looking elsewhere when consent is raised. Talaria calls `Window::request_user_attention(Some(UserAttentionType::Informational))`. It deliberately does **not** call `focus_window()`: stealing focus toward a screen whose primary button grants full browser control is the opposite of the arm delay |
| stray-click | Consent panel `Approve` | ✅ covered | `Approve` is `add_enabled(false)` for the first 1000 ms after the panel is raised, measured from the request's `raised_at_ms` on `Shared` (so no timing state lives on `Gui`), with `ctx.request_repaint_after(_)` scheduling the frame that enables it. `Deny` is enabled immediately |
| harassment | Repeated consent requests | ✅ covered | Two caps, both cheap. **One:** only one request on screen at a time (above). **Two:** a global cooldown after **every terminal resolution — Deny (10 s) and expiry (30 s) alike** — during which `/authorize` returns `access_denied` without raising a panel. Scoping the cooldown to Deny alone would leave the expiry path uncovered: a peer could raise a request, wait out a user who simply ignores it, and re-raise the instant it expired, holding the displayed page off screen indefinitely through the `chrome_replaces_page` gate. Because the cooldown covers all three exits, an unauthenticated local peer cannot repaint the chrome faster than the human can browse. (Approve needs no cooldown — the client that just got a token has no reason to ask again, and if it does, the one-on-screen cap still applies.) |
| empty | Toolbar listener indicator | ⛔ dismissed | The indicator has exactly two states (bound / not bound) and both are rendered; "empty" has no meaning for a two-state glyph |
| populated | Toolbar listener indicator | ✅ covered | `PLUGS` when off, `PLUGS_CONNECTED` plus a `Small` `:{port}` label when bound, with state-specific hover text. Always visible because the toolbar always is |
| long-text | Toolbar listener indicator | ⛔ dismissed | The label is a port number — at most `:65535`. Bounded by the type |
| error | Holding page | ✅ covered | Four static bodies (pending / approved / denied / expired), none of which carries any value from the request |
| long-text | Holding page | ⛔ dismissed | Every byte of the page is a compile-time constant. No attacker-supplied string reaches it, so there is nothing to truncate |
| a11y-color | Listener state signal | 🧪 backstop | The on/off distinction is carried by glyph shape plus a text label rather than by colour, which is the design intent. Whether `PLUGS` and `PLUGS_CONNECTED` are actually distinguishable at toolbar size was not rendered during this pass; needs an eyes-on check, and the `: {port}` label is the fallback that makes the state unambiguous regardless |

## Surface Contracts

The five surfaces this phase introduces, each stated as a contract the executor can build from and
the auditor can check against.

### 1. Consent decision — `ChromePanel::Consent`, native chrome only

**Where it lives, and why that is not a choice.** `04-RESEARCH.md`'s T-3 (High) is decisive: `http`
is in the agent navigation allowlist, so an agent holding `evaluate` can open
`http://127.0.0.1:PORT/authorize` in a tab it owns and script anything on that page. A page-hosted
Approve button is therefore clickable by the exact party requesting permission. The Approve control
lives **only** in native egui chrome, where page JavaScript, `evaluate`, and the control socket all
structurally cannot reach it — the same property that keeps `chrome_rects` off the MCP tool surface
and keeps autofill *suggesting* rather than injecting. The HTTP endpoint serves a holding page with
no controls at all (see Copywriting Contract).

This resolves `04-CONTEXT.md`'s "Still open — consent screen location" in favour of a chrome panel.
A system dialog was considered and rejected: no modal or secondary window exists anywhere in this
chrome, egui-on-winit would need a second window and a second GL surface, and it would buy nothing
the panel does not already have.

**Behaviour contract:**

- Raised only by `AppEvent` from the `talaria-http` thread, carrying a `ConsentRequest { id,
  client_id, client_name, redirect_uri, raised_at_ms }`, through a dedicated
  `Gui::raise_consent(request)` constructor — **not** through `Gui::set_panel`. The egui closure
  never raises it either way.
- **Not user-openable, and that is enforced rather than observed.** `apply_ui_actions` **rejects
  `UiAction::SetPanel(ChromePanel::Consent)` outright** (drop it and `log::warn!`; it can only mean
  a bug), and `Gui::set_panel` refuses the variant for the same reason. Adding `Consent` to the enum
  makes `SetPanel(Consent)` *representable*, and "no control constructs it" would otherwise be an
  invariant every future panel button has to maintain by discipline. With the refusal in place, "no
  control can open the Approve button" is a property a reviewer confirms in one place — the same
  move that makes `OpenDownload`'s single call site checkable. The only `UiAction`s the panel emits
  are `ApproveConsent(id)` and `DenyConsent(id)`, both carrying the parked request id and **never**
  a code, token, or verifier.
- **No Escape binding.** Phase 3 fixed "no Escape-to-close" for panels and this phase keeps it. The
  panel resolves in exactly three ways: Approve, Deny, or the 120 s expiry. Since the panel has no
  toolbar toggle, this also means it cannot be dismissed into an ambiguous state.
- Approve arm delay: 1000 ms, from `raised_at_ms`. Deny is live immediately.
- On resolution the panel returns to `ChromePanel::None` — it does **not** restore whatever panel
  was open before, because panel state is a single enum and inventing a restore stack for one
  screen would be new machinery for no benefit.
- Rect names under `TALARIA_TEST_HOOKS=1`: `consent.approve`, `consent.deny` — matching the names
  `04-RESEARCH.md` Q6 already anticipated, so the e2e suite drives the real human path.

**Accepted tradeoff, stated rather than hidden:** with `TALARIA_TEST_HOOKS=1`, `chrome_rects` +
`click_rect` *can* reach `consent.approve`. That is precisely what lets the e2e suite exercise the
real decision path, which is what makes an `TALARIA_AUTO_APPROVE=1` bypass unnecessary — and a
one-variable authentication bypass in a process holding a credential vault is the thing worth
avoiding most. `panel_click_test.py:467` already pins that `chrome_rects` is refused without the
hook; the new names extend that assertion rather than weakening it.

### 2. Consent content — presenting an attacker-chosen string

T-4 (High): `client_name` is whatever a DCR caller typed, and it is displayed at the exact moment
the human decides whether to hand over browser control. This is the most security-load-bearing copy
in the project. Four rules, all enforced in the rendering path:

1. **Sanitised and truncated at the boundary:** `sanitize_claim(truncate_chars(name, 48))`.
   `truncate_chars` — never `String::truncate`, which panics on a byte index inside a multibyte
   character. `sanitize_for_display` replaces control characters and the bidi overrides
   (U+202A–202E, U+2066–2069) with U+FFFD, so a name cannot take a second line or reorder the text
   around it.

   **`sanitize_claim` adds one rule `sanitize_for_display` does not have, and this phase needs it:
   the ASCII double quote `"` (U+0022) is also replaced with U+FFFD.** `sanitize_for_display` was
   written for filenames, where a quote is harmless; here the quote *is* the delimiter, so a
   `client_name` of `Talaria" verified by Talaria "` would otherwise render as
   `"Talaria" verified by Talaria ""` and read as Talaria's own words. U+FFFD rather than stripping,
   for `sanitize_for_display`'s own stated reason: a dropped character lets a name shorten silently
   into something else plausible, where the replacement character shows the human something was
   there. Curly quotes are left alone — they cannot forge an ASCII delimiter, and mangling ordinary
   punctuation in a legitimate name costs trust for nothing.

   The alternative — drop the quotes and let the fence carry the framing alone — was considered and
   rejected only because the quotes are nearly free once the delimiter is neutralised, and they keep
   the framing legible in the Access panel's single-line rows where the fence does not exist.
2. **Fenced, not inlined.** The name is rendered inside the one new `Frame` treatment (faint fill,
   noninteractive stroke, 8.0 inner margin), never in the heading, never in a running sentence.
   Talaria's own words are always outside the fence; the client's words are always inside it.
3. **Labelled as a claim, above and below.** `It calls itself:` precedes it; `Talaria did not check
   this name. Any program on this computer can claim any name.` follows it. Two labels rather than
   one because a single line above can be visually adopted as a heading for the fenced content.
4. **Paired with a fact Talaria actually knows.** The redirect URI host and port (a spec MUST),
   plus the loopback warning (a spec SHOULD), plus the `client_id` — the one identifier the client
   did not choose. The screen therefore reads as *"here is what a stranger says, and here is what
   Talaria can verify"*, which is the only honest framing available.

The precedent is direct: `03-04` refused to let a download's row lie about its own name, and
`DownloadEntry`'s comment records that the requesting session's label is "a string the agent wrote."
Same class of problem, same answer, one notch stricter because the stakes are higher.

### 3. Access panel — `ChromePanel::Access` (AUTH-02)

**Lists clients, not sessions**, resolving `04-CONTEXT.md`'s third open question in line with
`04-RESEARCH.md`'s recommendation. A row is one authorized `client_id` with a live token family.
Sessions come and go with every reconnect; the thing a human revokes is *the agent*, and the thing
that survives a restart is the client record.

**Named `Access`, not `Agents`** — `ViewMode::Agents` already exists and means "tabs an agent is
driving". Two things called Agents in one chrome is a bug waiting to be filed (`04-RESEARCH.md`
Pitfall 7).

- Panel body: status block (surface 4) → `add_space(16.0)` → client list, wrapped in
  `ScrollArea::vertical()`.
- Rows striped with `faint_bg_color` on odd rows, the Phase 3 pattern.
- **No "last used" column.** It would be genuinely useful and it is deliberately excluded: with the
  Phase 3 store pattern (whole-file atomic rewrite), a last-used timestamp makes every authenticated
  request a disk write. `authorized {relative_time}` costs nothing and answers the question that
  actually matters when revoking.
- Revoking removes the client's tokens **and** terminates its open streams (T-7). The UI shows no
  progress or confirmation for either — the row disappears, which is the whole feedback the rest of
  this chrome gives for a delete.
- Rect names: `toolbar.access`, `access.enable` / `access.confirm-enable` / `access.disable`,
  `access.row.N`, `access.revoke.N` / `access.confirm-revoke.N`. The two-state controls are named
  for the state they are in, exactly as `history.clear` / `history.confirm-clear` already are, so
  "the confirm armed" is observable rather than inferred.

**Toolbar placement and shortcut.** The Access button goes immediately after Settings and before
Credentials, inside the existing group — no third `ui.separator()` is added. It follows the same
`.selected(access_open)` toggle shape as every other panel button and stays enabled with no tab
open (it is not scoped to a page).

**No keyboard shortcut**, matching Settings. The `Ctrl+<char>` arm in `handle_browser_shortcut`
currently claims `l k h b j d t w r`; `a` is free but taking it would break `Ctrl+A` select-all
inside the location bar and the credential fields, and no cross-browser convention exists for a
"connected clients" keystroke. Toolbar-only is the consistent answer, and Phase 3 already set that
precedent for exactly this reason.

### 4. Listener enable control (D-04-04)

**Lives in the Access panel, not Settings.** Three reasons, in order of weight:

1. The Settings panel's own intro copy scopes it to the address bar's search engine and states
   *"Stored in plain text in config.json — no agent can read it or change it."* Hanging an unrelated
   security-critical switch off that paragraph means rewriting it to cover two things it has no
   relationship between.
2. Settings commits through a single `Save` button carrying a `SearchEngine`. A toggle with
   different commit timing inside that form is the inconsistency; a toggle wired into that `Save`
   would make turning on a network listener a side effect of saving a search engine.
3. The Access panel needs the listener's status anyway. Putting the switch where the status and the
   consequences already live means one surface tells one story: *this is off, here is what turning
   it on means, here is who is currently allowed in.* The empty state can then teach instead of
   apologise.

**Storage is unchanged by this choice:** the flag persists in `config.json` through
`settings.rs`, so `04-RESEARCH.md` Q6's "seed `config.json` before launching the shell" test
approach still works exactly as written. Where the control is drawn and where the value is stored
are separate questions.

**The copy must not oversell or undersell.** Both directions are named explicitly:

- Not safer than it is: `Anyone signed in to this computer can reach that address; the access token
  is the only thing stopping them.` This is the Phase 2 delta made plain — `SO_PEERCRED` has no TCP
  equivalent, and loopback is not a boundary between local accounts.
- Not more remote than it is: `It is not reachable from other machines.` Phase 5 changes that; this
  phase must not let a reader believe it already has.
- The address shown is the address **actually bound**, reported back by the listener thread — never
  the configured value. This makes the UI correct under either resolution of `04-CONTEXT.md`'s
  still-open "fixed vs ephemeral port" question, which the transport plan decides.

### 5. Always-visible connection state

**Yes — recommended, and specified.** A browser quietly listening on a port is exactly the kind of
state a user should be able to notice without going looking for it.

The signal is the Access toolbar button itself:

| Listener | Glyph | Adjacent label | Hover text |
|----------|-------|----------------|------------|
| off | `PLUGS` | none | `Remote access: off` |
| bound | `PLUGS_CONNECTED` | `Small` `:{port}` | `Remote access: on — {bound_addr}` |

Rendered from the same live bound-address state the Access panel's status block reads, so the two
can never disagree. Deliberately **not** accent-coloured (see Color) — the signal is glyph shape
plus a text port label, which stays legible under any `Visuals` and does not widen a reserved list
that a Phase 3 visual review confirmed is closed.

## Panel Taxonomy (native-GUI equivalent of a component inventory)

Extends Phase 3's enum with two variants:

```rust
pub enum ChromePanel {
    None,
    Credentials,
    History,
    Bookmarks,
    Downloads,
    Settings,
    Access,   // NEW — persistent, toolbar-toggled, same rules as the five above
    Consent,  // NEW — transient, event-raised, NOT user-openable.
              //       Reachable ONLY via `Gui::raise_consent`; `SetPanel(Consent)`
              //       is refused by `apply_ui_actions` and by `set_panel`.
}
```

All Phase 3 panel rules carry over unchanged for `Access`: view state lives on `Gui` (never on
`Shared`); the toolbar button computes `if gui.panel() == Access { None } else { Access }` and
pushes `UiAction::SetPanel(_)`; the `chrome_replaces_page` gate hides and un-routes the displayed
webview; a panel stays open across a tab switch; no Escape binding; human-only, unreachable from
any `Command` or MCP tool.

`Consent` differs in exactly three ways, each deliberate:

| Property | `Access` and the five Phase 3 panels | `Consent` |
|----------|--------------------------------------|-----------|
| How it opens | User click or shortcut → `UiAction::SetPanel` → `Gui::set_panel` | `AppEvent` from the `talaria-http` thread → `Gui::raise_consent(request)` in `apply_ui_actions`. `SetPanel(Consent)` is **refused** by both `apply_ui_actions` and `set_panel` — the two entry points are disjoint by construction, not by convention |
| How it closes | Same toggle again | Approve, Deny, or 120 s expiry — never a toggle |
| Toolbar presence | A button, `.selected()` when open | None. It has no button, and therefore no accent |

**New `Gui` view-state fields**, all reset in `Gui::set_panel` alongside `revealed_entry` and
`confirm_clear_history`, for the same reason ("a half-pressed confirm cannot survive the panel
closing and be completed by a click the user meant for something else"):

```rust
confirm_enable_remote: bool,           // the listener's arm-then-confirm
confirm_revoke: Option<String>,        // which client_id's Revoke is armed
```

No timing state lives on `Gui`: the consent arm delay reads `raised_at_ms` off the parked request
on `Shared` and compares it to `crate::app::now_ms()`.

`Gui::raise_consent(request)` performs the same view-state reset `set_panel` does (so a revealed
password or a half-armed confirm cannot survive a consent interruption either) and then sets
`panel = ChromePanel::Consent`. Factoring the reset into a private helper both call is the
implementation's business; what this contract fixes is that the reset happens on **both** paths and
that `set_panel` is not one of them.

**New `UiAction` variants:**

```rust
/// Turn the loopback MCP listener on or off. Persists through `settings.rs`
/// and starts or gracefully stops the `talaria-http` thread. Emitted only by
/// the Access panel's own control — no `Command`, no MCP tool, and no
/// control-socket message reaches it, the same rule `OpenDownload` follows and
/// for the same reason.
SetRemoteAccess(bool),
/// Approve the parked authorization request with this id. Carries the id and
/// nothing else — no code, no token, no verifier ever crosses the chrome.
ApproveConsent(u64),
/// Refuse the parked authorization request with this id, and start the
/// post-resolution cooldown (10 s for a Deny).
///
/// The cooldown is a property of *resolving* a request, not of this variant:
/// the HTTP layer is equally obliged to start it (30 s) when a parked request
/// expires unanswered, which is a terminal resolution the chrome never emits
/// an action for. Arming it on Deny alone would leave the expiry path open —
/// see the `harassment` row in UI Considerations.
DenyConsent(u64),
/// Drop this client's registration and every token in its family, and
/// terminate its open streams. Emitted only by a row's second, confirming
/// click — never by the first.
RevokeClient(String),
```

## Open Questions / Assumptions

Logged per this run's `--auto` mode. Each is a genuinely discretionary call made on the project's
behalf, flagged so the planner or a human can override it cheaply.

1. **The listener switch is in the Access panel, not Settings.** Reasoned in Surface 4. The
   counter-argument — "settings belong in Settings" — is real, and the cheap mitigation if someone
   wants it is a one-line `Small` pointer in the Settings panel (`Remote access for agents is in the
   Access panel.`). Not specified here because a second mention of a security switch is clutter that
   earns its place only if a user actually fails to find the first one.

2. **Arm delay = 1000 ms.** A judgement call with no local precedent. Firefox's permission-prompt
   delay is the ancestor of the idea. Long enough that an in-flight click cannot land, short enough
   that a deliberate user does not notice. Cheap to change; nothing else depends on the value.

3. **Consent expiry = 120 s; post-resolution cooldown = 10 s after Deny and 30 s after expiry; one
   pending request at a time.** All of these are anti-harassment caps invented here, not derived
   from a spec. The two cooldown values could equally be one — 30 s for both is defensible and
   simpler; the split exists because a Deny is evidence the human *is* at the keyboard, and an
   expiry is evidence they are not. What is **not** discretionary is that a cooldown covers every
   terminal resolution: scoping it to Deny alone leaves an unauthenticated peer able to hold the
   page off screen forever through the expiry path. The authorization *code*
   lifetime (~60 s per `04-RESEARCH.md` Q3) is a separate, shorter clock that starts after approval.
   If the planner wants a single clock, 120 s for the parked request is the one to keep, because a
   human switching applications and reading seven grant bullets needs more than 60 s.

4. **No "last used" column in the Access panel.** Excluded because it would turn every
   authenticated request into a whole-file atomic rewrite. If a later phase moves the token store to
   an append log or accepts a debounced write, this becomes a cheap addition, not a redesign.

5. **The grant bullets claim seven capabilities and no exclusions.** They were written against the
   actual tool surface (`tabs_list`, `tabs_open`, `tabs_close`, `tabs_focus`, `navigate`,
   `evaluate`, `screenshot`, `cookies_read`, `download`). Note that `tabs_list` returns **all** tabs
   including the user's own, which is why the second bullet says so. No "it cannot…" line is
   included, deliberately: any exclusion this spec asserted would have to stay true across every
   later phase, and an outdated reassurance on a consent screen is worse than no reassurance. If the
   tool surface changes, these bullets change with it — that coupling is intentional and worth a
   note in whichever plan touches `tools.rs`.

6. **Turning the listener on takes effect immediately** (spawn the `talaria-http` thread from
   `apply_ui_actions`), rather than at next launch. This is what makes the `Starting…` /
   `bind failed` states in the status block meaningful. If the transport plan finds runtime spawn or
   graceful shutdown awkward, the fallback is a restart-required note in the status block — but say
   so there, because a switch that silently does nothing until relaunch is worse than one that
   admits it.

7. **Fixed vs ephemeral listener port stays open**, as `04-CONTEXT.md` left it. This spec is
   deliberately agnostic: every surface renders the address the listener actually bound and reported
   back, so either resolution works without a copy change.

8. **The holding page renders zero request-derived values.** This is stricter than escaping, and it
   costs one nicety: the page cannot say *which* connection it is about. Judged worth it — the page
   exists for the seconds between opening a browser and switching to Talaria, and the Talaria window
   carries the full detail.
