# Talaria

## What This Is

Talaria is an open-source, non-Chromium web browser, built on the Servo engine (via libservo),
designed for both human daily use and AI agents to drive directly through a built-in MCP server.
A single toggle switches the view between the user's own tabs ("Me") and tabs an agent is actively
driving ("Agents"), and the user can take over an agent's live session at any moment, click, scroll,
type, in the same session, not a handoff to a copy.

## Core Value

An agent can drive a real, already-logged-in browsing session, and a human can take over instantly
the moment it hits something only a human can clear (a login wall, a CAPTCHA, a Cloudflare
challenge), without either side sacrificing performance.

## Requirements

### Validated

<!-- Shipped and confirmed via the two overnight test-and-improve loops. -->

- Servo/libservo rendering engine boots, loads pages, and holds sessions reliably
- egui-on-winit shell (chrome UI) is functional, fast, and keyboard-navigable
- The Me/Agents toggle and live takeover work end-to-end (verified via `xdotool`, real click → real navigation)
- Session/profile state persists across restarts
- Core MCP tool surface (`tabs.*`, `navigate`, `evaluate` incl. async/Promises, `screenshot`) works, is fast (screenshot capture 4–36ms, well under the 30–60ms takeover target), and is hardened against malformed protocol input
- Multiple concurrent agent sessions are distinguishable in the Agents view
- Crash recovery (tab-level) and an e2e test harness (Xvfb-based) both work reliably

### Active

<!-- Current scope. Building toward these. -->

- [ ] Finish and land in-flight fixes: `window.open`/`target=_blank` popup support, `file://` scheme allowlist, heavy-JS page wedging `evaluate`
- [ ] Add a lock-file preflight so two autonomous loop sessions can't run against the same branch concurrently (a real incident from the 2026-08-16 loop)
- [ ] Build OAuth (self-hosted MCP authorization server via `rust-mcp-sdk`) — designed in detail, not yet implemented
- [ ] Build the local credential vault (encrypted-at-rest JSON, domain-matched) — designed, not yet implemented
- [ ] Table-stakes browsing: history, bookmarks, address-bar search, downloads UI
- [ ] Distributed mode: Tailscale client/server split, remote live-viewing/takeover over the designed WebSocket protocol
- [ ] Linux and Windows ports (macOS is current baseline)
- [ ] Release readiness: license files in-repo, a real update mechanism (see Key Decisions — the original plan is now stale), manual accessibility verification, landing page live

### Out of Scope

<!-- Explicit boundaries. Includes reasoning to prevent re-adding. -->

- Browser extensions (v1) — Servo's WebExtensions support is immature; revisit once it matures
- OS-level multi-window support (v1) — rests on a part of libservo's embedding API Servo's own tracker lists as still in progress
- Per-agent permission scoping, rate limiting, request-level audit trails — deliberate product philosophy: the browser is infrastructure, not a policy/safety layer
- Proactive rendering-correctness or visual-regression testing — treated as Servo's own responsibility (tracked via their own WPT suite); this is a visual-judgment problem, a poor fit for code-based validation, and the reactive backstop (live-viewing/takeover) already covers it
- Cloud sync/backup — credential vault and session state are deliberately plain local files, which already work with whatever backup tooling the user has
- Telemetry — none, by design, stated explicitly as a privacy stance

## Context

- Built as a direct reaction against Chromium's resource weight and against the fact that the
  entire current AI-agent browsing ecosystem (ego-lite, OpenBrowser, orion-browser, steel-browser,
  agent-browser) automates Chromium rather than replacing it. Talaria is the only project in this
  space betting on a genuinely different, non-Chromium engine.
- Two prior working names: "OpenBrowser"/"Obie" (dropped — collided with an existing, unrelated
  open-source project of the same name) and "Charon" (dropped in favor of the current name).
  "Talaria" (Hermes' winged sandals) was chosen for fitting the messenger/agent theme and the
  speed/lightness positioning more directly.
- Built by Claude Fable 5, working autonomously in structured overnight test-and-improve loops
  (branch-per-run, one commit per fix, hard iteration caps, judgment calls logged and escalated
  rather than decided autonomously).
- A real incident on 2026-08-16: two Claude Code sessions ran against the same branch
  simultaneously without either knowing about the other, causing a silent edit collision and an
  invalid soak-test result. Root-caused and recovered without data loss, but exposed a real gap in
  the original loop guardrails (no ownership lock), now queued as a required fix.
- Servo's own WPT (Web Platform Test) conformance was ~62% and climbing (from ~45% a year prior)
  as of the last check — accepted as a known, monitored cost rather than a blocker.

## Constraints

- **Tech Stack**: Rust throughout — Servo/libservo (rendering engine), egui + winit (shell chrome,
  corrected from an original Tauri+React plan), `rust-mcp-sdk` (MCP server + OAuth) — established
  through direct implementation, not just design
- **Performance**: screenshot capture must stay well under the ~30–60ms active-takeover latency
  target (currently measured at 4–36ms); startup-to-socket-ready ~21ms; page load ~219ms
- **Platform order**: macOS first, then Linux, then Windows — chosen because the performance goal
  centers on running well on Mac
- **Dependency risk**: Servo itself, and previously the experimental Servo-backed WRY integration,
  were accepted as not-fully-mature dependencies; the egui-on-winit shell decision removed the WRY
  dependency entirely, a larger risk reduction than the originally planned fallback
- **Licensing**: dual MIT OR Apache-2.0 (standard Rust ecosystem convention), compatible with
  Servo/SpiderMonkey's MPL 2.0 (file-level weak copyleft, doesn't force Talaria's own code into any
  particular license)

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Reject Chromium as the engine | Chromium is the incumbent this project exists to replace; the entire current agent-browsing ecosystem is Chromium-only | Adopted |
| Servo over Blitz/Ladybird | Servo ships a real, JIT'd JS engine (SpiderMonkey) already wired to its DOM; Blitz has none, Ladybird isn't embeddable yet | Adopted |
| Shell: Tauri + Servo-backed WRY, React chrome | Reuse from [[insomniac]]; React was a stated soft preference | Superseded — see next row |
| Shell: egui-on-winit | `tauri-runtime-verso` found dormant during the Servo-WRY readiness check; egui needs no webview at all, eliminating that dependency entirely rather than just falling back to a native one | Adopted — built, verified working |
| MCP surface: minimal, `evaluate`-centric, not typed click/type/wait tools | Independently validated by ego-lite (2.5× faster) and OpenBrowser (3.2–6× fewer tokens) benchmarks | Adopted, built, verified — including async/Promise support |
| OAuth via `rust-mcp-sdk`, self-hosted auth server | MCP servers are expected to be their own auth server; avoid hand-rolling OAuth | Adopted — not yet built |
| No gatekeeping / rate limiting / audit trail | Browser is infrastructure, not a policy layer — explicit product philosophy | Adopted |
| No budget for rendering-correctness testing | Servo's own WPT conformance is the correctness signal, not something code-based validation can meaningfully check; reactive backstop is takeover/live-viewing | Adopted |
| Naming: OpenBrowser → Charon → Talaria | OpenBrowser collided with an existing project; Talaria better fits the speed/messenger-agent theme | Adopted |
| Licensing: dual MIT OR Apache-2.0 | Standard Rust ecosystem convention; compatible with Servo/SpiderMonkey's MPL 2.0 | Adopted — not yet added to repo |
| Update mechanism: Tauri's updater plugin | Assumed under the original Tauri shell plan | **Stale — shell is no longer Tauri, no replacement chosen yet** |
| Overnight loops: branch-per-run, no ownership lock | Seemed sufficient at design time | **Insufficient — a real two-session collision occurred; lock-file preflight now required** |

# Roadmap: Talaria

## Overview

Talaria's foundation, a working Servo-based engine, a native egui-on-winit shell, live agent
takeover, and a fast, hardened MCP tool surface, is already built and verified through two overnight
autonomous development loops. What remains is closing a handful of active bugs and a process gap
(Phase 2), building the auth and credential layers that were designed but never implemented
(also Phase 2), making Talaria usable as an actual daily-driver browser (Phase 3), extending it to
work across two machines over Tailscale (Phase 4), porting it to Linux and Windows (Phase 5), and
shipping it (Phase 6). By the end of Phase 6, Talaria is a publicly released, cross-platform,
open-source browser that both humans and AI agents can use interchangeably in the same session.

## Phases

- [x] **Phase 1: Foundation & Core Engine** — A working single-machine browser: Servo rendering, egui shell, live agent takeover, and a fast, hardened MCP tool surface. **Complete.**
- [ ] **Phase 2: Stabilize & Close Current Gaps** — Finish in-flight fixes, add the loop-ownership safeguard, and build the OAuth and credential layers that were designed but never implemented.
- [ ] **Phase 3: Table-Stakes Browsing** — History, bookmarks, address-bar search, and a downloads UI, so Talaria works as a real daily driver.
- [ ] **Phase 4: Distributed Mode** — Client and server split across machines over Tailscale, with remote live-viewing and takeover.
- [ ] **Phase 5: Platform Expansion** — Linux, then Windows.
- [ ] **Phase 6: Release Readiness** — License files, a real update mechanism, manual accessibility verification, and a live landing page.
