# Talaria — Working Notes

*Living document. Update as decisions change.*

## Naming — DECIDED: Talaria (renamed from Charon, 2026-08-15)

**Current name: Talaria** — Hermes' winged sandals. Keeps the mythological naming pattern already used elsewhere ([[chronos]], [[hermes-agent]]/Mnemosyne) and fits the product even more directly than Charon did: winged sandals are the lightweight thing you *wear* to move fast — a clean metaphor for a lightning-fast browser that carries both the user and their agents across the web. Single name for project and app; binary is `talaria`, crates are `talaria-shell` / `talaria-protocol` / `talaria-mcp`.

**History:** "OpenBrowser"/"Obie" was ruled out first — it collides directly with an existing, active, open-source project at openbrowser.me (235 stars, MIT licensed, listed on the MCP registry as `me.openbrowser/openbrowser-ai`), which we ourselves researched and ruled out as a foundation. "Charon" (the Styx ferryman) was the interim replacement — collision-checked and workable — but was superseded by Talaria by decision on 2026-08-15, before any public release, so the rename cost nothing.

## Positioning

A lightweight, lightning-fast web browser for humans and agents.

## Core features (decided)

- **Distributed**: runs fully on one machine, or splits client and server across two machines connected via Tailscale.
- **100% local credentials**: stored on the user's machine, usable by the user's agents.
- **Built-in MCP server**: OAuth'ed, exposed to any agent, including Claude Desktop.
- **No profiles**: single user, but tabs split between "Me" (human-driven) and "Agents" (agent-driven). UI: a single toggle button in the top-left corner switches the whole view between the two, not a permanent split-screen.
- **Takeover interaction**: while viewing an agent's tab, the user sees exactly what the agent is doing (clicks, scrolls, what it's looking at) and can directly interact with that same session, click, scroll, type, to take over when needed (e.g. completing a Cloudflare challenge or signing in), then let the agent continue from there. This is the same session, not a handoff to a copy.
- **Multiple concurrent agents**: the "Agents" view (reached via the toggle) is a list of active agent sessions, each labeled by the connecting client's identity (reusing the per-client identity that OAuth already tracks — no separate concept needed). Selecting one shows and allows takeover of that specific session.
- **Single-window, multi-tab for v1**: no OS-level multi-window support. Servo's own embedding roadmap lists multi-window support as still in progress, and it isn't worth stacking a fourth not-fully-ready dependency on top of Servo itself, the experimental WRY backend, and the screenshot/offscreen APIs. Revisit on the same cadence as the Servo WRY readiness checklist.
- **Shared session state by design**: agents access the user's own cookies and credentials directly, no isolation layer, to make automating real logged-in tasks frictionless.
- **Real-time viewing**: watch agents run live. Polling rate is adaptive: ~200–500ms for passive supervisory viewing, ramped up (as fast as reasonably achievable, target ~30–60ms) specifically while a human is actively driving via takeover, since takeover requires precise, low-latency interaction (e.g. timing-sensitive Cloudflare challenges) that passive-viewing latency isn't built for.
- **Target platform order**: macOS first, then Linux, then Windows — chosen because the performance goal centers on running well on Mac.
- **Credential file encrypted at rest**: the JSON credential file is encrypted at rest (OS keychain-backed), not plaintext on disk. This doesn't conflict with the no-gatekeeping philosophy — that philosophy governs agent permissions and access, not basic hygiene for how a secret sits on disk. Cheap to add, no added complexity to the agent-facing model.
- **Credential vault's actual role clarified**: the JSON file is for autofill suggestion during human-driven moments (matching by domain), and for cookie-based session reuse by agents via `cookies.read`. It is explicitly *not* a tool agents use to perform fresh/interactive logins — that flow is handled by takeover (agent hits a login wall, human switches in via the toggle, signs in, agent resumes), not by an agent autonomously entering stored credentials. This was the implicit design all along (the Cloudflare example was framed as human takeover); stating it explicitly closes the gap between the credential decision and the MCP tool surface without adding new scope.

## Deferred

- **Tab volume control UX.** The backlog item — how a user sets and sees limits on how many tabs an agent (or a tab spawned by another tab) can open. Explicitly deferred, not being decided now.

## Product philosophy

The browser is infrastructure, not a policy or safety layer. It doesn't gatekeep, sandbox, or add agent protections on top of what a normal browser already does (e.g. closing a tab). Permissioning, approval flows, rate limiting, and audit trails are the responsibility of whatever the user or an agent framework builds on top, not the browser itself.

**Rendering correctness is explicitly not our budget.** Whether a given webpage renders correctly is Servo's responsibility, tracked continuously against the real Web Platform Test suite, and we inherit its improving trajectory automatically via dependency version bumps, not through anything we build or test ourselves. This is a visual-judgment problem, not a code-correctness problem, and it's a poor fit for Claude Code (or any code-focused validation) for that reason. We don't build a screenshot-diff or visual regression harness, and we don't maintain a list of known-broken sites. The reactive backstop is the already-decided real-time viewing/takeover feature: a human notices live if something looks wrong and works around it. Our own testing budget stays scoped to our own code — the Tauri shell, the MCP surface, credential matching, the distributed protocol — where correctness is logical and testable, not visual.

## Rendering engine — DECIDED: Servo (via libservo)

**Decision:** adopt Servo as the core rendering engine, embedded through libservo, with a custom-built shell written in-house (following the pattern of Servo's own `servoshell` reference implementation, and the approach the now-archived Verso project attempted).

**Why Servo over the alternatives:**

| | Servo (libservo) | Blitz (Stylo+Taffy+Parley) | Ladybird (LibWeb+LibJS) |
|---|---|---|---|
| JavaScript | Included — SpiderMonkey fork, real JIT | None — would require building the full DOM/JS bridge ourselves | Included, but currently JIT-less |
| Standards coverage | ~62% weighted WPT, climbing (45%→62% in a year) | Deliberately partial by design | Unproven, pre-alpha |
| Maintenance | Active, Linux Foundation Europe, 0.1.0 shipped April 2026 | Active, Dioxus Labs | Active, but public alpha not yet shipped |
| Embeddability | Purpose-built libservo API | Purpose-built, this is its whole reason to exist | Not designed for embedding — it's a whole browser |
| Fit for "lightweight" | Heavier than Blitz | Best fit, ~12MB | Unknown, still early |

Servo wins because it already solves the hard, invisible core of building a browser: JS execution wired into the DOM. Blitz is explicitly "a webview without JavaScript" — using it would mean bolting on a separate JS engine (Boa/QuickJS) *and* building the entire DOM/JS integration layer from scratch, on top of the CSS/layout work Blitz already carries. That's building two hard problems instead of adopting one solved one.

**Known cost accepted:** Servo's ~62% WPT conformance means real sites will render incorrectly in ways we won't know about until we hit them. This is a monitorable, known risk rather than an unknown one.

**Verso is dead** — archived, no longer maintained. It was the prior attempt at "build a real browser shell around Servo," and it couldn't keep pace with Servo's own revisions due to limited manpower/funding. Its useful contributions were merged back into Servo itself. Lesson: building the shell ourselves is the same task that sank Verso — worth taking seriously as a resourcing risk, not just a technical one.

**Ladybird** is the most ideologically clean non-Chromium option and worth revisiting once its public alpha and an embedding story exist (alpha targeted 2026, beta 2027, stable 2028 — not viable to build on today).

**Blitz's remaining role:** not the core browsing engine, but a candidate for fast, lightweight HTML/CSS rendering *within our own UI* where JS isn't needed — in-app docs, settings panels, etc.

## Automation / agent layer

- **vercel-labs/agent-browser** — chosen for built-in CLI and MCP support (typed tools, MCP-over-stdio, WebSocket live-viewport streaming already built in).
- **Known conflict with the Servo decision**: agent-browser drives browsers over the Chrome DevTools Protocol (auto-discovers a running Chrome instance via remote debugging). CDP is Chromium-specific, so agent-browser will **not** drive our Servo-based browser out of the box.
- **Custom automation binding layer — DEPRECATED.** Decided this is unnecessary added complexity. Not building a bespoke libservo automation surface.

## Reference prior art — philosophies/systems worth borrowing

- **citrolabs/ego-lite** — Chromium-based, rejected as a foundation for that reason, but the most mature and directly comparable product here (47 stars, active, macOS-shipping, Windows/Linux on its roadmap). Several things worth borrowing:
  - **"Code base, not CLI base."** Its core architectural bet is that agents should get capabilities wrapped as JavaScript functions they call directly in a single written snippet, rather than a "call a tool, look at the result, call another tool" loop. Their own benchmark against Vercel's agent-browser shows this finishing complex tasks up to 2.5× faster with far fewer tool calls and higher success rates. This directly validates the `evaluate`-centric MCP surface we already decided on — same bet, and now we have a concrete performance argument for it, not just a complexity-reduction one.
  - **Spaces model.** Each agent/task gets a fully isolated workspace; the human can see which Space has an agent running at any moment and take it over or stop it whenever. Our Me/Agents split already borrows the isolation idea, and the explicit *takeover* interaction (a human reaching into a running agent's session and driving it directly, e.g. completing a Cloudflare challenge, then letting the agent resume) is now a confirmed decision, see the toggle/takeover UI note above.
  - **Snapshot quality as a named hard problem.** They call out needing "kernel-level customization" specifically to handle deeply nested iframes reliably, since that's where naive snapshot/DOM-reading approaches break. Worth treating as a known risk area for our own `evaluate`/screenshot design against Servo rather than assuming it'll just work.
  - **One-question onboarding.** On first launch, it asks once whether to migrate Chrome data, then the agent inherits existing logins/cookies/bookmarks. Worth considering as an onboarding path for our own JSON credential file, an import step, rather than requiring a blank-slate start.

- **oneKn8/orion-browser** — Chromium fork with a built-in agent + MCP integration. Caveat up front: this is a very early, low-traction project (1 star, "Phase 1 — Foundation" on its own roadmap), so treat it as an architecture sketch, not validated prior art. Still, one pattern is worth noting: it cleanly separates the **browser controller** (tab management, navigation, DOM interaction, its own extension component) from the **agent brain** (LLM orchestration, workflows, a separate local server), communicating over local WebSocket/HTTP. That mirrors the separation we already have, our MCP tool surface is deliberately thin and mechanical, leaving orchestration to whatever agent framework connects to it. Its "Workflows" (visual graph builder for repeatable automations) and "Scheduled Tasks" (autopilot on a timer) are both plausible future backlog ideas, not decided now, but worth keeping in mind alongside ego-lite's "Skills" concept as the same underlying idea: distilling successful agent runs into reusable, repeatable units.

- **steel-dev/steel-browser** — heavier infra-style agent browser sandbox (7.1k stars, active, Apache 2.0). Its most useful pattern for us is the split between two distinct API shapes:
  - **Sessions** — stateful, resumable, full Puppeteer/Playwright/CDP control, for complex multi-step workflows.
  - **Quick Actions** (`/scrape`, `/screenshot`, `/pdf`) — stateless, one-shot, no session overhead, for simple read-only jobs.
  This is a clean precedent for how we could extend our own MCP surface later: keep `evaluate` and session-scoped tools for real interactive work, but add lightweight one-shot primitives for agents that just need a quick read, without spinning up a full tab session. Also worth noting as a deliberate non-goal: Steel ships built-in proxy rotation, stealth plugins, and fingerprint/anti-detection tooling for evading bot detection. That's a feature category we're consciously not replicating, our philosophy is real accounts and real sessions, not evasion, so this is useful as a boundary marker rather than something to adopt.

## Competitive check: does OpenBrowser (openbrowser.me) already do this?

**No.** OpenBrowser is a Python automation framework and MCP server that drives an existing Chromium-based browser via raw CDP — it auto-detects Chrome/Edge/Brave/Chromium and installs Chromium automatically if none is found. That's the exact incumbent this project is meant to replace, not an alternative to it. It has no native desktop app for a human to daily-drive alongside agents (it's headless-by-default automation, optionally paired with a hosted cloud dashboard), no Me/Agents shared-tab concept, and no local peer-to-peer Tailscale-style distributed mode — its "distributed" story is a hosted SaaS backend with VNC streaming, not two of the user's own machines linked directly.

**What it does validate:** its MCP server exposes a single `execute_code` tool running Python in a persistent namespace, the same code-execution-over-tool-calls bet we already made with `evaluate`. Their own published benchmarks show 3.2x fewer tokens than Playwright MCP and 6.0x fewer than Chrome DevTools MCP, with MCP response payloads 144x smaller than Chrome DevTools MCP's. That's now three separate projects (ego-lite, OpenBrowser, and the CLI benchmarks showing agent-browser losing on the same axis) converging on the same conclusion.

**One refinement worth a later look:** OpenBrowser doesn't go pure-`evaluate` — it pairs a small named function library (`navigate`, `click`, `input_text`, `scroll`, tab switch/close, dropdown helpers) with `evaluate(code)` as an escape hatch. A middle ground between our current minimal surface and a full typed-action framework, worth considering once the core MCP surface is working, not a v1 change.

## Resolved (for reference)

- ~~OAuth mechanism for the MCP server~~ — resolved: Talaria acts as its own MCP authorization server (per the MCP spec's own model — an MCP server is expected to be its own auth server, no external IdP needed for a single-user tool), built on the **rust-mcp-sdk** crate (rust-mcp-stack/rust-mcp-sdk) rather than hand-rolled, which already provides OAuth metadata discovery, CIMD/DCR, PKCE, and token refresh. Flow: Authorization Code + PKCE, public client (no secret, correct for native/desktop-style agent clients). Consent is a native "Allow?" prompt, since there's only one user, no separate login. Tokens are short-lived access + refresh, issued **per connecting agent client**, not one shared token, which gives a free per-agent revoke capability (a simple "connected agents" list with revoke buttons) without building any new permission system. Scope clarified: OAuth only applies to HTTP-based connections (distributed mode / networked agents) — a locally-spawned stdio subprocess connection doesn't go through OAuth at all, per the MCP spec itself. Doesn't conflict with the no-gatekeeping philosophy — this is connection-level access control, not the request-level permissioning/rate-limiting/audit-trail that was deliberately excluded.
- ~~Table-stakes "Me" browser features~~ — resolved per item: **history** (v1 yes, simple local log — URL, title, timestamp), **bookmarks** (v1 yes, flat list, no folders), **search/omnibox** (v1 yes, address bar doubles as search via a configurable default engine, non-URL input gets encoded into a search query), **downloads** (v1 yes, ties to the new `download` MCP tool below), **extensions** (explicitly NOT v1 — WebExtensions support is immature in Servo, same "don't take on a whole subsystem's risk for a nice-to-have" call as the rendering-correctness decision; revisit once libservo's WebExtensions story matures).
- ~~Multiple concurrent agents in the toggle UI~~ — resolved: see the "Multiple concurrent agents" core feature above — the Agents view lists active sessions by connected-client identity, reusing what OAuth already tracks.
- ~~Multi-window support~~ — resolved: single-window, multi-tab for v1 (see core features above). No OS-level multi-window support until Servo's own multi-window embedding work matures.
- ~~Update/distribution mechanism~~ — resolved: Tauri's own updater plugin handles app updates rather than a bespoke mechanism. Servo engine updates aren't a separate channel — libservo is compiled into the app, so a new Servo version just ships as part of a normal Talaria release.
- ~~Full-process/server crash recovery~~ — resolved: local mode relies on normal OS behavior (a crashed app gets relaunched by the user, nothing special to build). Distributed mode: the server periodically persists a lightweight session manifest (open tabs, URLs, connected agent identities) to disk and offers to restore it on restart, the same shape as a normal browser's "restore pages" prompt. Agent *tasks* are not auto-resumed, only browser state — resuming a task is the agent framework's responsibility, consistent with staying thin infrastructure.
- ~~Sync/backup of local state~~ — resolved: no built-in sync in v1, and this is a smaller gap than it looked, since the credential vault and session manifest are already plain local files by design, they already work with whatever backup tooling the user has (Time Machine, dotfile sync, etc.) without Talaria building anything bespoke.
- ~~Telemetry stance~~ — resolved: none, by default, stated explicitly rather than left implicit. Consistent with the local-only-credentials, no-cloud-dependency, no-audit-trail posture throughout the rest of the project.

- ~~JS engine choice~~ — resolved: SpiderMonkey, bundled with the Servo decision.
- ~~Rendering engine~~ — resolved: Servo via libservo.
- ~~Shell UI framework~~ — resolved: Tauri, targeting the experimental Servo-backed WRY webview. Chrome UI built in React. The content pane stays libservo regardless of chrome tech maturity. If the Servo WRY backend isn't stable enough at ship time, native OS webview (WebKitGTK/WKWebView/WebView2) is an accepted interim fallback for chrome *only*, never for the content pane. Reuses the framework already chosen for the separate [[insomniac]] project. **Correction (see below):** the actual Tauri-Servo integration work runs partly through the Verso codebase itself (a `tauri-runtime-verso` crate), not purely through a separate WRY branch as earlier noted here — Verso's archival means the current status of that integration path needs direct verification, not assumption.
- ~~Automation binding layer~~ — deprecated. Decided this was unnecessary added complexity; not building a custom libservo automation surface.
- ~~Credential vault implementation~~ — resolved: a JSON file of credentials paired with the URLs they apply to, matched by domain for autofill suggestion and cookie-based session reuse (`cookies.read`), **encrypted at rest** (OS keychain-backed, not plaintext). Explicitly not used by agents to perform fresh/interactive logins — that's handled by takeover, not autonomous credential use.
- ~~Real-time viewing implementation~~ — resolved: built on libservo's own `WebView::take_screenshot()` and offscreen-rendering APIs, not a custom capture pipeline. **Local mode**: an agent's WebView renders offscreen and is composited directly into the app's own UI, no network, no polling. **Distributed mode** (Tailscale split): `take_screenshot()` polled adaptively — ~200–500ms for passive supervisory viewing, ramped to ~30–60ms during active takeover — frames sent as JPEG over a WebSocket to the client, mirroring agent-browser's own live-viewport streaming pattern but built against libservo instead of CDP. Caveat: both source APIs are recent/active areas of libservo, expect some churn. This same view is where takeover happens — the `input` message type already in the distributed protocol's envelope schema is tab-id-agnostic, so it forwards user input into an agent's tab the same way it forwards input into the user's own tabs, no separate mechanism needed.
- ~~MCP tool surface scope~~ — resolved: minimal core primitives only — `tabs.list/open/close/focus`, `navigate`, `evaluate` (run arbitrary JS in-page), `screenshot` (reuses `take_screenshot()`), `cookies.read` scoped to the JSON credential file, `download(url, filename)` (added alongside the table-stakes browser features resolution below — agents need file downloads as much as the human does). No separate typed click/type/wait tools — agents handle interaction via JS written and run through `evaluate`, matching ego-browser's proven pattern, and consistent with deprecating the custom automation binding layer. No per-agent permission scoping in v1 — OAuth governs connection access only, consistent with the no-gatekeeping philosophy.
- ~~Servo WRY fallback readiness check~~ — resolved as a process, not a date: go/no-go tied to our own ship timeline, checkpoint moved to **~16 weeks before intended launch** (moved earlier than the original 8-week checkpoint — three not-production-ready dependencies, Servo itself, the experimental WRY backend, and libservo's screenshot/offscreen APIs, sit on the same critical path, and a late "not ready" verdict could force a real chrome-rendering architecture change, React-in-Servo vs. React-in-native-webview, not just a config flip, so the fallback needs more runway to execute if triggered). Checklist, re-evaluated every 4–6 weeks: (1) confirm current maintenance status of the Tauri-Servo integration path itself — `tauri-runtime-verso` and/or the standalone `servo-wry-demo` branch — since this is genuinely unclear post-Verso-archival and must be checked fresh, not assumed; (2) multiview stability; (3) offscreen rendering + `take_screenshot()` working through the Tauri path specifically; (4) React chrome IPC verified working; (5) stability soak test on first target platform (macOS), **including confirming the Tauri-Servo integration is actually as mature on macOS as assumed, not just that one demo's window-chrome polish happened to target it first**; (6) startup time/binary size roughly at parity with native webview. If unmet at the checkpoint, ship on native-webview-for-chrome fallback and swap in later.
- ~~Target platform order~~ — resolved: macOS, then Linux, then Windows.
- ~~Distributed client/server protocol~~ — resolved: a single multiplexed WebSocket per client session over the Tailscale link, envelope schema `{type: "frame" | "input" | "control" | "tabs", tab_id, payload}`, carrying JSON control/input/tab-management messages and binary JPEG frames (reusing the real-time-viewing frame format) on the same connection rather than separate sockets. Relies on Tailscale's own WireGuard encryption rather than adding a second TLS layer. Server holds session/tab state for a grace period on disconnect; client resyncs tab list and requests a fresh frame on reconnect rather than tearing the session down. The MCP server runs on the server machine (co-located with libservo) and is exposed as its own endpoint over the same tailnet — a separate concern, not multiplexed into this socket. This protocol only applies in distributed mode; local mode composites in-process with no network path at all.

- ~~Tab/process crash recovery~~ — resolved with a minimal default: on a WebContent process crash, the affected tab shows a crashed state with a reload button (same shape as Chrome's "Aw, Snap"). For agent tabs specifically, the crash surfaces as an MCP tool error/event so the agent can decide to retry or reopen, rather than silently hanging.
- ~~Baseline functional adequacy~~ — resolved as a one-time gate, not ongoing QA: before committing further engineering time, do a single manual check that a short list of daily-use sites (Gmail, a banking site, Cloudflare, a couple of common SaaS dashboards) actually loads and functions in Servo, not just renders most CSS correctly. This is a go/no-go feasibility check early in the project, distinct from and much smaller in scope than the "we don't test rendering correctness" decision above, which is about not chasing cosmetic gaps, not about skipping a sanity check that the thing works at all.

## Resolved: licensing

**Fully open source.** Dual-licensed **MIT OR Apache-2.0**, the standard convention across the Rust ecosystem (Tauri itself and most Rust crates use this pattern), which makes for one less thing to explain to contributors coming from that world. This is compatible with Servo and SpiderMonkey's MPL 2.0 licensing: MPL is file-level weak copyleft, not viral, so it only imposes obligations on files actually derived from MPL-covered source. Talaria's own code, consuming Servo and SpiderMonkey as dependencies rather than modifying their source, is free to carry its own license.
